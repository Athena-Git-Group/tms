1全文件慣例

  • 每張業務表第一欄都是 tenant_id（哪家飯店的資料），所有唯一鍵與索引以它開頭；下面各表不再重複列，一律視為存在
  • 多租戶隔離：應用層每條查詢強制帶 tenant 過濾為主，Postgres RLS 當第二道保險（Row-Level Security，資料庫內建的列級門禁：查詢沒帶對 tenant_id，連撈都撈不到別家的列）——詳 11 §4 深入探討第六題
  • 實體表主鍵一律 id uuid，用 UUIDv7 產生（一種開頭帶出生時間的隨機編號：排起來跟自動遞增一樣由舊到新，但任何一台機器不用先問資料庫就能自己產號、保證全系統不撞）——為未來分庫或多寫入點鋪路；趁文件階段零資料時改，成本最低。app 層產號即可，Postgres 18 起也有內建 uuidv7()。外鍵以 _id 結尾，型別跟著對方的主鍵走，且一律宣告成複合外鍵 (tenant_id, xxx_id) REFERENCES 對方(tenant_id, id)——外鍵檢查不經過 RLS，單欄外鍵擋不住程式 bug 填進別家租戶的 id；被引用表補一條 UNIQUE (tenant_id, id) 給複合外鍵當落點（主鍵本來就唯一，這條純粹是外鍵的靶）
  • 例外一：事件與流水表（task_events、outbox）保留 id bigint 自動遞增——但這個序號不是給訂閱者當「給我第 N 號之後的」書籤用的：序號是交易一開始取號時配發，那一列要等交易 commit 才真正看得到，兩者順序可能顛倒（先取到小號的反而晚 commit）；拿 id 當增量輪詢書籤，會永久漏掉那些晚 commit 的小號事件。所以增量訂閱一律走 Kafka（relay 轉送進度靠 outbox 的 status 欄位推進、不拿 id 當書籤，所以 relay 不會踩這個坑）；id 只用在離線全表重放與排查時當排序欄位。分庫後各庫自己編號即可：訂閱按租戶走、同一租戶不跨庫
  • 例外二：tenants.id（即各表的 tenant_id）保留 bigint——租戶由我們集中開設，量少、又不會多台機器同時產生，沒有撞號問題；而它出現在每張表每條索引的開頭，8 bytes 比 16 bytes 省一半索引空間
  • 時間一律 timestamptz（含時區）、純日期用 date
  • 值域一律全名、不縮寫：狀態九值見 11 §3 的任務狀態機；值域用 text＋CHECK 限制，不用原生 ENUM（以後加值不用改型別）
  • 「值域由 DB 擋、轉移由程式擋」：CHECK 只保證值合法；「done 不能跳回 doing」這類轉移規則由任務引擎擋（11 §2 API 共同約定的 409）
  • 狀態轉移的並發規範：守衛一律寫成一句條件式 UPDATE（例：UPDATE tasks SET state='accepted', assignee_id=…, event_seq=event_seq+1 WHERE id=? AND state='pool' RETURNING event_seq），更新到 0 列就回 409；這個事件的 seq 就用這句 UPDATE 回傳的 event_seq。禁止「先 SELECT 檢查再 UPDATE」與「SELECT max(seq)+1」——前者兩人同一秒認領同一個任務會雙雙成功，後者在並發下會撞唯一鍵、整筆交易回滾
  • 小抄表（投影）＝可清空由 task_events 重算的表，每張都會標注
  • 彈性欄位用 jsonb，但只放「結構會因飯店而異」的東西（訂房屬性、事件細節、設定值）；查詢條件要用的欄位一律開正式欄位

2核心：流水帳・小抄・待寄信匣

對應 11 附錄 A 需求 2、4、6、7、11。四張表在建單與每次狀態變更時同一筆交易寫入——事件是真相、任務是小抄，待寄信匣同車進站。

tasks——每個任務目前的狀態（小抄，可重算）

一個任務一列，只記「現在的樣子」。查房退回會直接覆寫（清計時、redo+1），歷史都在流水帳。

欄位型別必填說明
typetext必填任務種類：amenity（備品）｜repair（修繕）｜cleaning（打掃）｜other（其他，自由文字先掛這）
sourcetext必填來源：guest（住客掃碼）｜desk（櫃檯）｜system（排房、訂房屬性準備工單）
room_iduuid → rooms必填哪間房
reservation_iduuid → reservations_cache可空住客來源的任務必填：綁建單當下的訂單。住客「看這次住宿的需求」一律以它過濾，不以房號——按房號撈會讓新住客看到前一位住客的需求原文
depttext必填目前負責部門：housekeeping（房務）｜engineering（工務）｜frontdesk（櫃檯，待判讀時掛這）
statetext必填九值全名（11 §3 的任務狀態機）：triage｜pool｜accepted｜doing｜done｜inspected｜deferred｜interrupted｜cancelled（取消，終點：住客撤回、主管作廢誤建單、計畫重產收回未開始的打掃單——統計一律排除取消單）。沒有獨立的 answered 狀態：櫃檯當場回答直接結案為 done、事件記 answered、回覆存 note。deferred 延後不是不做——主管可隨時拉回（undefer），worker 隔日班前也會自動把它重新入池（事件記 returned_to_pool，payload 註明原因）
event_seqint，預設 0必填事件取號器：每次狀態轉移在同一句 UPDATE 裡 +1 並回傳，回傳值就是該事件在 task_events 的 seq——取號、行鎖、狀態守衛三件事合在同一句（見 §1 慣例）
assignee_iduuid → staff_accounts可空負責人；任務先進部門待接池、不直接指派給人，所以在池中時為空
title / notetext必填／可空一句話標題（選單項名或判讀後命名）；備註（住客原文、翻譯、交代事項、當場回答的回覆）
est_minint可空預估分鐘（打掃任務由排房帶入；credit 換算屬 Q1 未決）
started_at / done_attimestamptz可空開始／完成時間戳；實際分鐘＝兩者相減；查房退回會清空重計
redo_countint，預設 0必填查房退回次數
ratingint，CHECK 1–5可空住客評分（done 之後）；低分觸發老闆推播
plan_iduuid → cleaning_plans可空打掃任務回鏈到它所屬的排房計畫
work_datedate可空打掃任務必填、發佈時抄自排房計畫的日期——支撐「一房一天只有一筆未完成打掃」的約束與班末掃描
sla_min / esc_levelint可空保留欄位，SLA 升級鏈啟用前不寫（11 §4 深入探討第八題）
created_at / updated_attimestamptz必填建立／最後更新

鍵與索引：PK id（uuid）；(tenant_id, dept, state) 餵待接池與看板；(tenant_id, assignee_id, state) 查個人在手任務；(tenant_id, room_id, created_at) 查單房歷程；(tenant_id, reservation_id, created_at) 查住客本次住宿的需求；partial unique (tenant_id, room_id, work_date) WHERE type='cleaning' AND state NOT IN ('done','inspected','cancelled')——計畫重產或匯入重複時，資料庫擋住同房同日第二筆未完成打掃單。寫：只有任務引擎。讀：所有人。

task_events——只進不改的流水帳（唯一真相）

每件事記一行、照順序排。資料庫權限直接收走 UPDATE／DELETE，連程式 bug 都改不了歷史。唯一的例外是一條受控的去識別化函式：抹除 payload 裡的個資欄位、連動把對應的員工帳號列去識別化（姓名與登入帳號換成不可回推的代號，事件列的 actor_id 從此指不回真人），執行本身也記一筆事件——個人資料「保留期限到了要能刪」靠這條路徑成立，不是刪列。

欄位型別必填說明
idbigint 自動遞增必填全館依序編號，但不是給訂閱者當書籤用的（§1 例外一）：增量訂閱一律走 Kafka，這個序號只用在離線全表重放與排查時排序
task_iduuid → tasks必填屬於哪個任務
seqint必填這個任務的第幾步（1、2、3…）
typetext必填發生什麼事（全名）：created｜triaged｜assigned（排房指派到人）｜claimed｜started｜completed｜inspection_passed｜inspection_failed｜reassigned｜returned_to_pool｜interrupted｜deferred｜answered｜rated｜sop_checked｜plan_adjusted｜checkout_imported｜cancelled（payload 帶原因：guest_withdrew｜manager_void｜plan_superseded）…（可擴充，加值不改表）
actor_role / actor_idtext / uuid必填／可空誰做的：角色（guest｜frontdesk｜housekeeping｜engineering｜manager｜system）＋員工 id（住客與系統為空）
payloadjsonb可空細節，也是重建投影的原料：會改動 tasks 欄位的事件 payload 必填且帶齊對應值——created 帶建立快照（種類、來源、房號、訂單、標題、預估分鐘）、triaged 帶部門與命名、reassigned 帶新負責人、inspection_failed 帶不過項目、rated 帶分數；純標記類（started 這種從 actor 與時間就能還原的）才可空。驗法：CI 定期在影子庫清空 tasks 重放、與線上比對
created_attimestamptz必填發生時間

鍵與索引：PK id（bigint 序號，§1 例外一）；UNIQUE (tenant_id, task_id, seq) 讀單任務歷程；(tenant_id, id) 供離線重放與排查——增量訂閱一律走 Kafka，不拿 id 當輪詢書籤（§1 例外一）。寫：只有任務引擎（append）。讀：Kafka 下游（知識庫、儀表板投影、即時推送）一律從 Kafka 消費；直接讀本表的只有離線重放重建與排查。

outbox——待寄信匣

所有要上輸送帶的事件與副作用（任務事件、推播、PMS 房況回寫）先放這裡，和狀態變更同一筆交易落庫——交易護欄；relay 掃到後轉送 Kafka，推播、SSE 即時推送、PMS 回寫都從 Kafka 消費——tasks 是同步投影，在交易內就更新完，不走 Kafka。

欄位型別必填說明
aggregate_keytext必填relay 轉送 Kafka 時的分區鍵（排隊的隊伍名），跟著被寫入對象的一致性邊界走，不是跟著觸發它的任務走：task_event 用任務鍵 task:0199c7a2-…（任務的 uuid）；pms_status 一律用房鍵 room:1:0199c7a2-…（tenant_id:房間uuid）——同一間房的回寫不論由打掃還是修繕任務觸發，都要進同一條分區，否則「查房通過」與「冷氣報廢停用」兩筆回寫誰先誰後看運氣，壞房可能被標成可賣；push 沿用任務鍵。同鍵進同一條分區、照順序消費，卡住只擋同一條分區
kindtext必填要送什麼：task_event（任務領域事件——與 task_events 同一筆交易入匣，轉送 Kafka 後供 SSE 即時推送與 room_memory、stats_daily 等衍生投影訂閱；Kafka 下游一律不回寫 tasks——它由任務引擎在交易內同步更新）｜push（APNS／FCM 推播）｜pms_status（房況 Inspected／OOO 回寫）。minibar 計費移出 v1，啟用時加 pms_minibar
payloadjsonb必填信的內容（收件 token、回寫的房號與狀態…）
idempotency_keytext必填防重複編號：下游消費者用它判斷「這筆處理過了」，重送不會做兩次
statustext，預設 pending必填pending（待轉送）｜sent（已轉送 Kafka）｜failed（重試用盡，等人工）
attempts / next_retry_atint，預設 0 / timestamptz必填／可空試了幾次、下次幾點重試（指數退避）
created_at / sent_attimestamptz必填／可空進匣／轉送時間

鍵與索引：PK id（bigint 序號，§1 例外一）；UNIQUE (tenant_id, kind, idempotency_key)；partial index (aggregate_key, id) WHERE status='pending' 給 relay 依鍵輪詢。寫：任務引擎（入匣）、relay（改狀態）。讀：relay——下游（推播、SSE 即時推送、PMS 回寫、衍生投影）不直接讀這張表，一律從 Kafka 消費。relay 同鍵串行：某鍵最早一筆還沒送成功（含排隊等重試）時，不取該鍵的後續列；Kafka 分區只保證「進去的順序」，進去的順序由 relay 負責。sent 的列保留 3 天供排查後由排程清除——outbox 是轉運匣不是歷史，事件的永久歷史在 task_events 與 Kafka。

processed_ops——弱網重送的去重簿

客戶端每個寫入請求帶操作編號（11 §2 API 共同約定的 Idempotency-Key）；同一編號再來，直接回上次結果、不重做。

欄位型別必填說明
op_idtext必填客戶端產生的操作編號（UUID）
result_refjsonb必填當時回了什麼（狀態碼＋精簡回應），重送時原樣回放
created_attimestamptz必填第一次處理時間；過期資料由排程清（例如 7 天）

鍵與索引：PK (tenant_id, op_id)。寫：API 層。讀：API 層。

3住客與憑證

對應 11 附錄 A 需求 1、2、3、8。兩層憑證的機制見 11 §4 深入探討第五題〈住客憑證〉。

rooms——房間主檔

一張房兩系統各管一半：清潔狀態 TMS 擁有、住否 PMS 擁有，不共用欄位。

欄位型別必填說明
room_notext必填房號（「305」）；UNIQUE (tenant_id, room_no)
floorint必填樓層——v1 排房演算法的排序鍵
room_typetext必填房型（標準雙人、套房…）；平均打掃分鐘按它統計
hk_statetext必填清潔狀態（TMS 擁有）：dirty（待打掃）｜cleaned（掃完等查房）｜inspected（查房通過可賣）｜out_of_order（故障停賣）
occupancytext必填住否（PMS 擁有，同步進來唯讀）：occupied（住人）｜vacant（空房）
updated_attimestamptz必填最後變動

鍵與索引：PK id（uuid）；UNIQUE (tenant_id, room_no)。寫：hk_state＝任務引擎（查房通過／退回）、occupancy＝worker（PMS 同步）。讀：排房、房況板、Guest Access。

room_qr_tokens——房間 QR 憑證（Guest Access 擁有）

一房一枚長期有效；貼紙被撕走就重產：發新的一版、舊的立即標作廢。

欄位型別必填說明
room_iduuid → rooms必填對應房間
tokentext必填貼紙網址裡那串亂碼：至少 128 bit 隨機（base62 編碼約 22 個字元），不可預測、不含房號等可推測的資訊——例如 t.tms.tw/r/8fQ2hL9xKpD3vRw1sTzUjm 裡 8fQ2hL9xKpD3vRw1sTzUjm 這一整段；全域 UNIQUE
versionint必填第幾版；重產＋1
statustext必填active（現行）｜revoked（已作廢，掃到顯示「請洽櫃檯」）
created_at / revoked_attimestamptz必填／可空簽發／作廢時間

鍵與索引：PK id（uuid）；UNIQUE (token)；partial UNIQUE (tenant_id, room_id) WHERE status='active'——一房同時只有一枚現行。寫：Guest Access（簽發／輪替／撤銷）。讀：Guest Access 解析、內部 Web 列印。掃碼端點另有 IP 層級限流與失敗計數（11 §4 深入探討第五題）。

guest_sessions——住客 session

掃碼簽發、退房自動失效，QR 輪替或提前退房／訂單取消時立即撤銷；住客端所有請求都靠它認人。

欄位型別必填說明
session_tokentext必填發給住客瀏覽器的憑證字串；全域 UNIQUE
room_iduuid → rooms必填綁哪間房
reservation_iduuid → reservations_cache必填綁簽發當下的訂單——換住客後舊 session 自然失效
expires_attimestamptz必填到期＝退房時間
revoked_attimestamptz可空撤銷時間：QR 輪替、提前退房、訂單取消時，同一筆交易把該房所有未撤銷 session 一併標上——只看 expires_at 關不掉已經簽發出去的 session
created_at / last_seen_attimestamptz必填／可空簽發／最後活動

鍵與索引：PK id（uuid）；UNIQUE (session_token)；(tenant_id, room_id)。寫：Guest Access（簽發、以及輪替／提前退房／訂單取消時的撤銷）。讀：每個 /guest 請求，驗證條件為 expires_at > now() 且 revoked_at IS NULL，兩者缺一都視為無效。

reservations_cache——訂房檔副本（真相在 PMS）

worker 定期從 PMS 抄來的唯讀副本；PMS 接不上時由 Excel 匯入補位（來源欄位區分）。

欄位型別必填說明
reservation_reftext必填PMS 的訂單編號；UNIQUE (tenant_id, reservation_ref)。Excel 匯入列用「excel:日期:房號」合成
room_iduuid → rooms必填住哪間
guest_name / langtext可空稱謂用；住客端語言
attrsjsonb可空訂房屬性：VIP／親子／寵物／紀念日…——自動開準備工單的依據
checkin_at / checkout_attimestamptz必填住期——判斷空房掃描、session 到期、今日退房清單
sourcetext必填pms（同步）｜excel（匯入今日房態，含入住與退房）
synced_attimestamptz必填這筆副本幾點抄的
superseded_attimestamptz可空作廢時間：PMS 恢復同步、比對到同一間房住期重疊的真訂單時，自動把 Excel 匯入列標上——否則同一住宿兩列並存，掃碼可能綁到假的那筆、之後 PMS 的屬性更新全對不上。所有「當前訂單」查詢（掃碼、排房、準備工單）一律加 superseded_at IS NULL

鍵與索引：PK id（uuid）；UNIQUE (tenant_id, reservation_ref)；(tenant_id, room_id, checkout_at) 查今日退房與當前訂單；EXCLUDE 約束（Postgres 的區間互斥：同一房、住期區間重疊、皆未作廢 → 拒絕寫入）——同一間房同一時刻只能有一筆有效訂單，資料庫層面擋死。寫：worker（PMS 同步）、匯入 API。讀：Guest Access、排房、準備工單。

4排房與工時

對應 11 附錄 A 需求 7、8、9、10。計畫是獨立實體：任務開出來之前就要能預覽、請假要能新舊對照、缺口試算要拿它對比班次容量。

cleaning_plans——排房計畫（一天一班一份）

發佈新計畫與收回舊計畫在同一筆交易：兩份計畫都有的房、舊任務未開始（pool／accepted）時改掛新計畫並更新負責人與順序（事件記 reassigned）；舊有新無的房，未開始任務取消（事件記 cancelled，原因 plan_superseded）；做到一半（doing）的不自動動，列給主管處理。

欄位型別必填說明
work_date / shiftdate / text必填哪一天、哪個班次（早班／晚班，值域從租戶設定來）
statustext必填draft（草稿，可調；可與已發佈計畫並存，重產對照用）｜published（已發佈，任務已開出）｜superseded（被重產的新計畫取代，留著對照）
versionint，預設 0必填每次調整 +1；PUT /admin/plans/{date} 要帶 If-Match 版本號，不符回 409 並附最新內容——兩位主管同時調整，後存的不會無聲蓋掉先存的
generated_bytext必填system（worker 班前自動）｜manager（主管手動重產）
algo_versiontext必填排的時候用哪版演算法（v1＝樓層×工時、一層一人）——日後 Q4 v2 對照用
generated_at / published_attimestamptz必填／可空產生／發佈時間

鍵與索引：PK id（uuid）；partial UNIQUE (tenant_id, work_date, shift) WHERE status='published'——同一班同時只有一份已發佈計畫；草稿不受唯一限制——重產時新草稿與現行已發佈計畫並存對照，發佈新的那一刻舊的才標 superseded。寫：worker（產生）、主管（調整／發佈）。讀：/staff/schedule、/admin/plans、人力試算。

plan_rooms——計畫明細（誰負責哪間房）

欄位型別必填說明
plan_iduuid → cleaning_plans必填屬於哪份計畫
room_iduuid → rooms必填哪間房；UNIQUE (tenant_id, plan_id, room_id)
staff_iduuid → staff_accounts必填分給哪位清潔人員——「誰在哪天負責哪些房」就是查這張
est_minint必填這間房的預估分鐘（抄自 cleaning_time_stats，沒數據用標準工時）
route_seqint必填建議打掃順序（v1＝照樓層）
task_iduuid → tasks可空發佈後回填對應的打掃任務

鍵與索引：PK id（uuid）；UNIQUE (tenant_id, plan_id, room_id)；(tenant_id, plan_id, staff_id) 查個人當日清單。寫：worker、主管調整。讀：員工班前畫面、人力試算。

cleaning_time_stats——平均打掃分鐘（小抄，可重算）

欄位型別必填說明
room_typetext必填哪種房型；PK (tenant_id, room_type)
avg_actual_minnumeric必填平均實際分鐘＝流水帳裡 completed−started 的平均（查房退回重計的以最後一輪為準）
sample_countint必填樣本數——沒累積夠（例如 <20）之前，排房先用租戶設定的標準工時
updated_attimestamptz必填worker 最後刷新時間

鍵與索引：PK (tenant_id, room_type)。寫：worker（從流水帳聚合）。讀：排房、人力缺口試算。注意：個人層級的工時統計受分級可見與保留期限管（11 §1 非功能需求的個資約束），本表只到房型層級、不含個人。

5通知

對應 11 附錄 A 需求 5。櫃檯主動發、自選對象、追已讀。

notices ＋ notice_reads

欄位型別必填說明
notices.sender_iduuid → staff_accounts必填誰發的（櫃檯／主管）
notices.title / bodytext必填標題與內容
notices.recipientsjsonb必填收件對象，部門或個人混選：{"depts":["housekeeping"], "staff_ids":["0199c7a2-…","0199d04e-…"]}；推播經 outbox 展開成一人一封
notices.created_attimestamptz必填發送時間
notice_reads.notice_id / staff_iduuid必填誰讀了哪則；PK (notice_id, staff_id)——打開即記一筆，重開不重記
notice_reads.read_attimestamptz必填已讀時間

鍵與索引：notices PK id（uuid）、(tenant_id, created_at)；notice_reads PK (notice_id, staff_id)。寫：協作模組。讀：通知板、已讀名單。「逾時未讀升級」是 SLA 升級鏈的延後項（11 §4 深入探討第八題）。

6身分與設定

對應 11 附錄 A 需求 3、14、15。RBAC 的資料面；檢查本身在每個 API 進來時做（伺服器端強制）。

staff_accounts ＋ staff_devices

欄位型別必填說明
staff_accounts.name / login_idtext必填姓名；登入帳號，UNIQUE (tenant_id, login_id)
staff_accounts.password_hashtext必填密碼雜湊（bcrypt／argon2），絕不存明文
staff_accounts.roletext必填角色（RBAC 的 R）：frontdesk（櫃檯）｜housekeeping（房務）｜engineering（工務）｜manager（主管）｜owner（老闆）——角色×動作矩陣定義在程式／設定，不在表裡
staff_accounts.depttext可空所屬部門（接池用）；主管／老闆可空
staff_accounts.activeboolean，預設 true必填停用＝不能登入，但歷史記錄保留
staff_devices.staff_id / device_fingerprintuuid / text必填推播地址簿：一列＝一台收推播的裝置。登入不驗裝置、同一人多台都合法（11 §1 不在範圍內）；device_fingerprint 只拿來去重——同一台重複登入不重複登記，UNIQUE (tenant_id, staff_id, device_fingerprint)
staff_devices.push_tokentext可空APNS／FCM 推播地址；權限被關就是空，推播降級看板（Q6）
staff_devices.registered_at / revoked_attimestamptz必填／可空登記／失效時間（登出或推播服務回報 token 失效時標記）

鍵與索引：各 PK id（uuid）；上列 UNIQUE。寫：Identity（登入驗帳密、順手登記推播地址；token 失效時標 revoked）。讀：/auth/login 與每個 API 的權限檢查只讀 staff_accounts；推播展開讀 staff_devices。

tenants ＋ tenant_config

欄位型別必填說明
tenants.nametext必填飯店名；PK id 就是全系統的 tenant_id 來源（保留 bigint，§1 例外二）
tenant_config.keytext必填設定鍵（全名）：standard_cleaning_minutes｜shift_capacity｜inspection_items｜sop_items｜guest_info_pages（資訊頁）｜request_menu（選單）｜minutes_per_credit（Q1 換算率）…；UNIQUE (tenant_id, key)
tenant_config.valuejsonb必填設定值——結構依 key 而異，所以用 jsonb
tenant_config.updated_at / updated_bytimestamptz / uuid必填誰、何時改的——設定變更也要能追

鍵與索引：tenant_config UNIQUE (tenant_id, key)。寫：/admin/settings。讀：所有模組（「什麼都可調」的落地）。
