TMS · System Design · v0.4 · 2026-10-06

Task Engine

一個泛用任務引擎，坐在既有 PMS 旁邊。PMS 擁有訂單與住客，TMS 擁有任務與現場時間。 這份稿把服務邊界、資料歸屬、狀態機、以及只有兩條寫回 PMS 的路徑定下來， 並在最後說明為什麼這個系統不該做成微服務。

目標客群
四五星飯店（現有 PMS 客戶優先）
規模假設
單店 200–500 房 · 首年 10 店
資料主權
訂單在 PMS · 任務與工時在 TMS
寫回 PMS
只有 2 條路徑

01 — 範圍

系統要做什麼、不做什麼

要做：把三種來源的需求（住客掃碼、員工建單、PMS 事件與排程）變成一張任務，路由到正確部門的待接池，追蹤它的實際起訖時間，並在逾時未處理時自動往上升級。

不做：訂房、房價、帳務、夜核、報表 BI。這些 PMS 已經有了，重做只會製造兩份互相矛盾的真相。

非功能需求目標為什麼是這個數字
員工端可離線100%電梯、樓梯間、地下室沒訊號。按鈕必須先寫本地再重送，否則回報率上不去
任務狀態一致性強一致兩人同時按接單只能一個成功。用 CAS，不接受最終一致
住客頁面延遲< 3s住客盯著畫面等狀態變。SSE 或短輪詢
逾時偵測誤差< 60sSLA 以分鐘計，掃描週期 30 秒足夠
稽核可回溯永久履約報告與勞資爭議都要能重建當時發生什麼
多租戶隔離Row-level10 店規模不需要每家一套獨立資料庫結構（schema-per-tenant），但每張表都要有 hotelId 且強制過濾，資料庫端再開 RLS 當第二道保險

02 — 架構

請求路徑與資料歸屬

一筆住客需求從掃碼到落地的完整路徑，以及每張表存什麼欄位。

TaskEvent 是真相，Task 是投影 工時、SLA 達成率、履約報告、勞資爭議的回溯，全部從 TaskEvent 這張 append-only 表算出來，不從 Task 的當前狀態算。Task 只是為了查詢方便而維護的投影。這讓你可以事後補算任何指標，也讓「誰在幾點按了什麼」永遠可證。
clientEventId 讓離線重送變安全 員工端離線時把「按了開始」寫進 localStorage，附一個自己產生的 clientEventId（UUID）。連線後重送，伺服器用這個 id 去重。沒有這個欄位，弱網重試會產生一堆重複事件，工時資料當天就髒了。

03 — 背景工作者

沒有人呼叫也必須發生的事

逾時升級是這個系統的核心價值，而它不能靠 API 觸發——沒人呼叫就永遠不會升級。所以它必須是獨立的 worker。

04 — 狀態機

Task 的生命週期

五個主狀態、三條分支。注意 escalated 是旗標不是狀態——升級的任務仍然在池子裡等人接，只是多了人在追。

05 — 介面

核心 API

Endpoint呼叫者用途與關鍵細節
POST /intake/guest住客（無登入）Body 帶 qrToken。伺服器解析房號與當前訂單。同房限流 3 筆 / 10 分鐘。非住期回 409 room_vacant
GET /guest/track/:token住客（無登入）SSE 串流該房目前進行中的任務狀態。住客關掉頁面後重掃 QR 可回到同一頁
GET /pool?dept=員工部門待接池。只回該員工所屬部門，工務單對房務回傳但標 readOnly
POST /tasks/:id/accept員工CAS：UPDATE … WHERE state='pool'。影響列數 0 就回 409 already_taken。兩人同按只有一個成功
POST /tasks/:id/events員工統一的事件入口（start / done / interrupt / transfer / photo）。必帶 clientEventId 做冪等去重
POST /tasks/:id/inspect查房員通過則觸發 PMS 房況回寫；任一項不過則退回原清房者（狀態回 accepted）、重掃次數加一、計時歸零，並記錄退回原因。清房者不得查自己的房
POST /shifts/:date/leave主管標記請假。伺服器同步把該員 accepted 退回池、doing 標為 interrupted，並回傳新的人力缺口試算
GET /capacity/:date主管需求 credit 對可用 credit，附三個可執行選項（呼叫候補 / 降級 / 延後）與各自代價
POST /commitments業務公司戶承諾模板。入住前 24h 由 Dispatch Worker 展開成跨部門任務
GET /reports/fulfilment業務履約報告。全部從 TaskEvent 重算，不讀快取

06 — 規模

算一下真實流量

這一節的結論會改變整個技術選型，所以先算清楚再決定架構。

項目單店 / 日10 店 / 日推算依據
房務任務~4004,000300 房 × 1.3（退房清 + 續住清 + 夜床）
住客需求~90900300 房 × 0.3 筆／間夜（保守估）
工務單~15150現場回報 + 預防保養排程
Task 總量~5055,050—
TaskEvent 寫入~2,50025,000每張 task 平均 5 個事件
平均寫入—0.3 / s25,000 ÷ 86,400
尖峰寫入—~8 / s08:00–11:00 集中，取平均 × 25 倍
尖峰讀取—~60 / s300 位員工在線 + 住客 SSE 連線
年儲存量—~9M 列 / 數 GB25,000 × 365，含 payload

結論：不要做微服務

尖峰 8 次寫入／秒、60 次讀取／秒、一年幾 GB。這是一台 Postgres 加一個單體應用就綽綽有餘的流量，而且未來成長 100 倍也還在同一台機器的能力範圍內。

所以：單一應用程式 + 幾個背景 worker + 一個 Postgres。不要訊息佇列（用 DB 當 outbox）、不要服務網格、不要 Kafka、不要 Redis 快取（除了 session 與限流）。

但模組邊界要照第 02、03 節切乾淨——Intake / Routing / Task / Dispatch / Notification / PMSAdapter 各自獨立、只透過明確介面互動。這樣真的需要拆的那天才拆得開；現在就拆只會讓你用分散式的痛苦去換不存在的擴展性。

唯一真正需要注意的效能點 早上 08:00 派工那一刻，300 位員工的手機同時拉取「我的今日任務」。這是可預測的尖峰，用推播（把清單直接推給他們）而不是讓所有人同時輪詢，就完全避開了。

07 — 決策

關鍵取捨

決策選擇放棄了什麼
任務歸屬先進部門池，assignee=null放棄「一眼看出誰該做」的簡單性，換到請假、交班、離職都不斷線
真相來源append-only TaskEvent放棄寫入的簡潔（每個動作要寫兩張表），換到永久可稽核與可補算任何指標
需求分類規則引擎，非 LLM放棄自由文字的彈性，換到可解釋、可稽核、零推論成本。LLM 只做兜底分類與翻譯
PMS 整合可插拔 adapter，寫回只 2 條放棄深度整合能做到的自動化，換到三個市場一套產品、且不被自家 PMS 綁死
員工端Web + Flutter App（一套 Dart 碼出 iOS 與 Android）放棄員工端的零安裝（要裝 App），換到可靠的離線回報與原生推播（APNS／FCM）；住客端維持免安裝 Web。（2026-09-29 D5 修訂，原為 LINE LIFF——見文件 11）
缺人處理自動偵測與試算，人工決策放棄全自動重派的「聰明」，換到主管不會在第一週關掉它
部署形態單體 + worker + 一個 DB放棄微服務的獨立部署，換到一個人也維護得動、故障面極小
多租戶Row-level（hotelId）放棄 schema 級隔離，換到遷移與查詢簡單。代價是每個查詢都必須強制過濾——用 ORM 層攔截，不靠開發者記得，並開 Postgres RLS 當第二道保險

阻塞級

自家 PMS 能不能推事件？

如果能訂閱 reservation.changed，Adapter 是薄的。如果只能輪詢或只有報表匯出，就要自己做變更偵測與去重——工作量差好幾倍。去問 PMS 團隊，不要假設。

影響資料模型

credit 還是分鐘？

四五星習慣 credit，但實際量測出來是分鐘。目前設計是兩個欄位並存加換算率。要確認客戶的 credit 定義是否每家不同——如果是，換算率要進 CleaningStandard 而不是全域設定。

合規

工時資料的勞資與個資界線

量測員工實際工時等同績效監控。需確認：資料保留多久、誰能看到個人層級、能不能用於考核。這會影響 API 的權限設計，不是上線後再補的政策。

可延後

離線衝突的處理策略

兩位員工都離線、都對同一房間按了開始，回到線上怎麼辦？目前用 clientEventId 去重可以避免重複，但不能解決衝突。建議 v1 用「先到先贏 + 通知後到者」，v2 再細緻化。

09 — 佇列與多租戶

10 個租戶，不需要 message queue

結論先講：引入 MQ 會把 outbox 剛解掉的問題又帶回來。但多租戶確實有一個真問題，而它不是 MQ 能解決的。

Outbox 的邊界最容易寫錯的地方

不是「業務 transaction 成功之後再寫一筆 event」——那是兩個 transaction，中間 crash 就會出現「業務改了但事件沒了」，而這正是 outbox 要解決的問題本身（dual-write）。

正確的是：業務資料與 outbox 那一筆，在同一個 transaction 之內一起 commit。要嘛都成功，要嘛都失敗，沒有中間狀態。

at-least-once 是前提，不是缺陷 worker 可能「外部呼叫成功了，但還沒標記 done 就掛掉」，重啟後會再送一次。所有消費端與外部呼叫都必須冪等——這是分散式副作用的固有性質，換成 Kafka 也一樣。

outbox 不是 task_events

兩張表都在記「發生了什麼」，但用途相反。混成一張會很痛：一張你永遠不會刪，另一張你希望它永遠只有幾百列。

—task_eventsoutbox
用途稽核與真相來源，算工時、SLA、履約報告待投遞的副作用
保留永久投遞完即可清掉或歸檔
規模一直長（約 9M 列／年）穩定維持在數百列
讀取者Metrics Worker、報表、爭議回溯只有 relay worker 與 reaper
刪除風險刪掉就無法重建指標刪掉只是少一次通知
 
-- 同一個 transaction 內三個寫入
BEGIN;
  UPDATE tasks SET state='accepted', assignee_id=$1, accepted_at=now()
   WHERE id=$2 AND hotel_id=$3 AND state='pool';      -- CAS，rowCount=0 就整筆 rollback

  INSERT INTO task_events (task_id, type, actor_id, at, client_event_id)
  VALUES ($2, 'accepted', $1, now(), $4)
  ON CONFLICT (client_event_id) DO NOTHING;                -- 離線重送去重

  INSERT INTO outbox (hotel_id, lane, topic, payload, dedupe_key)
  VALUES ($3, 'realtime', 'notify.guest', $5, 'task-'||$2||'-accepted');
COMMIT;

-- ─────────────────────────────────────────────

CREATE TABLE outbox (
  id          bigserial   PRIMARY KEY,
  hotel_id    uuid        NOT NULL,
  lane        text        NOT NULL,                        -- 'realtime' | 'bulk'
  topic       text        NOT NULL,                        -- notify.push | pms.writeback | commitment.expand
  payload     jsonb       NOT NULL,
  dedupe_key  text        UNIQUE,                          -- 同一副作用只投一次
  run_at      timestamptz NOT NULL DEFAULT now(),          -- 延遲、排程、退避全靠這一欄
  status      text        NOT NULL DEFAULT 'pending',     -- pending | claimed | done | dead
  attempts    int         NOT NULL DEFAULT 0,
  claimed_at  timestamptz,
  last_error  text
);
CREATE INDEX ON outbox (lane, run_at) WHERE status = 'pending';
CREATE INDEX ON outbox (claimed_at)   WHERE status = 'claimed';   -- reaper 用

-- ─────────────────────────────────────────────
-- 領取：短交易，絕不在持有交易時打外部 API

BEGIN;
  WITH claimed AS (
    SELECT id FROM outbox
     WHERE status = 'pending' AND lane = $1 AND run_at <= now()
     ORDER BY run_at
     LIMIT 50
     FOR UPDATE SKIP LOCKED          -- ← 沒這行，多個 worker 會重複投遞
  )
  UPDATE outbox o
     SET status='claimed', claimed_at=now(), attempts=attempts+1
    FROM claimed c WHERE o.id = c.id
  RETURNING o.*;
COMMIT;
-- 然後才做外部呼叫 → 成功 UPDATE status='done'
--                  → 失敗 status='pending', run_at = now() + 指數退避
--                  → attempts > 8 則 status='dead' 並告警（沒有死信，壞資料會無限重試）
run_at 順便解掉兩個排程需求 入住前 24 小時展開業務承諾、SLA 逾時檢查排到 10 分鐘後——都只是插一筆 run_at 在未來的 outbox 列。不需要另一套 scheduler，也不需要 cron 表達式。

多租戶唯一的真問題：批次會餓死即時

早上 08:00，一家 500 房飯店丟 650 筆晨間派工進佇列。這時候另一家飯店的住客按了「我要水」——那筆有 10 分鐘 SLA 的通知，不能排在 650 筆批次後面。

這才是 10 個租戶真正會遇到的問題，而它不是換 MQ 能解決的（用 MQ 也是要分兩個 queue）。解法是分道：

lane裝什麼worker 節奏公平性策略
realtime住客需求通知、SLA 逾時升級、接單推播poll 2s量小，先到先服務即可
bulk晨間派工、每日報表、履約展開、PMS 同步poll 30s每租戶每輪限量，避免單店霸佔整輪
 
-- bulk lane 的租戶公平性：每輪每個飯店最多取 10 筆
WITH fair AS (
  SELECT id, row_number() OVER (PARTITION BY hotel_id ORDER BY run_at) AS rn
    FROM outbox
   WHERE status = 'pending' AND lane = 'bulk' AND run_at <= now()
)
SELECT id FROM fair WHERE rn <= 10 ORDER BY id LIMIT 50 FOR UPDATE SKIP LOCKED;

-- 10 個租戶其實還輪不到這個。但先寫下來，長到 50 家時你知道要動哪裡。

10 個租戶真正需要的五項配置

項目做法為什麼是這樣
租戶隔離每張表 hotel_id，在 repository／ORM 層強制過濾不靠開發者記得加 WHERE。再開 Postgres RLS（Row-Level Security，資料庫自己依 hotel_id 擋下別家資料列的內建機制）當第二道保險——應用層萬一有漏，資料庫還會擋（2026-10-06 修訂，原立場「10 家規模僅用應用層攔截」；與文件 11 §9 一致）
佇列公平性outbox 兩條 lane，兩個 worker批次餓不死即時。這是唯一真正的多租戶問題
每租戶設定RoutingRule、CleaningStandard、SLA、credit 換算率設計裡已有。credit 定義每家不同，換算率必須綁 hotelId 而非全域
資料庫單一 Postgres、單一連線池不要 per-tenant DB。10 家的 schema migration 就會讓你想死
匯出與刪除依 hotel_id 匯出／刪除的獨立路徑個資法會被問「能不能只給我們家的資料」。先寫好，不要臨時湊

什麼時候才真的該加 MQ

給具體門檻，不要憑感覺。MQ 是外部系統，而你的業務資料在 Postgres——「改 DB + 發 MQ」就是 dual-write，你還是需要 outbox 來保證一致。所以 outbox 是前提，MQ 只是 relay 的目的地換一個，對正確性沒有任何改善。

MQ 通常解決你現在的情況判定
吞吐與緩衝尖峰 8 writes/sPostgres 隨手上千。不需要
扇出給多個獨立消費者消費者就是自己的幾個 worker不需要
跨團隊解耦部署週期一個團隊、一個應用不需要
外部呼叫的重試與退避真需求attempts + run_at 已解決
延遲與排程工作真需求run_at 已解決
同 key 有序需要（同一 task 的事件順序）Postgres 免費給你：ORDER BY id

引入 MQ 的四個門檻，達到任一個再談

一、持續寫入 > 500/s —— 目前估算的 60 倍。
二、需要跨服務獨立部署，而那些服務由不同人維護。
三、事件要被你控制不了的外部系統消費（例如客戶自己要訂閱）。
四、需要長期 replay —— 但這個你已經有了，task_events 就是 append-only 事件流。

以第 06 節的成長曲線，前三個大概三年內都不會發生。

10 — PMS 整合契約

到底需要 PMS 給什麼

短答：「今日退房清單」只能跑一半。而且要注意——清潔的觸發必須是「實際退房」，不是訂單上的退房日期。客人還在房裡的時候房務不能進去。

資料需求分層

依「沒有的話會怎樣」排序。Tier 0 是能開機的最低限度，Tier 1 才是四五星能上線的門檻。

層需要的資料用在哪沒有的話
T0 今日退房房號清單 產生退房清任務 整個系統沒有東西可做
T0 房間主檔
房號 · 樓層 · 房型 · OOO/OOS		 房型 → 清潔標準時間；樓層 → 派工聚合 所有房間用同一個預估值，派工無法聚合樓層，E2 要找的 10% 浪費消失
T1 checkout.completed
實際退房事件 + 時間戳		 觸發清潔任務進池 只能早上批次產生「今日待退」，實際觸發要人工確認 → 自動化價值掉一半
T1 reservation.changed
延遲退房 · 換房 · 提早入住 · 取消 · no-show		 重算今日清潔清單與派工 清單早上準、中午開始錯。房務會去敲還有客人的房門
T1 續住 / 空房清單 續住清、空房巡、夜床 只能做退房清，覆蓋不到一半的房務工作量

三種整合品質，各自能做到什麼

這張表直接回答第 08 節的第一個阻塞級待決事項——先去問 PMS 團隊落在哪一格，再決定 v1 範圍。

整合形態能做到做不到Adapter 工作量
A · Webhook / 事件訂閱
最理想		 全部。實際退房即時觸發、訂單變更即時跟上、房況即時回寫 — 薄。接事件、轉成內部 event、寫 DB

C · 報表 / CSV 匯出
最差		 早上產生今日清潔清單、事後統計 實際退房觸發、訂單變更跟進、房況回寫全部做不到。系統退化成「數位版的紙本房況表」 薄，但價值也薄。只適合無 PMS 的中小型客戶當過渡

如果自家 PMS 只到 C

那就不要一開始做四五星。C 級整合下的 TMS 沒有自動化，只是一個比較好看的紙本房況表——四五星客戶看得出來，而且他們已經有 PMS 報表。

這種情況下比較務實的路線是：先投資把自家 PMS 的事件介面做出來（這件事本身對 PMS 產品也有價值），或者先用手動／CSV adapter 打中小型市場驗證產品，等事件介面就緒再回頭打四五星。
