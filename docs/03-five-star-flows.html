五星動線

四張流程圖：住客從送出需求到看見「已送達」、房務從前一晚排班到查房放行、 老闆的三種節奏、業務的承諾到履約。 四五星有真正的部門分工，所以動線跟中小型旅宿不只是規模差異——有一條路由必須改掉。

00 — 前提

四五星和中小型不是同一條動線

先修正一個路由

前一份文件用「我要水 → 櫃檯」當範例——那是中小型旅宿的路由，因為小旅館櫃檯兼房務。

在四五星，備品是房務部樓層服務員送的，不是櫃檯。櫃檯／話務中心的角色是監看、跨部門協調、客訴升級，不是執行。這條路由如果照小旅館的寫，第一天上線櫃檯就會被灌爆，而房務部完全不知道有需求進來。

01 — 住客端

從送出需求到看見「已送達」

你問的三個問題都在這張圖上：需求怎麼進來、櫃檯在哪個環節、住客怎麼知道處理完了。

住客關掉頁面怎麼辦 這是實務上一定會發生的。三層處理：一、QR 貼紙隨時可再掃，回到同一頁看得到進度（token 綁房號，不綁 session）。二、四五星多有官方 LINE／WhatsApp，願意的住客可選擇綁定接推播，但不強制、不要求輸入手機號。三、不做 email 通知——沒人會為了一瓶水去收信。
話務中心必須看得到 QR 進來的單 四五星的住客習慣打電話。如果 QR 的單只進房務部、話務中心看不到，住客打電話追問時話務會重複建一張單，樓層送兩次水，然後這個系統當週就會被判定「越用越亂」。監看板不是儀表板，是防重複的必要機制。
會員等級決定 SLA，不決定要不要做 VIP／高等級會員縮短 SLA（10 分鐘變 5 分鐘）、提高優先序，這是合理的。但不要讓一般房客的 SLA 長到形同沒有——那會讓逾時升級機制失效，而那正是系統的核心價值。

02 — 房務端

從前一晚排班到查房放行

四五星房務有五個角色參與同一條動線。查房是強制關卡——這是跟中小型最大的結構差異。

credit 和分鐘要同時支援 四五星習慣用 credit／point 計算房務工作量（退房清 15cr、續住清 8cr、夜床 4cr），因為它已經內含品牌標準的作業時間。但你的 T1／T2 拿到的是實際分鐘。兩者要能換算，而且第一個月後用實際值回頭校正 credit 定義——「這家飯店的 15cr 其實要 42 分鐘」就是你賣給 GM 的第一份洞察。
夜床（Turndown）是被遺忘的那一半 四五星傍晚有夜床服務，而它幾乎從來沒被數位化過——房務員拿紙本名單，做完沒人知道。這是 recurring task 的天然場景，而且示範成本極低、GM 有感度很高：夜床完成率是可以立刻拿出來看的數字。第一版就該包含。
Minibar 與遺留物 房務員在房內發現 minibar 消耗要計入住客帳、發現遺留物要進 Lost & Found。兩者都是「在清潔任務裡順手回報」的動作，schema 只要多一個附加欄位。但 minibar 計費會寫進住客帳，必須雙向寫 PMS——這是第二條需要寫入權限的路徑（第一條是房況回寫）。

03 — 老闆 / GM

三種節奏，不是一個儀表板

老闆的動線跟前兩個本質不同——他不執行任務，他接收聚合結果並做決策。所以不要畫成流程，要畫成節奏。

不要做 BI 四五星的 GM 已經有 PMS 的報表、有集團的 BI、有財務系統。你的價值不是再做一個儀表板，是提供只有你有的資料：實際清潔工時、SLA 達成率、跨部門任務軌跡、住客需求評分。這四項全部是 PMS 拿不到的。把它們算成三個數字推給他，比做十張圖有用。

04 — 業務 / Sales

從承諾到履約證明

業務的動線是四個角色裡最容易被低估的，因為它反過來跑——先有承諾，再自動變成任務，最後要能證明做到了。

履約報告裡放什麼

  • 承諾達成率 —— 本季度貴公司客人住 128 晚，合約承諾項目 384 項，完成 381 項，未完成 3 項及原因
  • 需求回應表現 —— 提出需求 47 件，平均回應 8.2 分鐘，SLA 達成率 96%，逾時 2 件已致意
  • 客訴與處理軌跡 —— 1 件，發生時間、升級到誰、幾分鐘內解決、後續補償
  • 住客評分 —— 貴公司客人平均 4.6 / 5，全飯店平均 4.3

這份報告解決業務最尷尬的處境：談續約時只能講感覺，客戶抱怨時只能道歉。有了 task 軌跡，續約談判從「請多支持」變成「數字在這裡」。

這是四五星才成立的 use case 中小型旅宿沒有真正的業務職能、沒有公司戶合約、沒有 MICE。這條動線是你們選四五星當第一市場才拿得到的東西——而它剛好也是最難被 PMS 廠商複製的，因為它需要跨部門的任務軌跡，而 PMS 只有訂單。
MICE / 宴會是同一條動線的放大版 會議室設置、視聽設備、餐飲時段、翻桌——本來就是 task 密集且跨部門的場景，而且現在幾乎全靠紙本 function sheet。同一個 task 模板機制直接適用，但建議放 v2：它的複雜度（時段依賴、場地衝突、設備庫存）比客房高一個量級，會拖慢 v1。

05 — 收斂

四條動線共用的東西

四張圖看起來很不一樣，但底層只有一組東西。這是驗證 schema 夠不夠通用的方式。

動線進單來源執行者閉環方式v1 該不該做
住客QR（guest）房務樓層 / 工務 / 餐飲住客頁面即時狀態 + 評分做
房務PMS 事件 + recurring（system）房務員 → 查房員回寫 PMS「可售」做
老闆 / GM不進單，讀聚合—三種節奏的推播做即時 + 每日
業務合約模板（staff，pre-arrival）房控 / 房務 / 櫃檯履約報告做（差異化最強）
MICE / 宴會function sheet 模板跨五個部門活動後結案報告v2
只有兩條路徑需要寫入 PMS 房況回寫（Inspected → 可售、不可售鎖房）與 minibar 計費。其他全部單向讀取。把寫入面縮到最小，整合風險和你們自家 PMS 的耦合度都最低，日後要接第三方 PMS 也最容易。
這四條動線是 v1 的目標設計，其中住客端與房務端的核心假設（房務願意每間房回報兩次、離線回報可靠）尚未驗證。
改到四五星後有兩個假設值得重測：房務員的數位接受度可能高於中小型（有正式訓練體系與班表），但部門本位與既有 SOP 的阻力會高得多——導入的難點會從「員工會不會用」轉移到「部門主管願不願意讓流程被看見」。
