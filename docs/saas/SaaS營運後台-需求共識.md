# SaaS 營運後台：需求共識

> 產出日期：2026-10-22
> 狀態：需求已確認，待寫成正式規格
> 產品線：飯店 SaaS

---

## 1. 定位與目標

| 項目 | 內容 |
|---|---|
| 使用者 | 公司內部人員：管理員、業務、實施、客服、主管 |
| 不包含 | 飯店端自己用的管理後台（Tenant Admin） |
| 架構 | 真正的多租戶雲端，一套系統服務所有飯店 |
| 預估規模 | 約 100 家飯店 |

**要解決的痛點**

1. **新飯店上線**：上線流程靠人工、進度無法追蹤、每家都從頭設定
2. **授權與計費**：方案、模組、數量、到期日沒有集中管理
3. **帳號權限**：內部人員權限沒有分層；飯店帳號要手動處理

---

## 2. 核心設計決策

### 2.1 租戶模型

- 採**兩層**結構：`集團 → 飯店`
- 合約可以掛在集團層，一份合約涵蓋多家飯店；也可以掛在單一飯店
- 機台不是一個租戶層級（見 2.3）

### 2.2 技術棧與系統邊界

| 項目 | 決策 |
|---|---|
| 後端 | Java |
| 前端 | React |
| 資料 | 後台有自己的 DB，存租戶、合約、授權、上線清單、稽核紀錄 |
| 和產品端的整合 | 呼叫產品端的 **Admin API** 寫入設定和帳號；產品端呼叫後台的 **License API** 讀取授權狀態 |
| API 開發分工 | 後台定義 API 契約（OpenAPI），產品團隊依契約實作 Admin API 和 License client |

```
┌──────────────────┐   Admin API（寫設定／帳號）   ┌──────────────────┐
│                  │ ───────────────────────────▶ │                  │
│   營運後台        │                              │  產品端           │
│  (Java + React)  │ ◀─────────────────────────── │  (PMS 等)        │
│                  │   License API（讀授權、快取）  │                  │
└────────┬─────────┘                              └──────────────────┘
         │
    後台 DB（租戶／合約／授權／上線清單／稽核）
```

### 2.3 授權模型

- **收費依據**：依飯店訂閱、依模組開通、依機台數或房間數
- **方案結構**：方案 → 模組開關（feature flag）→ 數量上限 → 起訖日
- **數量上限**：只記錄合約上的數字，系統**不強制檢查**
- **到期處理**：
  - 到期前 **30 天**和 **7 天**提醒業務
  - 到期後有 **14 天寬限期**，期間功能照常
  - 寬限期過後，**關閉該模組**
  - **主管**可以手動延展寬限期
- **授權怎麼生效**：產品端呼叫 License API，結果快取約 5 到 10 分鐘。**API 掛掉時沿用最後一次的狀態，不中斷服務**

### 2.4 計費範圍

- 只記錄合約和授權資訊：方案、金額、起訖日、到期提醒、匯出給財務
- **不做**：自動產生帳單、線上收款（金流）、電子發票

### 2.5 帳號與權限

**內部人員**

- 用公司**內部 AD／LDAP** 的 SSO 登入，離職時帳號自動失效
- 固定五種角色，對應 AD 群組：

| 角色 | 權限範圍 |
|---|---|
| 管理員 | 全部功能、系統設定 |
| 業務 | 合約、方案、授權的新增與修改 |
| 實施 | 租戶建立、上線清單、租戶設定 |
| 客服 | 只能查看，加上重設飯店帳號密碼 |
| 主管 | 查看全部、延展寬限期、核准敏感操作 |

**飯店帳號（代管）**

- 替飯店建立管理員帳號、重設密碼、停用帳號
- **不做**代客登入（impersonation），列入之後的規劃

### 2.6 上線流程

- 每家新飯店都有一份**上線清單（Checklist）**，可以看到每個步驟的狀態、負責人和完成時間
- **從範本館複製**：選一家已上線的飯店當範本，一鍵複製它的設定
- **不做**：匯入 Excel、飯店自助填寫（第二階段）

### 2.7 租戶設定內容

| 類別 | 內容 | 維護方式 |
|---|---|---|
| 基本資料 | 名稱、地址、統編、聯絡人、時區、預設語系、幣別 | 表單 |
| 品牌資產 | LOGO、主色系、圖片 | 上傳和預覽 |

### 2.8 稽核紀錄（Audit Log）

- **所有寫入操作**都要記錄
- 每筆紀錄包含：操作者、時間、租戶、操作類型、改前內容、改後內容
- 可以依租戶、操作者、時間區間查詢
- 稽核紀錄只能新增，不能修改或刪除

## 3. MVP 範圍

**人力與時程**：1 到 2 人，約 3 個月

| # | 模組 | 重點功能 | 要用到的產品端 API |
|---|---|---|---|
| 1 | SSO 和角色權限 | AD／LDAP 登入、AD 群組對應角色 | — |
| 2 | 租戶管理 | 集團和飯店的新增、修改、查詢、停用；基本資料；品牌資產 | Admin API（同步設定） |
| 3 | 合約與授權 | 方案、模組開關、數量上限、起訖日、到期提醒、寬限期與延展、License API | 產品端 License client |
| 4 | 上線管理 | 上線清單、從範本館複製 | Admin API（寫入設定） |
| 5 | 飯店帳號代管 | 建立管理員、重設密碼、停用 | Admin API（帳號） |
| 6 | 稽核紀錄 | 記錄所有寫入、提供查詢介面 | — |

## 4. 第二階段（之後再做）

- 飯店自助填寫設定（寄連結給飯店填）
- 匯入 Excel
- 代客登入（impersonation），需搭配稽核和飯店授權
- 自動產生帳單和請款單
- 多語系文件內容（條款、公告、單據文字）
- 各模組的業務參數設定
- 強制檢查機台數和房間數的上限
- 飯店端自用的管理後台（Tenant Admin）

## 5. 風險與建議

### ⚠️ 風險：產品端目前沒有任何 Admin API

MVP 的模組 2 到 5 都要靠產品團隊開發 API 才能串接。後台本身可以在 3 個月內完成，但**能不能上線取決於產品團隊的排程**。

**建議做法**

1. **第 1 到 2 週**：後台寫出 OpenAPI 契約（Admin API 和 License API），跟產品團隊一起確認，並排進他們的開發排程
2. **開發期間**：後台用 mock server 對著契約開發，不必等產品端完成
3. **整合順序**：
   1. License API：產品端只需「讀」後台資料，改動最小、風險最低
   2. 租戶設定寫入（基本資料、品牌資產）
   3. 飯店帳號代管 API

### 其他注意事項

- 產品端快取授權狀態時，要定義**快取時間**和 **API 掛掉時的行為**，避免後台出問題時飯店無法營運
- 「關閉模組」這個動作對飯店營運影響很大，建議關閉前再發一次通知，並記錄在稽核紀錄中
- AD 群組和角色的對應關係，要跟 IT 部門確認群組命名和管理權責
