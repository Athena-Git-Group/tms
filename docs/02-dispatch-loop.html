TMS · 運作流程與 Use Case

派單迴圈

一個泛用 task 引擎、三種進單管道、四種角色視圖。 這份文件把「305 要一瓶水」和「今天有 22 間房要清、但一個人請假」 兩條路徑從頭走到尾——包括訊息最終落在哪裡， 以及為什麼不該做全自動重派。

00 — 骨架

一張 task，三種進單方式

房務、櫃檯、工務不是三個系統，是同一張 schema 的三組 preset。這個決定 v1 就要做對，否則第 6 個月要重寫。

task = {
  // 來源 —— 三種進單管道
  source:      guest | staff | system,   // QR 房客 / 員工建單 / PMS事件·排程
  room:        "305",
  reservation: "R-88421",               // 由房號 + 當前住期解析

  // 路由 —— 規則引擎填入，不是人選的
  dept:        housekeeping | frontdesk | maintenance,
  type:        "備品-礦泉水",
  priority:    normal | urgent,
  sla_min:     15,                      // 逾時就升級，這是 LINE 群組做不到的事
  est_min:     5,                       // 預估工時 → 排程與人力預測

  // 執行 —— 實際值，這是差異化資料
  assignee:    null,                    // 先進部門池，不直接指派人
  started_at:  null,                    // T1 時間戳
  done_at:     null,                    // T2 時間戳 → 實際工時 = T2 - T1

  checklist:   [...], attachments: [...],
  recurring:   null,                    // 預防保養、週期性深度清潔
  lang:        "zh-TW"                  // 房客端多語，員工端自動翻譯
}

est_min 對比 T2−T1 就是你的護城河

Flexkeeping 有 est_min（指派預估分鐘數，用於排程與人力預測），但沒有量測實際起訖。你同時有兩者，「預估錯得多離譜」這件事只有你算得出來——那才是老闆願意付錢看的數字，單純量工時是苦力活。

01 — 房客

「305 要一瓶水」最終落在哪裡

你問的訊息終點：不是某個人的收件匣，是部門的待接池。這個差別在請假、交班、離職的時候決定系統會不會斷掉。

QR token 的三個實作細節

token 綁房號，不綁住客。貼紙 t.tms.tw/r/aXk9 對應 305 號房，後端用「該房目前的訂單」解析成住客。退房換人後同一張貼紙自動對新住客生效——不需要每次換 QR。這點如果做錯，房務每天要換貼紙，產品當天就會被丟掉。

空房掃描要有正確回應。非住期掃到就顯示「本房目前未入住，如需協助請洽櫃檯」，不要進單。否則清潔人員和維修師傅會製造大量幽靈需求。

限流。同房 10 分鐘內最多 3 筆。小孩拿手機亂掃是真實情境。

02 — 端點取捨

App、QR、還是 LINE

答案依角色不同。把所有人塞進同一個端點是這類產品最常見的死法。

角色端點要不要 App理由
房客 QR → 手機網頁 絕對不要 住 1 晚不會裝 App。無登入、無需輸入房號、多語（日英韓）圖示選單，備註欄放最後。
房務 / 工務 LINE 官方帳號 + LIFF 不要（先） 競爭對手是 LINE 群組——不取代它，住進去。零安裝、零新帳號。同一網址提供帳密登入的 web 版，給不願用私人 LINE 的員工。
櫃檯 / 值班主管 桌機 web + LINE 推播 不要 房況板需要大畫面一頁看完。他們有電腦，但離開櫃檯時要收得到推播。
外包清潔團隊 LINE LIFF（受限視圖） 不要 只給「今日任務 + 完成回報 + 月結對帳」，看不到房客資料與其他部門。
老闆 每日 LINE 推播 不要 老闆不會登入 dashboard。三行數字推給他，想看細節再點進來。

LIFF 的四個實務限制，先算清楚再決定

一、推播要錢。LINE 官方帳號按方案分級計費，超量另計。每天每人 8 條任務推播 × 30 天 × 客戶數，這筆成本要進定價模型，不能事後才發現。

二、要先加好友才推得到。員工必須加官方帳號為好友，離職要記得解除綁定，否則前員工還收得到房號資訊。

三、員工可能拒絕用私人 LINE 工作。這是勞資議題不是技術議題，web 版備案不是 nice-to-have，是必須。

四、LINE 內建瀏覽器的行為差異。iOS 與 Android 的相機權限、檔案上傳、背景 tab 行為都不同，拍照回報功能要在兩邊都實測。

03 — 房務日循環

從前一晚 23:00 到隔天查房

這是系統每天真正在跑的迴圈。時間點是實務排班的節奏，不是隨便訂的。

23:00產生今日清潔清單system
  1. 從 PMS（或手動名單）取得今日到離 → 為每間房判定清潔類型
  2. 套用預設工時：退房清 35min · 續住清 18min · 空房巡 8min · 加床 +10min
  3. 加上 recurring 任務：週期性深度清潔、冷氣濾網、地毯
  4. 產生預估總工時。例：退房清 14 + 續住清 6 + 空房巡 2 = 614 分鐘 ≈ 10.2 人時

設計決定清潔類型的預設分鐘數要每家旅館可調，而且第一個月後用實際 T2−T1 自動建議修正值。用業界平均值寫死，第一週就會被房務主管罵。

07:30人力對帳（不是排班）房務主管
  1. 主管打開房況板，看到今日預估 10.2 人時 vs 今日排班 3 人 × 8h
  2. 系統扣掉非清潔工時（備品整理、洗衣、樓層移動的歷史平均）
  3. 顯示結論：「人力充足」或 「缺 1.4 人時」 + 三個具體選項

設計決定系統只做試算與推薦，不做決策。缺人時給選項（叫候補 / 降級服務標準 / 延後無入住房間），由主管按下去。自動降級服務標準會出事，而且主管會立刻關掉這個功能。

08:00自動派工system
  1. 樓層聚合 —— 同一人的房間盡量集中同樓層。這是 E2 要找的那 10% 浪費，也是軟體唯一能修的結構性浪費
  2. 依預估分鐘數平衡，不是依房間數平衡。8 間續住清 ≠ 8 間退房清
  3. 優先序前置 —— 有早 check-in 需求或 VIP 的房間排前面
  4. 技能 / 區域限制 —— 例如套房只有特定人員處理
  5. 推播給每人：「今天 8 間，從 3F 開始」

設計決定派工結果主管可覆寫且不會被系統改回去。誰昨天比較累、誰跟誰不能排一起、誰資歷帶新人——這些隱性知識系統拿不到。

現場清潔回報房務人員
  1. 打開 LINE → 我的今日 → 一頁清單。大字、依樓層分組、戴手套可點
  2. 進 305 → 按 [開始] → 寫入 started_at = T1，房況轉 Cleaning
  3. 清潔中發現異常 → 拍照 → 一鍵開工務單（同一個 task 引擎，dept=maintenance）
  4. 掃完 → 按 [完成] → 寫入 done_at = T2，房況轉 Vacant Clean
  5. 若旅館有查房制度 → 轉「待查」，主管查房通過才 Inspected（可售）

設計決定離線優先。按鈕點擊先寫 localStorage 加樂觀 UI，背景重試上傳。電梯、樓梯間、地下室沒訊號也要能按，出來自動同步。這一項做不好，回報率永遠上不了 85%——而那正是 E1 的過關門檻。

04 — 缺人

請假要不要自動派給下一位

要自動偵測、自動試算、自動退回池——但不要自動決定服務標準怎麼降。先看為什麼「池」是這一切的前提。

缺人有三種發生時點，處理方式不同。混成一種是錯的。

情境 A · 開工前

前一晚或當天早上請假

主管在排班上標「今日請假」→ 系統重跑派工並推播更新。若總預估工時超過可用人時，明確報「缺 3.5 人時」並給三個選項：呼叫候補（推播給候補名單搶單）、降級部分任務（續住清改為只換布巾補備品）、延後今日無入住的房間。按哪一個由主管決定。

情境 B · 開工後

中途離場（身體不適、臨時有事）

該員按「無法繼續」→ 名下未開始的任務直接退回部門池。已開始未完成的要特別處理：狀態改「中斷」、記錄 checklist 進度到哪、推播主管決定重派，並優先給同樓層的人。不要靜靜地重派已開始的房間——下一個人不知道前面做到哪，會重做或漏做。

情境 C · 兜底

沒人請假，但房間就是沒人碰

最常見也最容易被忽略的情境：漏派、忘記、以為別人做了。SLA 逾時升級是唯一的兜底——任務超過預估時間 × 1.5 仍在「待接」，自動升級給主管。這條規則同時覆蓋了請假、漏派、和人為疏失，是三個情境裡最該先做的一個。

不要做全自動重派

技術上很容易——偵測到請假，把任務平均灑給剩下的人，推播出去。然後你會在第一週被關掉。

因為房務排班牽涉的是隱性知識：誰昨天做了 12 間今天該輕一點、誰的體力適合套房、誰在帶新人不能單獨排、誰跟誰不能同層。系統拿不到這些，主管拿得到。

正確的分工是：系統負責偵測、試算、退回池、和逾時升級；人負責決定服務標準怎麼降。把試算做到位（缺幾人時、哪些可延後、延後的代價是什麼），主管的決策就快得多——這才是產品的價值，不是替他決定。

05 — 其他 Use Case

同一個引擎，其他四條路徑

這些不是額外模組，是同一張 schema 換 preset。列出來是為了驗證 schema 夠通用。

UC-5房客要求早 check-in櫃檯 → 房務
  1. 櫃檯在房況板看到 305 是 Vacant Dirty、預估 35 分鐘
  2. 按「加急」→ priority=urgent，該任務跳到負責人清單最前面並推播
  3. 完成後房況即時轉綠，櫃檯不用打電話問「305 好了沒」

這是收入不是成本知道哪間現在可以給，就能賣早 check-in 加價。若 E2 找不到 10% 可壓縮工時，這條路徑就是計畫裡的備用賣點——從「省成本」換成「加收入」。

UC-6清潔中發現設備故障房務 → 工務 → 櫃檯
  1. 房務拍照 → 一鍵開工務單（dept=maintenance，同一個引擎）
  2. 系統檢查該房今日有無入住 → 有客則標「須在 15:00 前修好」並提高優先序
  3. 工務回報無法當日修復 → 櫃檯收到「305 不可售」，房況鎖定，回寫 PMS

設計決定「不可售」必須能回寫訂房系統，否則櫃檯會把壞掉的房間賣出去。這是唯一必須雙向寫入 PMS 的路徑——其他都可以單向讀。

UC-7外包清潔團隊派工與對帳外包
  1. 外包團隊成員綁定受限視圖：只看今日任務與完成回報，看不到房客資料與其他部門
  2. 清潔完成同樣按 [開始] / [完成] → 一樣產生 T1 / T2
  3. 月結自動產出：清潔 X 間 × 單價 = 金額，附實際工時分布

這是最痛的地方外包對帳現在全靠紙本點數量吵架。有時間戳就吵不起來，而且雙方都能拿實際工時來談合理單價。Flexkeeping 的 maintenance 模組有協力商協調功能，但在台灣中小型市場沒人做。

UC-8櫃檯交班櫃檯
  1. 交班時系統自動產生交班單：未完成 task、待處理房客需求、不可售房間、今日特殊事項
  2. 接班人簽收 → 未完成 task 的責任轉移到新班別的池

為什麼值得做小旅館交班全靠口頭和紙條，這是漏球的主要來源。而且交班單是第一版就能展示價值、開發成本又極低的功能——它只是把已有的 task 狀態換個視圖呈現。

UC-9老闆的每日三行老闆
  1. 每日 20:00 LINE 推播：今日入住率 / ADR · 今日逾時 task 數 · 本月房務工時成本 vs 上月
  2. 週報一張圖：預估工時 vs 實際工時的落差趨勢

設計決定不要做 BI。老闆不會登入 dashboard，但每天會看 LINE。三行數字裡至少要有一個是錢，否則他不知道這個系統在幫他做什麼。

這份文件描述的是 v1 的目標流程，不是已驗證的事實。
其中「房務願意每間房回報兩次」（假設 V2 / U1）與「離線回報可靠」（F2）尚未驗證—— 它們是驗證計畫裡 E1 與 E5 的測試對象，門檻是連續 7 天回報率 ≥ 85%。 在 E1 跑完之前，不建議依這份流程開始開發。
