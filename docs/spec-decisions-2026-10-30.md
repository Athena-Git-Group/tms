## 一、已明確拍板的 12 項決策

| # | 決策項目 | 採用方案 | 對 spec 的影響 |
|---|---------|---------|--------------|
| D1 | 查房策略（X5） | **採原型完整版**：inspection 三值 passed / waived / failed；租戶「續住清免查房」開關；**開工當下鎖定查房策略**（之後改設定不影響進行中的單）；免查單仍可被主管抽查退回 | 修正狀態機圖與「打掃一律查房」敘述；PMS 回寫條件改依 inspection 值；報表口徑區分 passed / waived |
| D2 | 延後／中斷語意（Y1） | **只做員工本人版**：員工對待開始的單可 `snooze`（附原因，單留本人名下、可直接開工）、對進行中的單可 `pause`（附原因，計時停、SOP 勾記保留、可自行 `resume`）。主管端不另設 defer／interrupt，主管要處理時一律走既有的**改派**或**回池** | 刪除／改寫 spec 既有的 `deferred`（主管對空房巡）與 `interrupted`（請假連鎖）轉移；新增員工端 snooze／pause／resume 端點；請假連鎖改為走 requeue 回池 |
| D3 | 工務單資料模型（X1） | **Task 的子型，同表擴充**：`tasks` 表加 `type=maintenance` 與審核相關欄位，共用狀態機、待接池、認領、通知、統計 | 狀態機加修繕專屬狀態（pending／approved／rejected、完修→驗收兩段）；不另建 work_orders 表 |
| D4 | 一次一單限制（X6） | **強制限制**：任務引擎加 per-assignee 守衛，同一員工 `doing` 狀態同時最多一張。開始／恢復第二張時回 409 並帶「前往該單」所需的 taskId | 任務引擎守衛章節新增此約束；工時統計口徑據此定義 |
| D5 | 急件機制（X2） | **完整做**：伺服器端判定 R1 安全類（門鎖／漏水／漏電／冒煙…）、R2 影響今日入住（VIP 6h、一般 3h）、R3 影響在住住客；三條規則皆進規則引擎且租戶可調。急件 **bypass 主管審核**直接進工務待接池並通知主管；主管可降級為一般件（**必附原因**，留痕供檢討）；急件升級門檻另設 **3 分／8 分** | 派工模組加 `priority` 欄位與急件判定規則；升級鏈設定按優先級分組；新增降級事件 |
| D6 | 照片／附件（X3） | **完整原型版，浮水印在 client**：App 端壓縮（長邊 1600px／JPEG 0.7）與浮水印「房號·拍攝時間」；逐張上傳進度與重試，**全部成功才算送出**；相簿備援；一次性隱私提醒；相機權限被拒引導；離線先存手機、恢復連線自動補傳 | 新增「附件」章節：上傳 API、物件儲存、壓縮與浮水印規格、離線補傳、與 outbox 的關係。套用於報修／完修／開工單／遺失物拾獲四處（皆必填 1–3 張） |
| D7 | 公共區域任務（X8） | **任務加 location 欄位**：`location` 為「房號」或「區域」二擇一，區域清單由租戶後台設定 | 任務模型加 location；所有按房號的查詢與 PMS 回寫須處理 location 非房號的情況；租戶設定加區域清單；只有公共區域／保養的單可「放回待認領」，客房報修由接手者負責到底 |
| D8 | 櫃檯共用 iPad 身分模型（X13） | **裝置登入＋PIN 切換**：iPad 以裝置帳號登入維持連線，操作者用短 PIN 快速切換；所有派單／代開單／歸還／當場回答的 **actor 記實際操作者** | 身分權限模組新增共用裝置會話模型；明定 actor 歸屬規則；櫃檯個人統計（X14）據此才有意義 |
| D9 | 通知模組（X10） | **全做，含 Live Activity**：App 內通知中心（今天／更早、未讀、全部已讀、深連結、目標不存在時提示）；個人推播偏好，**必要通知不可關**（急件、指派／改派、查房退回、工務核准）；「只在上班時間通知」依班表閘門（急件也擋但保留紀錄）；新需求推播只送負責樓層（主管後台設定）；回饋分流三原則（擋操作→Alert／成功→不跳通知／背景→系統推播）；**Live Activity 動態島即時計時**（最多更新 8 小時、結束後鎖定畫面再留 4 小時） | 新增通知模組章節：notifications 實體與已讀、個人偏好（含不可關清單）、班表閘門、樓層路由。Live Activity 需後端推送更新事件；Flutter 需 iOS 原生 extension（唯一需原生開發的部分） |
| D10 | 介面多語系（X11） | **五語全做**：繁中／簡中／英／日／越；語言跟著操作者走（共用 iPad 切人即切語言）；**只翻譯介面字串**，住客與同事輸入的內容一律保留原文；簡中以繁中字元轉換＋用語替換產生 | 員工偏好設定加語言欄位（需後端儲存，因跟著操作者而非裝置）；明定「輸入內容不翻譯」原則 |
| D11 | 交辦（Y8） | **做成獨立 memo 實體**：memos 表＋已讀事件，可掛在任務或房間；統一承載主管交代／接手進度／同房交班項／櫃檯備註；開工前升級為「開工前請先看」引言卡，按知道了／開始即已讀；收進「這間房的資訊」列表（未讀藍點） | 新增 memo 實體與已讀事件；「這間房的資訊」聚合頁有資料來源；保留 requeue 的 progressNote 作為 memo 的一種來源 |
| D12 | v1 範圍 | **住客 Web 與老闆儀表板都留在 v1**：住客掃碼是整個系統的需求入口，老闆數字是賣點 | spec 既有的住客端（需求 1）與老闆儀表板（需求 7）章節全數保留；這兩塊需補設計稿，前端工作量須計入 |

## 二、未逐項詢問、一律採原型版的項目

以下項目原型敘述已明確且與 spec 無方向性衝突，**一律以原型為準**補進 spec：

| # | 項目 | 要補的內容 |
|---|------|-----------|
| X4 | 完修回報與驗收 | 完修照片必填＋結果三選一：已修好／暫時處理（自動建追蹤單指派給自己，通知櫃檯與主管）／無法修復（房間停用 OOO、回寫 PMS、通知櫃檯與主管）。完修後等主管驗收，驗收通過才結案（記驗收人／時間） |
| X7 | 櫃檯代開單 | 工具列常駐入口；房號驗證＋住客卡；品項沿用住客選單（綁部門、數量上限）；依部門自動拆成多張單；自由文字須指定部門；同房已有未結案同品項時**黃色警告但不阻擋**；空房照常可開單；來源記「櫃檯代開（姓名）」 |
| X9 | 工務單與打掃任務關聯 | 房務從任務頁報修（不中斷）或經「中斷→需要工務協助」轉開單並記錄工單號；任務頁「這間房的資訊」聚合交辦與工務單；工務端進度（已接／維修中／暫停原因／已修好／無法修復）即時同步到房務任務狀態列 |
| X12 | App 內文字大小 | 七段滑桿、預設「跟隨 iPhone 設定」、只套用本 App、即時預覽。偏好存裝置端即可 |
| X14 | 櫃檯今日成果統計 | 今天經手 N 單圓環（目標 30），細分派單／代開單／當場回答。由 task_events 依 actor 投影 |
| Y2 | 保養巡檢排程 | 頻率語彙擴充（每日／每兩週／每月…）；當天到期**自動派給值班工務**（不進待接池、不經審核）；開始保養即生成工務單，完修回寫保養完成時間；做不完可放回池；未來保養預告清單 |
| Y3 | 遺失物完整流程 | 手機端（房務／工務）拾獲登記（照片必填＋浮水印、地點 Chips 由主管後台設定、客房須填房號）；四態狀態機 待交櫃檯→櫃檯保管中→已認領／逾期已處理；歸還需「已核對身分」開關必開、記領取人與聯絡方式；自動編號 L-MMDD-NN |
| Y4 | AI 問答「查一下」約束 | 只能點情境建議問題（不開放自由輸入）；僅依 sop_items／room_memory 回答並附出處卡與資料新鮮度；查不到明說並轉「問主管」（回覆用推播）；回答可評有幫助／沒幫助（負評轉 SOP 管理者）；稽核記錄含模型版本；住客偏好回答不露身分 |
| Y5 | 離線操作白名單 | **離線可做**：進行中的單勾 SOP、完成／完修、報修先存手機（恢復連線自動同步、照片補傳）。**離線一律擋下**：開始新單、認領、延後、開新工務單、開始保養。離線完成需顯示「已先記錄在手機」標示 |
| Y6 | 進行中超時提醒 | 按開始起算，超過預估分鐘即標示超時（變色＋膠囊＋Live Activity 同步），**只提醒不擋操作**。因 D9 決定做 Live Activity，需後端推送超時事件而非純前端計算 |
| Y7 | triage 拆單建議 | 櫃檯判讀動作由三選一擴充為四選一，加入「拆單」（一張變多張、各帶部門）；AI 在一單含多件事時主動建議拆單 |
| Y9 | 工務類別預估工時 | tenant_config 的工作量規則表擴充修繕類別維度（冷氣 40 分、水電 30 分…，主管後台可調） |

## 三、未決、留作開放問題

- 急件判定 R2 的「影響今日入住」門檻（VIP 6h／一般 3h）是否需按租戶分別設定，或全平台固定。
- Live Activity 在 Android 端的對應方案（Android 無等價 API，可能退回常駐通知）。
- 共用 iPad 的 PIN 強度與鎖定policy（連錯幾次鎖多久）。
- 附件物件儲存的供應商與保存期限（照片量會隨時間線性成長）。
