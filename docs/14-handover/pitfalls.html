TMS 交接手冊 / 坑與待查

交接 · 坑與待查

會咬人的地方，與還沒確認的事

前五節是已知的坑，每一條都真的發生過，或是讀程式碼時確認過的事實。最後一節是還沒確認的事，請不要當成已知事實。

約 7 分鐘

裝環境時會卡在哪？

重點

最常見的兩個：JDK 不是 25，以及後端測試忘了帶 -DargLine="-Dapi.version=1.44"。啟動後端時永遠帶 TMS_DB_URL。

  • JDK 版本：shell 預設是 17，所有 Java 專案都要 25。run-feature.sh 找不到 JDK 25 會以結束碼 2 離開；手動環境的 scripts/manual-env/env.sh:25 把 JDK 路徑寫死成原機器的使用者目錄，換機器要設 MANUAL_JAVA。
  • OrbStack＋Testcontainers：OrbStack 的 Docker 29 拒絕 API 1.40 以下，而 docker-java 沒指定時退回 1.32，會看到「client version 1.32 is too old」。試過 DOCKER_HOST、DOCKER_API_VERSION、升級 Testcontainers 都沒用，唯一解法是 -DargLine="-Dapi.version=1.44"，把值傳進 surefire 分出來的 JVM（specs/plans/003-manager-sign-off-queues/implement-notes.md:109-114）。沒有寫進任何設定檔，每次都要帶。
  • Flyway 預設埠與應用預設埠不同：application.properties:11 的 Flyway 預設連 5432、:3 的應用預設連 5433。沒設 TMS_DB_URL 時 Flyway 會連到 5432——在原機器上那是別的 Postgres。
  • 電腦睡眠會殺掉長時間執行：App 全量驗收要 60–90 分鐘，開跑前掛 caffeinate -dimsu -t 28800。
  • macOS 內建 bash 3.2 會把變數名後面緊接的全形標點吃進變數名，腳本訊息一律寫成 ${var}。新寫腳本時照做。

跑測試時會卡在哪？

重點

分三類：誰跟誰不能同時跑、漏一個參數就整輪紅、simulator 的怪癖。各條線的詳細坑在 BDD 測試。

誰跟誰不能同時跑

  • Appium 4723 與 simulator 全機唯一：兩個 App 驗收同時跑會搶同一個 session，整輪作廢（發生過，0 個測試跑完）。開跑前先 lsof -i:4723 與 ps aux | grep RunModuleFeatureTest。
  • App 驗收與 Web 驗收不能同時連 8080／5433：兩邊每個場景都清空同一個資料庫。
  • 多個工作目錄同時 install bdd-support 會互相覆蓋 ~/.m2 裡同一份 SNAPSHOT；解法見 BDD 測試。

漏一個參數就整輪紅

  • bdd-support 改了要重新 install；直接下 mvn 時更要記得。
  • -Dcucumber.features 會讓場景跑兩遍：有這個屬性時 Cucumber 引擎忽略入口寫死的目錄，surefire 又會再發現同一批 feature 一次。三個專案都已設 excludeJUnit5Engines=cucumber，run-module.sh 也會另外帶。
  • App 一定要用 TEST_BACKDOOR=true 編譯，否則每個場景都「等測試後門就緒逾時」。
  • App 驗收的後端要帶 test-support 設定檔（SPRING_PROFILES_ACTIVE=test-support），否則沒有 /api/v1/test/clock，run-module.sh／run-all.sh 第一步就停。Web 驗收的腳本自己起後端時會帶；沿用的 8080 後端沒帶會報錯，先 run-feature.sh --stop。

simulator 的怪癖

  • 剛開機時 simctl install 會靜默失敗，env.sh 已加重裝驗證。另外要接硬體鍵盤，否則螢幕鍵盤會蓋住密碼欄。
  • headless 下 simctl privacy grant notifications 會失敗，系統權限彈窗靠 Appium 的 setAutoAcceptAlerts(true) 自動按掉。

哪些操作會不小心毀掉別人的資料？

重點

測試會清資料庫。手動操作一律用 8083／tms_manual，測試永遠不要指到它。

  • 測試會清資料庫：backend.db.url 千萬不要指到 tms_manual。
  • Web 驗收的後端只能是 8080（vite 代理寫死）；5300 是手動環境、5199 是驗收，不要混用。
  • 推播 consumer group 寫死：8083 與 8080 互相起停會讓對方推播停頓幾秒。

改後端程式碼與遷移時要小心什麼？

重點

src/main 是反編譯還原的，原本的註解都沒了；既有 Flyway 遷移檔連註解都不能動；測試端點不設權限，部署時絕不能帶 test-support 設定檔。

  • src/main 是從編譯產物反編譯還原的（tms/pom.xml:15 的 description 寫著 "reconstructed from compiled artifacts"）：原本的 Javadoc 與註解都沒了，風格也像反編譯產物（大量 this.、多餘的型別強轉）。src/test 是重寫過的。
  • 既有 Flyway 遷移檔不能動，包含註解。整理反編譯程式碼的註解時，遷移檔要排除在外。
  • 測試端點 /api/v1/test/**（含撥時鐘的 /api/v1/test/clock）不驗身分（config/TestSupportConfig.java:31-34 一律 permitAll）。它們只在啟動時帶 test-support 設定檔才存在（:18 的 @Profile），所以對外部署時絕不能帶這個設定檔。
  • JWT 密鑰與 tms_app 密碼的預設值都是開發用：正式環境要設 TMS_JWT_SECRET，並 ALTER ROLE tms_app 改密碼（V1__schema.sql:387 的註解）。
  • 舊整合測試還在保護舊行為：tms/src/test/resources/features/*.feature 不是 truth，但在全套裡跑。改行為時要一起看。
  • 即時更新不補送，靠重讀對回來：後端重啟期間的 Kafka 事件不會補讀，網頁是靠重連時必收的 resync 整份重讀補回。另外待送匣裡某張單只要有一筆重試用完被標 failed，這張單之後的事件全部停送，要人工到 outbox 查 status = 'failed' 處理。詳見 Kafka 掛掉或後端重啟時會怎樣。
  • 註解規範：改任何註解前先讀 docs/14-handover/code-comments.md；有一批禁用詞（守衛、空窗、投影）。

員工 App 有哪些還沒補的洞？

重點

上線前最優先：Android 正式版缺網路權限。其次是 Android 整條路沒驗證過，App 驗收目前只支援 iOS。

  • Android 正式版缺網路權限：android/app/src/main/AndroidManifest.xml 只宣告了 POST_NOTIFICATIONS；INTERNET 只在 src/debug 與 src/profile 裡，release APK 會連不上網。Android 也沒有允許 http 明碼的設定。（只讀檔確認，尚未實際建置驗證。）
  • Android 整條路都沒驗證過：沒有 google-services.json，App 驗收的 AppiumWorld.start() 遇到 Android 直接丟 UnsupportedOperationException。
  • 預設 simulator 不存在：app/bdd/lib/env.sh 與 AppiumWorld.java:92 寫死的 79F32D5C-7A71-47D6-AA8D-8142E68CFF48 在原機器的 simctl list 裡找不到，一律用 UDID= 指定（例如 iPhone 18 Pro＝B07951C2-DF41-4AF6-9C98-0DFC7413ED8C）。
  • App 連哪個後端是編譯期決定的，不帶 API_BASE_URL 就連 8080（資料會被測試清掉）。
  • token 只在記憶體、沒有逾時、沒有統一 401 處理：token 過期後的行為要自己留意。
  • iOS 沒有 App Transport Security 例外：實機連 http 區網 IP 會被擋。
  • 程式裡找不到 TODO：註解已清理過，待辦要看各輪的 specs/plans/*/tasks.md 與 implement-notes.md。

接手後還有哪些事要先查？

重點

17 件盤點時沒能從程式碼確認、或要實際執行才知道的事，分四組。先處理第一組：測試現在綠不綠。
