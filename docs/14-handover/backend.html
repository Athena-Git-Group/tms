程式碼怎麼分套件？狀態變化怎麼變成推播，照片又存在哪？

重點

業務邏輯集中在 service/。任務狀態一變，事件和資料在同一個交易寫進資料庫，再經 Kafka 與 SSE 提醒網頁「這張單變了」。

這條路只負責提醒；畫面上的真相永遠從資料庫重讀，所以掉一兩則訊息、後端重啟或 Kafka 暫停，畫面都會在重連或重讀後對回來。

工務單照片的本體放在雲端儲存，資料庫只記它叫什麼名字；App 與櫃檯網頁一律經後端讀照片，後端先確認是同一家飯店的員工。

任務狀態一變，網頁畫面怎麼跟著動？

最直覺的做法是網頁每幾秒問一次後端。櫃檯好幾台電腦一起開著看板時，大部分時間都在空問，而且畫面還是慢幾秒。

另一個極端是把後端推來的訊息直接當資料改畫面。只要掉一則或順序亂了，畫面就一直錯下去，沒有人會發現。

現在的做法夾在中間：後端一有變動就推一則訊號給網頁，給櫃檯的訊號順手附上那張卡片的最新樣子；網頁一發現對不上，就向後端重讀整份看板。代價是前後端都要多寫「什麼時候不信訊號」的判斷，換來的是訊息掉了只會慢、不會錯。

事件怎麼從資料庫送進 Kafka？

待送匣（outbox）是資料庫裡的一張表，作用像寄信前先放進的待寄籃：要送出去的事件先寫在這裡，再由專人投遞。

TaskEngine 的每個狀態方法都包在一個交易裡，寫 task_events 的同時也寫一筆 outbox。兩者一起成功或一起失敗，所以不會「資料改了，事件沒記」，也不會「事件送了，資料卻回復原狀」。

投遞的是 OutboxRelay，一條背景執行緒。交易一提交它就被叫醒；沒人叫的話最多等 2 秒自己巡一次。每一輪逐家飯店撈出待送的紀錄，按單號分組依序送：同一張單前一筆沒送成功，後面的先不送，所以同一張單的事件不會亂序。

送上 Kafka 時，訊息的 key 就是 task:<單號>。Kafka 的一個主題會切成幾條平行的隊伍，叫分區；同一個 key 一定進同一條分區，所以讀的那端看到的也是原本的順序。

送失敗會等一下再試，間隔每次加倍（1 秒、2 秒、4 秒…）。8 次都失敗、再等完最後一次間隔（128 秒）就標為 failed，而且這張單之後的事件全部停送，要人工處理。推播用另一把 key（push:task:<單號>），推播卡住不會連帶擋住看板訊號。

多台後端都會跑 relay。每台送之前先在那筆紀錄上搶 60 秒的租約，租約內別台不碰，所以同一筆不會被兩台同時送。

為什麼每台後端都要收到全部訊息？

網頁和後端之間靠 SSE（伺服器推送事件）：網頁對後端開一條不關的 HTTP 連線，後端有事就往裡面寫一段，網頁不必來問。這條連線只會掛在某一台後端上。

於是問題來了：房務員的開工請求打到後端 A，櫃檯的看板卻連在後端 B。B 也必須知道這件事，才推得出去。

Kafka 用消費者群組（consumer group）分工：同一組的成員分著讀，一則訊息只交給組裡其中一個；不同組則各自讀到完整的一份。

壞做法所有後端用同一個組名

每則事件只到其中一台。連在其他台上的網頁永遠收不到，而且收不收得到看運氣。

現在的做法每台啟動時取一個隨機組名

TaskEventsSseConsumer 的組名是 sse-<隨機 UUID>，每台自成一組，所以每台都收到全部，再各自挑出自己身上的連線推。啟動時 log 會印出實際組名。

權衡每多一台後端，每則事件就多一次查資料庫；目前規模可以接受。

推播剛好相反。PushDeliveryConsumer 讀 tms.push，組名預設是 tms-push-sender（設定 tms.push.consumer.group 可改，手動環境就加了 manual. 前綴），同一套環境的後端共用一組，所以一則推播只會有一台送，手機不會響兩次。

隨機組名還有一個後果。群組在每條分區上讀到第幾則，記在一個叫 offset 的書籤裡；新組沒有書籤，設定又是「從最新位置開始讀」（auto-offset-reset=latest）。所以後端停機期間的事件，重啟後不會補讀，要靠下面說的 resync 補回來。

後端收到事件後做了什麼、怎麼決定推給誰？

每台後端的 SSE 消費者對每則事件依序做這幾件事：

  1. 量落後：事件的時間比現在晚超過 10 秒，就進入降級狀態；跟上了就離開。
  2. 檢查欄位：少了飯店、單號、步數或事件種類就略過。
  3. 去重：記住每張單已推過的最大步數（最多記 1 萬張單），重複或更舊的丟掉。
  4. 查資料庫補路由資料：這張單現在的部門、負責人、訂房；撤回待派單時，另記原本的部門。
  5. 組看板卡片：這家飯店有櫃檯連線時才組，所有櫃檯連線共用同一張。
  6. 逐條連線問「要不要」，要的就送；另外送一則房態給 PMS 對接用的整合串流。

任何一步出錯只記 log、不重試。掉這一則可以接受，因為網頁之後總會重讀。

每台後端有一份連線註冊表，記著目前掛在這台身上的所有 /staff/stream 連線。決定送不送的規則只有三條：

  • 不同飯店一律不送。
  • 櫃檯畫面的角色（frontdesk、manager、duty_manager）收整家飯店，而且只有他們拿得到看板卡片，因為卡片上有住客姓名與 VIP 標記。
  • 其他角色只收自己部門的單或指派給自己的單；單被撤回待派單時，原部門也會收到。

連線本身是 GET /staff/stream，只認 Authorization: Bearer 標頭裡的登入憑證，允許 housekeeping、engineering、manager、frontdesk、duty_manager。後端最多讓一條連線開 30 分鐘就收掉，網頁會自己重連；連線斷掉、逾時或送不出去，都會立刻從註冊表移除。

網頁收到後怎麼更新看板？

網頁沒有用瀏覽器內建的 EventSource，因為它不能帶 Authorization 標頭。改用 fetch 帶著標頭連上去，自己一段段解析串流；登入憑證一換就重連。

每次連上，後端都先送 init，接著送 resync 叫網頁整份重讀一次。所以每次重連都等於重新對帳一次，斷線期間漏掉什麼都會補上。之後收到的每則 task 訊號：

  • 帶著卡片、步數也接得上：只換掉這一張卡，開著的詳情重抓。
  • 沒帶卡片、步數跳號、或營業日不同：整份看板重讀。
  • 同一時間來了好幾個重讀要求：合併成一次。

後端每 15 秒送一次心跳。網頁 35 秒什麼都沒收到，就自己斷開重連；重連第一次等 1 秒，之後每 5 秒試一次。

收到 degraded（降級，意思是後端自己知道訊號可能不準），或心跳裡寫著 degraded: true，網頁就不再信訊號：顯示連線警示，每 4 秒自己重抓整份看板。等到 recovered，再整份重讀一次並回到只靠訊號。

Kafka 掛掉或後端重啟時會怎樣？

原則跟前面一樣：訊息掉了只會慢、不會錯，因為網頁最後都會從資料庫重讀。差別在於「多久之後」以及「要不要有人出手」。

Kafka 掛掉時，寫入照常，事件都還在 outbox 裡等。relay 會間隔加倍地重試，Kafka 回來後依序補送。斷線約 5 分鐘內恢復不會出事，最多晚兩分鐘補送。但依程式碼推算，停超過約 5 到 6 分鐘，斷線當下正在排隊的每張單，最前面那一筆會重試用完、被標 failed，這張單之後就停送等人工；斷線期間才新增的單，要自己撐滿約 5 到 6 分鐘才會被標。

網頁這端，讀 Kafka 的元件若發出「停止」或「沒回應」的通知，後端會進入降級，網頁改成定時重讀，恢復時再整份重讀。不過 Kafka 掛掉時框架是否一定發出這些通知，屬於框架行為，程式碼無法保證；沒發的話，網頁只是暫時收不到訊號，畫面停在舊的狀態。

後端重啟時，掛在那台上的網頁會斷線，1 秒後重連。連上後必定收到 resync 並整份重讀，停機期間漏掉的變動就這樣補回來。消費者本身不補讀那段期間的事件。

工務單照片存在哪？本機和正式環境怎麼用同一套程式？

照片一張幾百 KB，不適合塞進資料庫：備份會跟著照片一起變胖，每次查工務單也不該把照片一起搬出來。所以照片本體放在外面，資料庫的 repair_photos 表只在 storage_ref 欄記它在儲存空間裡的名字。難的是「外面」在本機和正式環境不一樣。

壞做法本機存電腦資料夾，正式環境另寫一套存雲端，用設定切換

本機跑的永遠是資料夾那一套，雲端那一套要到上線才第一次真的被執行；權限、物件名稱、連線逾時的錯誤都留到正式環境才冒出來。

現在的做法只寫一套，用 Google 官方程式庫；本機接模擬服務

PhotoStorage 只有「存」與「讀」兩個方法，唯一的實作 GcsPhotoStorage 用 Google 官方的雲端儲存程式庫。本機與自動化測試把連線位址指向 fake-gcs-server，它說的是跟雲端儲存一樣的語言，所以同一段程式在本機寫進模擬服務、在正式環境寫進真的雲端儲存。整個後端只有 StorageConfig 一處看「有沒有模擬服務位址」（storage/StorageConfig.java:40-49）：有位址就用無憑證模式連過去，並在啟動時建立儲存空間，建不起來就讓後端啟動失敗（:50-57）；位址留空就用伺服器本身的雲端身分連真的雲端儲存。連線、讀取與重試總時限都是 10 秒。

每張照片的名字是 repair-photos/{飯店編號}/{照片編號}.jpg（repair/RepairService.java:168-170）。照片編號在建立照片時就產生，同一張照片重傳會寫到同一個名字、整份蓋掉，重送幾次結果都一樣；名字不帶雲端廠商的網址，換廠商時資料庫不用改。

權衡本機多跑一個容器，而且它沒起來後端就起不來。換來的是每一次本機測試都跑過正式環境會跑的那段程式。

讀照片也有一個選擇。一種做法是後端發一個有時效的下載網址，讓手機直接向雲端儲存拿照片，後端不用搬流量；但這要讓後端握有能簽網址的憑證，還得決定網址多久失效、外流了能不能撤回，而模擬服務對這種網址的支援也跟真的雲端儲存不同。現在的做法是手機與網頁都向後端要照片，後端確認身分後從雲端儲存讀出來轉送。照片已壓過、一張工務單最多幾張，多搬的流量不大；真的遇到流量問題再改成臨時網址，App 與網頁都只要換掉讀照片的那一個地方。

櫃檯網頁的登入憑證不能放進圖片網址（網址會留在瀏覽器紀錄與各種伺服器紀錄裡），所以網頁跟呼叫其他端點一樣帶 Authorization 標頭去讀，拿到內容後轉成只有這個分頁看得到的暫時網址給圖片用，面板關掉就釋放（app/web/src/api/repair-photos.ts、features/detail/RepairPhotoStrip.tsx）。工務單詳情面板分「報修照片」「完修照片」兩排，點縮圖看大圖；住客網頁沒有照片功能。

照片上傳、讀取、附到工務單上，各檢查什麼？

一張照片走三步：POST /api/v1/repair-photos 帶用途（report 或 completion）與帶時區的拍攝時間，建立一筆 pending（還沒上傳）的照片並拿回編號；PUT /api/v1/repair-photos/{編號}/content 把 JPEG 原樣當 body 送上來（Content-Type: image/jpeg），照片變成 uploaded；最後開單、補照片或完修時帶著照片編號，把它附到工務單上。

  • 上傳（RepairPhotoContent.java、RepairService.java:117-144）：超過 5 MB 回 413，內容是空的回 422，標頭不是 image/jpeg 或內容開頭不是 JPEG 的記號回 415；只有建立照片的員工能上傳（否則 403），照片附上工務單之後不能再換內容（409 photo_already_attached）。附上之前可以重傳，以最後一次為準。
  • 讀取（RepairController.java:98-106）：房務、工務、主管、櫃檯、值班主管都讀得到同一家飯店已上傳的照片，老闆帳號不行（SecurityConfig.java:76-77）。別家飯店的照片、還沒上傳的、儲存空間裡找不到的，一律回 404。已附上工務單的照片回應帶 Cache-Control: private, max-age=86400, immutable，還沒附上的帶 private, no-cache。
  • 附上工務單（RepairService.java:535-561 的 requireAttachablePhotos，開單、補照片、完修三處共用）：每張都要存在而且已上傳（否則 422 photo_not_uploaded），用途要對（422 photo_purpose_mismatch），不能已附在別張單上（409 photo_already_attached），一次最多 3 張（422 photo_limit）。完修結果是「不需處理」時不必附照片，但帶了照樣檢查。
  • 同時附同一張照片：檢查時就把照片的資料列鎖住，兩個請求排隊，只有一個成功、另一個 409。補照片先鎖照片再鎖工務單，跟完修同一個順序，兩個請求不會互等卡死。

權衡上傳時「寫進雲端儲存」與「把照片標成已上傳」放在同一個資料庫交易裡：雲端寫失敗，整筆取消、照片維持未上傳；寫完雲端、還沒標記就當機，重傳是同名覆寫，結果一樣。代價是雲端儲存變慢時，這個請求會佔著一條資料庫連線，最多等 10 秒的時限。

多家飯店的資料是怎麼隔開的？

重點

一家飯店在系統裡叫一個「租戶」。隔離做在資料庫層：每條連線綁一個租戶，資料表規則讓它只看得到自己那家的列，就算程式忘了加條件也查不到別家。新表若沒有 GRANT 給 tms_app，應用會寫不進去。

用的是 Postgres 的 RLS（Row Level Security，列層級安全）：在資料表上設一條規則，讓每條連線只看得到 tenant_id 等於某個連線變數的列。

  1. 資料表規則：V1__schema.sql:414-437 對 16 張表開啟 RLS，條件是 tenant_id = current_setting('app.tenant_id', true)::bigint；跨表外鍵用 (tenant_id, id) 複合鍵。
  2. 每條連線綁租戶：config/TenantAwareDataSource.java:23-66 取得連線時 SET app.tenant_id，沒有租戶就設 '0'（什麼都看不到），歸還前再重設成 '0'。
  3. 租戶從哪來：common/TenantContext.java（每個執行緒一份）。filter/BearerTokenAuthFilter.java:56-110 驗完 JWT 後設定它，請求結束清掉。
  4. 背景工作（沒有請求）：TenantScopedExecutor.callAsTenant(tenantId, work) 開交易並設定租戶，排程、relay、消費者都逐租戶執行。
  5. 對外用飯店代碼 tenants.code（例如 demo-hotel），內部流水號不外露。櫃檯網址是 /{飯店代碼}/login，登入請求帶 hotelCode；登入前可用 GET /api/v1/public/hotels/{hotelCode} 查飯店名稱。

資料庫有兩個帳號：Flyway 用管理帳號 tms 建表；應用執行時用最小權限的 tms_app，由 V1__schema.sql:383-391 自己建立並授權。

員工、住客、PMS 各自怎麼登入、怎麼授權？

重點

員工換 12 小時的 JWT，住客掃房內 QR 換 session，PMS（飯店的訂房管理系統）用 API key。要特別注意：員工 App 登入不帶飯店代碼，後端會跨飯店找帳號。

  • 員工登入怎麼決定飯店（service/StaffAccountLoginService.java:58-80）：有 hotelCode 就只在那家驗證；沒帶時先找出所有有這個員工編號的飯店，只有一家就用那家，多家就取第一家密碼相符的。所以不同飯店員工編號與密碼都相同時，會登進別家——bdd-support 的預設帳號因此刻意不重複編號（BackendChannel.java:70）。
  • 員工 token：POST /api/v1/staff-accounts/login 換 HS256 JWT，內含租戶、員工、角色、部門與密碼指紋（JwtService.java:49-56）。filter 每次請求還會確認帳號存在、啟用、密碼指紋仍相符（改密碼後舊 token 立刻失效）、是否必須先改密碼（BearerTokenAuthFilter.java:77-100）。登入失敗多次會鎖定。
  • 住客：掃房內 QR → POST /guest/scan（公開、有 IP 限流）換住客 session token，之後帶 Authorization: Bearer 或 X-Guest-Session。主管換新 QR 時一併撤銷舊 session。
  • PMS 對接：/integration/** 用 API key（IntegrationApiKeyAuthFilter），角色 INTEGRATION。
  • 授權規則：SecurityConfig.java:45-81 以「路徑＋角色」對應，角色有 guest、housekeeping、engineering、manager、frontdesk、duty_manager、owner、INTEGRATION。無 session、CSRF 關閉。
  • 冪等：寫入端點帶 Idempotency-Key，IdempotencyFilter 搭配 processed_ops 表回放上次結果，保留 7 天。

資料庫遷移（Flyway）有什麼規矩？

重點

既有的遷移檔一個字都不能改，連註解都不行——Flyway 會比對每個已套用檔案的 checksum（內容指紋），改了就啟動失敗。要修正只能新增更高版號的檔案。

遷移檔在 tms/src/main/resources/db/migration/，命名 V<n>__說明.sql，目前是 V1 到 V33、連號無缺。後端啟動時 Flyway 會自動套用新版號。

  • 新表要記得 GRANT 給 tms_app（V18 就是為了補 notifications 的授權）。
  • V24__tenant_code.sql:14-30 回填 tenants.code 時只認得「示範飯店、示範二店、測試飯店」三家；資料庫裡有其他飯店時這個遷移會失敗，要先補對照。
