新人導讀：app、specs、tms 各是什麼，從哪裡讀起

新人第一週最常問三件事：app/ 底下五個資料夾各是什麼、specs/ 該怎麼讀、不會 Java 的人怎麼看懂 tms/ 後端。這一頁依序回答，並說明規格是用哪一串指令一步步產出來的。細節都指到其他頁，這裡只給地圖。

約 9 分鐘

app/ 底下五個資料夾各是什麼、彼此怎麼牽連？

重點

兩個是給人用的畫面（員工 App、櫃檯與住客網頁），三個是測試：兩個驗收專案，加上它們共用的「準備測試資料」工具庫。驗收要讀的 feature 檔不放在 app/，統一放在 specs/truth/features/。

先分清楚「產品」和「測試」。mobile 與 web 是真的會交到使用者手上的東西；bdd、web-bdd 與 bdd-support 只在開發時用，負責證明產品照規格運作。

資料夾是什麼技術
app/mobile/員工 App（房務、工務、主管）Flutter
app/web/櫃檯網頁；住客掃房間 QR 開的住客頁也在這裡（app/web/src/guest/）React＋Vite＋TypeScript
app/bdd-support/共用的測試資料工具：直接寫資料庫來準備與清除資料，本身不含任何測試Java 函式庫
app/bdd/員工 App 驗收：在 iOS simulator 裡真的點畫面Java＋Cucumber＋Appium
app/web-bdd/櫃檯網頁與住客頁驗收：開瀏覽器真的點畫面Java＋Cucumber＋Playwright

bdd 和 web-bdd 都依賴 bdd-support，而且是透過本機 Maven 倉庫找到它，所以改了 bdd-support 要重新 mvn install。用下面的腳本跑時會自動做，自己直接下 mvn 才要記得。兩條驗收線讀的 feature 檔分別在 specs/truth/features/ios-app/ 與 specs/truth/features/{frontdesk-web,guest-web}/；後端自己的行為規格則在 specs/truth/features/backend/。

兩條線的差別在起不起後端。網頁驗收的腳本會自己起後端與網頁，一行就跑；App 驗收的腳本不會，要先自己起一個帶 test-support 設定檔的後端（它才有測試用的撥時鐘端點），否則腳本第一步就停下來告訴你怎麼起。

# 網頁驗收：腳本自己起 8080 後端與 5199 網頁，跑完收掉
bash app/web-bdd/run-feature.sh frontdesk-web/待派單/待派單清單.feature desktop
# App 驗收：先起開發堆疊與帶 test-support 設定的後端（8080）
docker compose up -d
TMS_DB_URL=jdbc:postgresql://localhost:5433/tms SPRING_PROFILES_ACTIVE=test-support \
  JAVA_HOME="$(/usr/libexec/java_home -v 25)" ./tms/mvnw -f tms/pom.xml spring-boot:run

# 另開一個終端機，跑單一模組（不帶參數會列出可選模組）
app/bdd/run-module.sh 工務單
app/bdd/run-all.sh          # 全部模組，約 60–90 分鐘

simulator 的指定方式、隔離堆疊與每條線怎麼加場景，見 BDD 測試：三條線各自怎麼跑；工具要先裝哪些，見 第一天。

specs/ 裡的 truth 和 plans 差在哪？

重點

truth/ 是「系統現在長什麼樣」，永遠只有一份；plans/NNN-*/ 是「每一次需求變更做了什麼」，一次一包。兩者靠每包裡的 truth-delta.md 串起來。

問題是：規格要同時回答兩種問題。新人想知道「認領現在的規則是什麼」，維護的人想知道「上次為什麼改了認領」。只用一份會被覆寫的文件，就答不了第二題；只留一包包變更紀錄，又要從頭疊加才答得了第一題。

壞做法只有一份規格，每次需求直接改它

現況清楚，但改了什麼、為什麼改都不見了；出問題時無從回查是哪一次需求引進的。

現在的做法現況一份、變更一包包，中間用 truth-delta 對帳

specs/truth/ 只寫現況：contracts/ 是 API 契約（入口 openapi.yaml，細節依業務分在 groups/），data/data-model.dbml 是資料模型，features/ 是可執行的規格，另有 techstack.md 記技術選型。

specs/plans/ 底下每個 NNN-名稱/ 是一次需求變更的工作包，目前有 001 到 008。每包裡的 truth-delta.md 逐列記下這次把 truth 的哪一塊新增、修改、刪除或確認不動，以及理由，常附上程式位置。

權衡每次需求都要同時維護兩處，而且 truth 必須在實作前先改好。換來的是現況永遠可直接讀，歷史也查得到。

一個工作包裡有哪些檔 — 依產出順序（8 種）
檔案內容
spec.md這次要做什麼：使用者故事與系統規則（另有 checklists/requirements.md 檢查完整度）
features/acceptance/*.feature用業務語言寫的驗收情境，還不分介面
research.md技術調查與選型理由
plan.md這次動到哪些系統介面、分幾波做
ui/畫面設計與靜態雛形
truth-delta.md這次對 specs/truth/ 的每一筆改動與理由
tasks.md可直接照做的實作任務清單，做完一項打勾
implement-notes.md實作時的發現、已知會紅的測試、留給下一手的事

不是每包都有全部的檔。006 是錯誤修正，沒有 research.md 與 ui/，另外多了 evidence/ 放實機截圖；001、002 還沒有 implement-notes.md。plans/ 底下另有一個不帶編號的 desk-board-push-card/，只有一份設計筆記，不是完整工作包。

第一次讀 specs，該照什麼順序讀？

重點

由粗到細：先看手冊總覽的全景，再讀 truth 的句型表與一個模組，接著把一整包工作包從頭讀到尾，最後順著 truth-delta 指的程式位置回到程式碼。

先讀 truth 是因為它是現況，工作包裡的每份文件都假設你知道現況。讀 truth 時不要從 .feature 開始，先讀 dsl.md：它是這個介面的「句型表」，說明每句 Given／When／Then 實際代表什麼操作、狀態用語對到資料庫哪個值。每個介面根目錄有一份共用的，每個模組資料夾裡再各有一份。

  1. 手冊總覽的全景圖：系統有哪些方塊、怎麼連。
  2. specs/truth/features/backend/dsl.md：後端共用句型與狀態用語對照（例如「待認領」就是 pool）。
  3. 挑一個模組讀到底：例如 specs/truth/features/backend/任務執行/，先讀該資料夾的 dsl.md，再讀裡面的 .feature。
  4. 讀完整一包 006（specs/plans/006-engineering-pool-repair-ticket/）：照 spec.md → features/acceptance/ → plan.md → truth-delta.md → tasks.md → implement-notes.md 的順序。
  5. 回到程式碼：truth-delta.md 的理由欄常寫著程式位置，例如 eng_pool_screen.dart:247，照著打開看。

選 006 是因為它從住客報修一路走到主管驗收，前後端都碰到。它的 implement-notes.md 同時是目前「已知會紅的測試」清單，第一次跑測試時會用到。

規格和工作包是怎麼一步步產出來的？

重點

用一串 Claude Code 指令（skill）依序產出，放在 .agents/skills/（.claude/skills/ 是指回那裡的捷徑）：從需求描述開始，經過驗收情境、技術調查、系統分析、更新 truth，最後拆成任務並實作。每一步只寫自己負責的檔。

這串指令的用意是讓「需求 → 規格 → 程式」每一步都留下檔案，並且分清楚誰能動 truth。會改 specs/truth/ 的步驟（技術調查、API、資料、可執行規格）每次改完都要在 truth-delta.md 記一筆，這件記帳工作由 /truth-delta 代勞，不用手動叫。

  1. /specify：把一段需求描述變成新的工作包，寫 spec.md。需要時接著跑 /clarify-over-specs，找出高影響的缺口來問人。
  2. /spec-by-example：把 spec 收斂成業務語言的驗收情境 features/acceptance/。它和下一步都只需要 spec.md，先後可以對調。
  3. /technical-research：寫 research.md，並更新 specs/truth/techstack.md。
  4. /system-analysis：盤點動到哪些介面、分幾波，寫 plan.md。
  5. /api-plan、/data-plan、/ui-plan：由 /system-analysis 依波次委派，分別更新 API 契約、資料模型，以及產出畫面設計 ui/（畫面設計不進 truth）。
  6. /dsl-refine：把驗收情境拆成各介面可執行的 .feature 與 dsl.md，寫進 specs/truth/features/。
  7. /tasks → /implement：產出 tasks.md，再逐項實作並打勾；先由 /implement 自己把新句子寫成會失敗的測試（紅），到「讓測試轉綠」與「重構」的任務才交給 /bdd。

每個指令的完整規則在 .agents/skills/<指令名>/SKILL.md。部分指令會讀 .agents/constitution/ 下的規則檔，這個資料夾目前不在 repo 裡，指令讀不到時只能照 SKILL.md 本身的規則走。

每一步何時停下來問人、為什麼 truth 在規劃階段就直接改、平常修 bug 或改規格該走哪幾步，見 流程 Skill。

不熟 Java，怎麼讀得懂 tms/ 後端？

重點

它是一個 Spring Boot 4.1.1、Java 25 的單一 Maven 專案，分三層：controller 收請求、service 做業務規則、dao 存取資料庫。從網址找到 controller，再一路往下點就讀得懂；行為「應該」怎樣，以規格為準，不以程式為準。

所有程式在 tms/src/main/java/com/athena/tms/。三層的意思很單純：controller 是門口，每個方法對到一個網址；service 是辦事員，判斷誰能做、狀態能不能變，任務狀態的核心是 TaskEngine，員工操作任務的入口是 TaskExecutionService；dao 是檔案櫃，負責讀寫資料表。資料表的來歷看 tms/src/main/resources/db/migration/ 的 Flyway 遷移檔，目前從 V1 到 V29；後端的行為規格測試在 tms/src/test/java/com/athena/tms/bdd/。

讀的時候有三個實用的入口：

  • 從網址進去：在 controller 搜 @PostMapping／@GetMapping，對照 specs/truth/contracts/openapi.yaml 的同名路徑，它會指到 groups/ 底下寫清楚請求、回應與錯誤碼的那份檔。注意 controller 類別上的 @RequestMapping("/api/v1") 是共同前綴。
  • 用 IntelliJ 的 Find Usages（⌥F7）：看一個方法被誰呼叫，比讀全檔快得多。
  • 先讀規格再讀程式：src/main 是從編譯檔反編譯還原的，原本的註解都不在了，還有不少多餘的型別轉換。想知道某個行為「應該」怎樣，先看 specs/truth/features/backend/。
# 起後端（先 docker compose up -d；連 5433 的 Postgres 與 9092 的 Kafka）
TMS_DB_URL=jdbc:postgresql://localhost:5433/tms \
  JAVA_HOME="$(/usr/libexec/java_home -v 25)" ./tms/mvnw -f tms/pom.xml spring-boot:run

TMS_DB_URL 不能省：沒設時資料庫遷移（Flyway）會預設連 5432，與應用本身的 5433 不同。根目錄沒有 ./mvnw，後端一律用 ./tms/mvnw。套件分法、多飯店隔離、登入與設定檔，見 Java 後端；遷移檔為什麼一個字都不能改，見 遷移規矩。

員工按下「認領」，後端程式會經過哪些地方？

重點

一條請求依序經過 controller、權限判斷、狀態變更，再在同一個交易裡記事件與待送匣；交易提交後由背景工作把事件送上 Kafka，最後推到櫃檯看板與各員工的即時連線。跟一遍，就認得後端大部分的骨架。

下面的路徑都相對於 tms/src/main/java/com/athena/tms/。待送匣（outbox）是資料庫裡的一張表，要送出去的事件先寫在這裡，再由背景工作投遞，所以資料與事件不會一個成功一個失敗。

  1. 門口：controller/TaskExecutionController.java:38 的 @PostMapping("/tasks/{id}/claim")，加上前綴就是 POST /api/v1/tasks/{id}/claim，只把單號轉交給 service。
  2. 判斷能認領哪個部門的單：service/TaskExecutionService.java:108 的 claim 取出飯店與登入者，再由 :120 的 claimDept 決定部門；主管認領別部門的單會在 :127 被拒（403）。
  3. 改狀態：service/TaskEngine.java:176 的 claim（上一行 @Transactional 表示整段是一個交易）把任務從 pool 改成 accepted；條件裡帶著「現在是 pool、部門相符」，兩人同時搶只有一人成功。
  4. 記事件並放進待送匣：同一交易裡呼叫 TaskEngine.java:489 的 recordEvent，:499 寫一筆 task_events，:500 經 OutboxWriter 寫一筆 outbox。
  5. 送上 Kafka：交易一提交，service/OutboxRelay.java:74 被叫醒，把待送事件依序送到 tms.task-events；沒被叫醒也會每 2 秒自己巡一次。
  6. 推給畫面：service/TaskEventsSseConsumer.java:79 收到事件，更新櫃檯看板，並推給相關員工的即時連線。

手機推播走的是另一條路：需要通知人的操作會另外寫一筆推播待送（PushOutboxWriter），送到 tms.push，再由 push/PushDeliveryConsumer.java:40 經 FCM 送出。認領本身不發推播。整個事件流的圖與故障時會怎樣，見 Java 後端：一個狀態變化怎麼變成推播與即時更新；這條規則在規格裡的寫法，見 specs/truth/features/backend/待認領/主管認領自己部門的單.feature。
