流程 Skill：一個需求怎麼一步步變成規格、任務與程式

這個 repo 的規格與程式，是用 16 個 Claude Code 指令（skill）一棒接一棒做出來的。這一頁說明每一棒做什麼、讀什麼寫什麼、什麼時候會停下來問人，以及平常開發該挑哪幾棒走。測試本身怎麼跑，見 BDD 測試。

約 10 分鐘

這 16 個 skill 是什麼？整條流程長什麼樣？

重點

skill 是一份寫給 AI 的作業手冊（SKILL.md），在 Claude Code 裡打 /名稱 就照著做。16 個 skill 排成一條線：需求 → 規格 → 系統分析 → 可執行規格 → 任務 → 程式。主要階段由人打指令推進，中間的細活由上一棒委派下一棒。

每個 skill 是一個資料夾，裡面除了 SKILL.md，多半還附有它要遵守的判準（rules/），不少也附範本（templates/）。它們放在 .agents/skills/，另在 .claude/skills/ 放了指回同一份內容的捷徑，Claude Code 才找得到。

讀這一頁會反覆碰到幾個詞，先講清楚：

truth（現況規格）
specs/truth/ 底下「系統現在長什麼樣」的規格，永遠只有一份：技術選型 techstack.md、API 契約 contracts/、資料模型 data/、可執行規格 features/。
工作包
specs/plans/NNN-名稱/，一次需求變更一包，裝這次的需求、分析與任務。
truth-delta（變更紀錄）
每個工作包裡的 truth-delta.md：逐列記下這次對 truth 新增（ADD）、修改（MODIFY）、刪除（DELETE）或確認不動（NOOP）了什麼，以及原因。
Gherkin 與 DSL
Gherkin 是用「假設／當／那麼」寫情境的格式，就是 .feature 檔。DSL 是每個資料夾裡的 dsl.md，一張「句型表」，寫明每一句 Gherkin 實際代表什麼操作、要查哪些資料。

每一棒做什麼、讀什麼寫什麼、什麼時候會停下來？

重點

前半段（到 /dsl-refine）在寫規格，後半段（/tasks 之後）在寫程式。每一棒只寫自己負責的檔，碰到會改變結果的缺口就停下來問人，不自己猜。

下面照順序走一遍。舉例都取自工作包 specs/plans/007-frontdesk-create-request/（櫃檯代開單），它從頭到尾走完整條線，最後的 tasks.md 有 183 條任務全部打勾。

  1. /specify：把一段需求描述變成新的工作包，寫 spec.md（使用者故事、需求、驗收情境與邊界情況）與 checklists/requirements.md，並建好空的 truth-delta.md。它明文禁止改 truth，也禁止改舊工作包。寫完可以再跑 /clarify-over-specs，把整份 spec 掃一遍找高影響缺口。
  2. /technical-research：做技術調查寫 research.md，並直接更新 specs/truth/techstack.md。007 在這一步決定了「同一把防重複鍵兩個請求同時進來，只做一次」要怎麼實作。
  3. /spec-by-example：把 spec 寫成給產品經理看的業務驗收情境，放在工作包的 features/acceptance/。這一層不分前端後端，也不會被任何測試執行。
  4. /system-analysis：盤點這次動到哪些系統介面，排成幾個 Wave（可以同時進行的一批工作），寫進 plan.md，再委派 /ui-plan、/data-plan、/api-plan。007 的 Wave 1 讓畫面與資料模型同時做，Wave 2 才定 API，因為 API 要回什麼取決於前兩者。
  5. /dsl-refine：把業務驗收情境拆成各介面（後端、櫃檯網頁、住客網頁、員工 App）可執行的 .feature 與 dsl.md，直接寫進 specs/truth/features/，再委派 /gherkin-and-dsl 檢查句型與用腳本稽核。
  6. /tasks：把工作包與 truth 變成 tasks.md。順序固定：先裝新技術（Setup）、再搭共用骨架（Foundational）、接著把測試層一次對齊最新的 truth，最後才是每個 feature 的產品程式。
  7. /implement：照 tasks.md 一條一條做，每做完一條驗證後立刻打勾，不能跳步。碰到「讓測試轉綠」與「重構」的任務時委派 /bdd；全部打勾後會問你要不要 commit，不會自己 commit。

/bdd 一次只處理一個 feature 檔，走 red／green／refactor 三步：紅是先讓測試以正確的理由失敗，綠是只補剛好讓它通過的程式，重構是在測試全綠的保護下整理程式。它把每句 Gherkin 接到一段測試程式，這段程式叫 step definition；step definition 怎麼寫、測試怎麼跑，見 BDD 測試：三條線共用的骨架。

停下來的時機各棒都寫得很明確，歸納起來有三種。第一種是需求本身有洞：任何一棒發現會改變故事切分、驗收結果、對外契約或既有行為的缺口，都會叫 /clarify，一輪問 1 到 3 題、一次訪談最多 5 題，每題附背景、選項與推薦答案，沒拿到回答就不往下做。第二種是上游給的東西不夠：/tasks 找不到某句話唯一的 DSL 定義、/bdd 發現 feature 或 dsl.md 有缺口，都會退回 /dsl-refine。第三種是 /implement 發現 truth 與任務互相矛盾，停下受影響的任務並回報。

為什麼 truth 由規劃階段直接改，而不是做完再合併？

重點

四塊 truth 各有唯一一個負責的 skill，在規劃階段就直接改好；truth-delta.md 只是這次改了什麼的紀錄，沒有「做完再合併回 truth」的步驟。舊工作包寫完就不再動，每次新需求都開新的編號。

問題是：一次需求變更期間，同時有「系統現在的樣子」和「這次要改成的樣子」兩個版本。後面每一棒（畫面、API、資料、測試、任務）都要知道要照哪一個版本做，而且彼此要對得上。

壞做法工作包裡各寫一份新版規格，做完再合併回 truth

規劃期間 API 規劃讀到的是舊資料模型、畫面規劃讀到的是舊 API，各自推理出不同版本。合併那一步又是人工對帳，最容易漏，漏了 truth 就不再是現況。

現在的做法負責者直接改 truth，另記一份變更紀錄

techstack.md 歸 /technical-research、contracts/ 歸 /api-plan、data/ 歸 /data-plan、features/ 歸 /dsl-refine，其他 skill 一律只讀。負責者改完就叫 /truth-delta，在 truth-delta.md 自己那一段追加一列，寫明動作、改了哪裡、為什麼；沒改也要記一列 NOOP，表示「看過了，不用動」。後面的 skill 讀 truth 拿到的一定是新版，讀 truth-delta.md 就知道這次動了哪裡。

例如 007 的 truth-delta.md，/api-plan 那段第一列就是新增 POST /desk/requests，並寫明錯誤碼與防重複規則；/tasks 再依每一列是新增、修改還是刪除，決定要排「讓測試轉綠」還是「移除程式再跑回歸」的任務。

權衡truth 在程式寫好前就已經是新版，中間這段時間 truth 與程式不一致，測試會紅，這是預期的；007 就在動工前把這批紅燈逐條記進 implement-notes.md。另外 /truth-delta 看到高影響的修改或刪除、卻沒有經過 /clarify 確認時會拒絕記錄，逼你先問過人。

同樣的道理，舊工作包是歷史，不回頭改。即使這次是修改或刪除既有行為，/specify 也一定開新的 NNN，讓每個決定都查得到出處。

為什麼每個 skill 都要人手動觸發？

重點

16 個 skill 都設了 disable-model-invocation: true，意思是 AI 不能自己決定啟動它們，一定要人打 /名稱。代價是每個主要階段都要人接著打下一棒。

問題是：這些 skill 會開新工作包、改 truth、改程式。如果 AI 可以自己決定什麼時候用，你只是問一句「代開單能不能一次開兩張」，它可能就順手開了一個新工作包，或改了 API 契約。

壞做法讓 AI 看情況自動啟動

省掉打指令的功夫，但規格什麼時候被改、為什麼被改，人不一定知道；改到 truth 的動作尤其難收拾。

現在的做法關掉自動啟動，主要階段由人推進

每一棒做完都會回報產出與「可以進下一棒了嗎」，人看過再打下一個指令，等於每一棒之間都有一道人工關卡。

權衡SKILL.md 裡寫的「委派」（例如 /system-analysis 委派 /api-plan）也受這個開關影響：AI 不一定能自動叫起下一棒，所以有些 skill 直接寫明要去讀下一棒的手冊，例如 /dsl-refine 明寫要先讀 ../gherkin-and-dsl/SKILL.md。如果 AI 沒有接下去，就自己打該指令，並把工作包路徑告訴它。

新功能、小 bug、規格改動，各要走哪幾棒？

重點

新功能走完整條線。規格改動也一樣要開新工作包，只是動作多了修改與刪除。小 bug 先看現有規格抓不抓得到它：抓得到就直接用 /bdd 修，抓不到就等於規格有缺口，改走規格改動。

新功能

  1. /specify（需要時加 /clarify-over-specs）
  2. /technical-research 與 /spec-by-example
  3. /system-analysis（會帶出 ui、data、api 三個規劃）
  4. /dsl-refine
  5. /tasks → /implement

規格改動（改或刪既有行為）

  1. 同樣用 /specify 開新工作包，在 spec 寫明改哪些既有行為
  2. 同樣走到 /dsl-refine；truth-delta 會出現 MODIFY、DELETE 列，各負責者會先叫 /clarify 確認
  3. /tasks 會先排「把舊測試對齊新規格」，再排產品程式或「移除程式＋回歸」
  4. /implement

小 bug

  1. 在 specs/truth/features/ 找描述這個行為的場景
  2. 場景已經紅：直接打 /bdd，指定那個 feature 檔、從 green 開始
  3. 沒有場景抓得到：/bdd 不會自己寫 feature，改走「規格改動」路線

工作包 006（派給工務的單一律開成工務單）就是一個走完整條線的錯誤修正：它是實機走過一輪才發現的問題，修法改了 API 契約、資料模型與四個介面的可執行規格，所以照樣開了新工作包。它沒有 research.md 和 ui/，因為沒有新技術也沒有新畫面，但 truth-delta.md 裡 /technical-research 那段仍然記了一列，表示看過技術選型、不用改。

/constitution 不在日常路線上。它維護 .agents/constitution/ 裡的共同規則（例如規格文件一律怎麼寫），想讓所有 skill 都遵守同一條規矩時才用。

現在用這套流程會踩到什麼？

重點

幾個 SKILL.md 指到不存在的資料夾、指令或過時的名稱，AI 會照字面去找，找不到時要你告訴它怎麼辦。另外稽核腳本需要先裝好 uv。

下面的位置格式是 路徑:行號，都相對於 repo 根目錄。

  • 規則資料夾不存在：多個 skill 要讀 .agents/constitution/CONSTITUTION.md 與 shared.md，但 repo 裡沒有這個資料夾，例如 .agents/skills/specify/SKILL.md:18、.agents/skills/tasks/SKILL.md:16、.agents/skills/implement/SKILL.md:48。讀不到時只能照 SKILL.md 自己的判準走；要補，就用 /constitution 建。
  • /dsl-refine 的介面名稱過時：說明寫它更新 features/backend/ 與 features/frontend/（.agents/skills/dsl-refine/SKILL.md:3），實際的介面資料夾是 backend、frontdesk-web、guest-web、ios-app 四個。用的時候要明講是哪個介面。
  • /clarify-over-specs 指向不存在的 /plan：說明與結尾的建議下一步都寫 /plan（.agents/skills/clarify-over-specs/SKILL.md:3、:38），對應的是 /system-analysis；照本頁的順序，中間還有 /technical-research 與 /spec-by-example。
  • 稽核腳本要 uv：/gherkin-and-dsl 用 uv run 跑 scripts/audit_feature_dsl_topology.py（.agents/skills/gherkin-and-dsl/SKILL.md:58）。沒裝就 brew install uv；這支腳本沒有外部套件，用 Python 3.10 以上直接跑也行。
  • /constitution 指向不存在的 skill：它說後續要接上規則時交給 /skill-engineering（.agents/skills/constitution/SKILL.md:38），repo 裡沒有這個 skill。

其他和測試執行有關的坑（simulator、埠號、會清空資料庫），見 坑與待查：跑測試時會卡在哪。
