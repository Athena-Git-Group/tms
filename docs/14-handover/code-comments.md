# 程式註解慣例

適用於 `tms/src/main` 與 `tms/src/test` 的所有 Javadoc 與行內註解。

## 為什麼需要這份規則

build agent 是隔離執行的，讀到的輸入（phase 卡、mini-handoff、spec）充滿
需求編號、階段編號和踩雷紀錄。這些資訊對 agent 很重要，但程式碼的讀者
沒有這些脈絡。把它們原樣寫進註解，會產出只有當下那個 agent 看得懂的文字。

## 規則

1. **讀者設定**。註解寫給「第一次打開這個檔案、不熟悉本專案歷史」的工程師看。
   不假設讀者知道任何內部代號、階段編號、需求編號或過去的討論。

2. **結構：由上而下的論證順序**。有非顯而易見意圖的註解，不論長短，一律依序寫：
   (a) 這段程式**要保證什麼**（結論先行，一句話立住主線）；
   (b) **怎麼做到**（機制）；
   (c) **不這樣做會壞在哪**（具體的失效情境，例如「同房兩筆回寫顛倒會把房況蓋錯」）。
   長度只決定標記方式——長註解用標題分段，短註解用粗體開頭或乾脆不標——
   不改變這個順序。禁止由下而上：先描述 SQL 或 API 行為、再想到什麼補什麼的寫法，
   每段各自成立但合起來沒有主線，讀者得自己拼論證。
   方法名稱和簽章已經說清楚的（例如 `cancelRequest(sessionToken, taskId)`），
   一句話或不寫都可以；不要硬湊三段。

   **檢驗法**：把程式碼遮住，只讀註解，要能當一篇短文讀下去。
   讀不下去（某段預設你剛讀過上面那段程式碼才接得上），就是順序錯了。

3. **一個論證只講一次**。同一條理由（例如「不能讓後面的訊息插隊」）只出現在
   它所屬的層級：整個類別的不變量寫在類別 Javadoc，方法各自的機制寫在方法
   Javadoc 並視需要一句話回指類別層的保證，不在多處重講同一套理由。
   讀者在三個地方讀到同一件事的三種說法，只會更難確定哪個是準的。
   行內註解同理：**一句話、回指而不重述**——說「這裡在執行類別層的哪條保證」，
   不在原地把那條保證的內容再講一遍（範例見下方「行內註解」）。

4. **內部代號**。提到 FR-xxx、E-xx、Phase xx 這類代號時，必須在同一句用
   一小段白話說明它指的是什麼。例如「FR-005（住客可查看前一次入住的歷史需求）」。
   不寫「phase-05 教訓」這種沒有內容的指涉。

5. **完整句子**。不用破折號或括號塞入多層補充。需要補充就另起一句。

6. **術語一致**。英文術語依下方對照表翻譯；程式碼中實際出現的識別字
   （欄位名、類別名、方法名）保留原文。對照表沒有的詞，同一檔案內用法一致即可。

7. **不重複程式碼**。程式碼本身已經說明的事（例如 SQL 在更新哪個欄位、
   方法在呼叫哪個 API）不寫。註解解釋的是程式碼看不出來的意圖和限制。

8. **去專案脈絡**。如果某段註解只有專案成員才看得懂，就改寫到不需要
   專案脈絡也能理解為止。

9. **歷史與教訓進 handoff，不進註解**。從 phase 卡或 mini-handoff 得知的
   踩雷經驗、設計取捨、與規格的對應關係，寫進 handoff 的
   `Notes for Next Phase` 或 `Spec Deviations`。程式註解只保留讀者操作這段
   程式碼時必須知道的限制。

10. **禁用詞**。「守衛」「空窗」「投影」不得出現在註解。這三個是只有寫的人
    自己懂的行話，一律改成把機制講出來的白話：
    - 守衛 → 「前提條件直接寫在 UPDATE 的 WHERE 裡，條件不符就一列也不改」。
      視上下文可簡寫為「條件式更新」。
    - 空窗 → 「先查詢再更新，查與改之間資料可能被別的請求改掉」。
    - 投影 → 「從事件紀錄整理出來、方便查詢的目前狀態副本」。
      權威來源是事件表，副本可隨時重算。
    同一檔案第一次出現處把機制講完整，之後可用該處建立的簡短說法回指。

## 範例

### 壞

```java
/**
 * 住客側佈景的共用捷徑。
 *
 * <p><b>訂單種子一律 now() 相對住期</b>（phase-05 教訓：seed 的固定日曆住期
 * 在跑測日期之後就全部不「當前」）：{@link #ensureSeeded()} 把種子訂單
 * PMS-88321 改成「現在在住」、502 的訂單推成已退房，並自種 FR-005 要的
 * 「前一筆訂單」與租戶 2 的當前訂單。
 */
```

問題：讀者不知道 phase-05、FR-005 是什麼；「教訓」是歷史敘事而不是說明；
括號和冒號把三層意思塞進一句；「佈景」「種子」「自種」用詞不固定。

### 好

```java
/**
 * 住客側整合測試的共用工具：建立測試資料、呼叫住客 API。
 *
 * <p>測試資料的住期一律以資料庫目前時間為基準（例如「現在起兩小時前入住」），
 * 不寫死日期。寫死的日期在測試執行日之後就不再是「當前住期」，
 * 會讓依賴「現在在住」的斷言失效。
 *
 * <p>{@link #ensureSeeded()} 會把種子資料調整成測試需要的狀態：
 * 房 305 的訂單改為目前在住、房 502 的訂單改為已退房，並新增兩筆訂單。
 * 一筆是房 305 的上一次入住，供「住客可查看前一次入住的歷史需求」的場景使用；
 * 一筆是租戶 2 的當前訂單，供跨租戶掃碼的場景使用。
 * 這些資料屬於種子層，不會被每個場景的清理步驟刪除，整個測試套件只需執行一次。
 */
```

### 長註解的骨架（由上而下論證）

複雜類別（併發、順序保證、跨 instance 協調）的 Javadoc 用三層骨架，
h2/h3 標題標出論證的三段，每個設計決策自帶「為什麼合適」：

```java
/**
 * Outbox relay：定期把 outbox 資料表裡 pending 的訊息送上 Kafka。
 *
 * <h2>這個類別要解決什麼問題</h2>
 *
 * 搬運過程必須同時滿足三件事：
 * <ol>
 *   <li><b>同一個 aggregate_key 的訊息，送達 Kafka 的順序必須和寫入順序一致。</b>
 *       例如同一間房先後產生「dirty → inspected」兩筆 PMS 回寫，如果順序顛倒，
 *       PMS 的房況會被舊狀態蓋掉，而且事後無法自動修正。順序錯誤是不可逆的，
 *       延遲則可以等，所以設計上一律用「寧可慢、不可亂」取捨。</li>
 *   <li>…（其餘保證）</li>
 * </ol>
 *
 * <h2>為了達成這些保證，做了哪些設計決策</h2>
 *
 * <h3>1. 同鍵串行（per-key serialization）</h3>
 * 同一個 aggregate_key 的訊息按 id 排隊，排在前面的那筆還沒 sent（包含送失敗、
 * 正在等退避重試的），後面的全部不送。不同 key 之間彼此獨立，互不影響。
 * <p>
 * 為什麼合適：Kafka 只保證同 partition 內「送進去的順序」會被保留，
 * 不保證「我們送進去的順序是對的」。如果前一筆失敗了、後一筆照送，
 * 就等於把順序送反。串行化是在 relay 這一側把順序釘死的唯一方法。
 *
 * <h3>2. …（每個決策都是：機制一段 + 「為什麼合適」一段）</h3>
 *
 * <h2>已知但刻意不修的殘餘風險</h2>
 *
 * …（風險是什麼、徹底解法是什麼、為什麼現在接受不修）
 */
```

注意順序：全類別的保證先立住（含違反時的具體後果），每個機制段落回扣
它支撐哪條保證。讀者遮住程式碼也能把這篇當短文讀完。
反面就是由下而上版：五段粗體開頭各講一件事（租約怎麼算、attempts 為什麼先加、
為什麼用 UPDATE…），每段都成立，合起來沒有主線。

### 行內註解

壞：
```java
// E-17 的壞 session 只有直插做得出來——簽發端點只簽得出好 session
```

好：
```java
// 過期或已撤銷的住客工作階段無法透過簽發 API 產生，只能直接寫入資料庫。
```

類別層已經論述過的保證，行內註解只回指、不重述。

壞（在原地把類別層的理由再講一遍）：
```java
// 這個 aggregate_key 最早的一筆還沒送成（送失敗或還在等重試），
// 後面的不能插隊，整鍵留到下一輪。其他鍵不受影響。
break;
```

好（一句話說清這裡在執行哪條保證）：
```java
// 同鍵前一筆未送成：依類別註解的順序保證，整鍵停送到下一輪。
break;
```

### 可以不寫的

```java
/** 住客收回。 */
public HttpResult cancelRequest(String sessionToken, UUID taskId) { ... }
```

方法名已經說明一切，這行 Javadoc 刪掉也不損失資訊。保留或刪除都可以，
但不要為了「每個 public 方法都要有 Javadoc」硬湊三段結構。
