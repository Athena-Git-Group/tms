交接 · BDD 測試

規格怎麼變成三條可執行的驗收測試

先看三條線共用的骨架，再挑你要的那一條。每條線都照同一個順序寫：在測什麼、怎麼跑、一句話怎麼走完、怎麼加場景、這條線專屬的坑。

約 10 分鐘

三條測試線共用什麼骨架？

重點

規格只寫一次，用中文寫在 specs/truth/features/。每一行句子比對到一個 Java 方法，方法再透過各自的驅動層去操作真的系統，最後回頭查資料庫驗證。沒有複製、沒有程式碼產生步驟。

幾個會反覆出現的詞：Gherkin 是用「假設／當／那麼」寫測試情境的格式，這裡每份 feature 第一行都是 # language: zh-TW，所以關鍵字是中文。Cucumber 是讀 Gherkin 的測試框架，它把每一行句子比對到一個 Java 方法，這個方法叫 step 定義。

方法上的註解（例如 @當("{string} 把 {string} 派給 {string}")）就是比對用的句型。一條線去哪些 Java 套件裡找 step 定義，這個設定叫 glue。

句型不是隨便寫的。每個子目錄都有一份 dsl.md，它是句型的權威清單：參數、預設值、Java 端怎麼實作、驗證時必須查哪些資料表。後端的 specs/truth/features/backend/dsl.md 開頭寫明：驗證以 Postgres 裡的 tasks、task_events、outbox、processed_ops 為準，不以 API 回應為準。

測試線讀哪個目錄怎麼驅動後端從哪來資料庫
1 後端（tms/）backend/（44 份，13 個模組目錄）同一個 JVM 起 Spring Boot，RestClient 打真的 HTTP測試自己起Testcontainers，隨機埠
2 員工 App（app/bdd/）ios-app/（23 份）Appium＋XCUITest 操作 iOS simulator要先手動起好（預設 8080）外部 Postgres（5433 或 5434）
3 網頁（app/web-bdd/）frontdesk-web/（29 份）、guest-web/（29 份）Playwright 操作 Chromium／WebKit腳本自動起 8080 與 5199外部 Postgres 5433

三條線各自怎麼跑、怎麼加場景？

重點

後端線完全自給自足，只要 Docker；App 線要先自己起好帶 test-support 設定檔的後端；網頁線的腳本會幫你起後端與 vite，但不起容器。挑你要的那一條讀。

線 1：後端行為規格測試

① 它在測什麼？

在同一個 JVM 裡起 Spring Boot，用真的 HTTP 打 API，再查資料庫確認權威狀態。資料庫、Kafka 與照片模擬服務（fake-gcs-server，模仿 Google 雲端儲存）由 Testcontainers——測試開始時自動用 Docker 起真實容器、結束就丟掉的函式庫——自己起，所以不用先起任何服務。

② 怎麼跑？

JAVA_HOME="$(/usr/libexec/java_home -v 25)" TESTCONTAINERS_RYUK_DISABLED=true \
  ./tms/mvnw -f tms/pom.xml test -DargLine="-Dapi.version=1.44" -Dtest=RunTruthFeaturesTest
其他跑法 — 全套、只跑一份 feature 或一個模組、只檢查句型

拿掉 -Dtest=RunTruthFeaturesTest 就是後端全套（行為規格＋舊整合線＋單元測試）。縮小範圍一律靠 -Dcucumber.features 指路徑（相對 tms/）；feature 檔裡沒有任何 @tag，不用標籤篩選。

# 只跑一份 feature（也可以指到模組目錄 ../specs/truth/features/backend/工務單）
JAVA_HOME="$(/usr/libexec/java_home -v 25)" TESTCONTAINERS_RYUK_DISABLED=true \
  ./tms/mvnw -f tms/pom.xml test -DargLine="-Dapi.version=1.44" -Dtest=RunTruthFeaturesTest \
  -Dcucumber.features=../specs/truth/features/backend/工務單/櫃檯轉來的工務單.feature

# 只檢查有沒有找不到 step 定義的句子（不真的執行）：再加
  -Dcucumber.execution.dry-run=true

報表在 tms/target/cucumber-reports/truth.html、truth.json。

③ 一行句子怎麼走完？

以 specs/truth/features/backend/工務單/櫃檯轉來的工務單.feature:14 的背景句「並且 "林佩君" 已把 "305" 派給 "工務"」為例：

  1. RunTruthFeaturesTest 讓 Cucumber 找到這份 feature；ResetHooks 先清空資料表。前面的「飯店有以下員工：」經 StaffFixtures 寫進資料庫，並用正式的 JwtService 簽好 JWT 存進 ScenarioWorld。
  2. 句子比對到 tms/src/test/java/com/athena/tms/bdd/steps/desk/DeskCommonSteps.java:90 的 @假設("{string} 已把 {string} 派給 {string}")：把「工務」轉成 engineering，呼叫 deskApi.assign(...)。
  3. DeskApi.assign（bdd/support/DeskApi.java:63）經 BddApiClient 對 /api/v1/desk/tasks/{id}/assign 送出真的 HTTP，帶 JWT 與 Idempotency-Key（冪等鍵，同一操作重送不會做兩次）。
  4. 後端派給工務時同時開一張工務單，寫入 tasks、task_events、repair_tickets、outbox。
  5. 步驟用 DbProbe 驗證權威狀態（DeskCommonSteps.java:96-110）：狀態待認領、部門 engineering、最新事件是時間等於 MutableClock 現在時間的 triaged、工務單恰好一列。
  6. 後面的「那麼 工務待認領包含 "W-0621"」比對到 steps/repair/RepairThenSteps.java:201：讀前一個 When 打 GET /pool 的回應找單號，再回頭查資料庫。

同檔 :120 的 When 版「當 "林佩君" 把 "305" 派給 "工務"」會先讓 LastOperationGuard 拍快照，且不假設一定成功。

④ 新增一個場景要做哪三步？

  1. 寫規格：在 specs/truth/features/backend/<模組>/ 加場景，句子先查 backend/dsl.md。
  2. 補 step 定義：tms/src/test/java/com/athena/tms/bdd/steps/<模組>/；共用的資料準備放 bdd/support。
  3. 先 dry-run 再實跑：加 -Dcucumber.execution.dry-run=true 確認沒有找不到定義的句子。

⑤ 這條線專屬的坑

  • 指定單一 feature 時會多一個 CucumberTestEngine 的假錯誤，可忽略。
  • Cucumber 只能經由 @Suite 入口執行：tms/pom.xml 的 surefire 設了 excludeJUnit5Engines=cucumber；否則帶了 -Dcucumber.features 時，Cucumber 引擎會無視 -Dtest、以整個 classpath 當 glue 再跑一遍。
  • 同一個 mvn test 裡還有舊線：integration/RunCucumberTest.java 讀 tms/src/test/resources/features/ 底下 8 份舊 feature（不是 truth），還在保護舊行為。改行為時一起看，例如 01-guest-requests.feature:114。

線 2：員工 App 驗收

① 它在測什麼？

在 iOS simulator 裡真的點 App 畫面。Appium 是讓程式遠端操作手機 App 的伺服器：測試對它下「找到這個元素、點它」，它再透過 iOS 的 XCUITest 去操作。

這裡用原生 XCUITest driver，不用 appium-flutter-driver，所以 App 裡每個要被找到的元素都要掛一個 Semantics identifier——Flutter 寫進系統無障礙樹的字串 id，Appium 用 AppiumBy.accessibilityId 找它（約定見 Flutter App）。

這條線還依賴 App 內的測試後門：以 --dart-define=TEST_BACKDOOR=true 編譯時（app/mobile/lib/core/test_backdoor.dart:56），App 在 simulator 內的 127.0.0.1:9099 開小 HTTP 伺服器，讓測試撥時鐘、讀狀態、注入斷線，也用來直接帶入登入狀態（/session）與把 App 重置回登入頁（/reset）。

② 怎麼跑？

腳本不會幫你起後端，要先自己起，而且一定要帶 test-support 設定檔（SPRING_PROFILES_ACTIVE=test-support）。只有帶了它，後端才有可撥時間的測試時鐘 /api/v1/test/clock 與其他 /api/v1/test/** 測試端點；沒帶的話，腳本第一步的就緒檢查就會停下來：

# 先起開發堆疊（含照片模擬服務 4443，沒有它後端起不來）＋帶 test-support 設定檔的後端（8080）
docker compose up -d
TMS_DB_URL=jdbc:postgresql://localhost:5433/tms SPRING_PROFILES_ACTIVE=test-support \
  JAVA_HOME="$(/usr/libexec/java_home -v 25)" ./tms/mvnw -f tms/pom.xml spring-boot:run
# 再跑單一模組（不帶參數會列出可選模組）
UDID=B07951C2-DF41-4AF6-9C98-0DFC7413ED8C app/bdd/run-module.sh 工務單
其他腳本與腳本做了什麼 — 全量、只跑推播、改連隔離堆疊、不經腳本直接下 mvn 
app/bdd/run-all.sh                # 全量，約 60–90 分鐘
app/bdd/run-f3.sh                 # 只跑推播模組

# 覆寫預設值（見 app/bdd/lib/env.sh）
UDID=B07951C2-DF41-4AF6-9C98-0DFC7413ED8C \
BACKEND_URL=http://127.0.0.1:8081 BACKEND_DB_PORT=5434 \
  app/bdd/run-module.sh 工務單

腳本開跑前檢查 GET /api/v1/pool 連得上、/api/v1/test/clock 回 200、Postgres 埠連得上。接著做五件事：

  1. 檢查後端就緒；每次也會先 mvn install bdd-support。
  2. flutter build ios --simulator --debug --dart-define=TEST_BACKDOOR=true --dart-define=API_BASE_URL=...、開機 simulator、安裝 App（裝完會確認，最多重裝 3 次）。
  3. 在 4723 起 Appium，log 在 /tmp/tms-app-bdd-XXXXXX/appium.log。
  4. mvn test，帶入 Appium 位址、UDID、bundle id、後端與資料庫位址。
  5. 收尾時關掉 Appium 與 simulator。

不經腳本直接下 mvn 時，要自己先 JAVA_HOME="$(/usr/libexec/java_home -v 25)" mvn -q -f app/bdd-support/pom.xml install。報表在 app/bdd/target/cucumber-reports/{truth,module,f3-push}.html。

③ 一行句子怎麼走完？

以 specs/truth/features/ios-app/待認領/待認領列表.feature:4-23 為例：

  1. app/bdd/run-module.sh 待認領 完成就緒檢查、編譯安裝 App、起 Appium，再以 -Dcucumber.features=../../specs/truth/features/ios-app/待認領 執行 RunModuleFeatureTest。
  2. AppiumWorld 的 @Before(order=0)（AppiumWorld.java:97-102）建好 IOSDriver，呼叫 resetAppState()：先叫 App 測試後門 9099 的 /reset 清掉 App 記在記憶體裡的狀態並回登入頁（叫不到才用 simctl 重開 App），再清後端資料、重置時鐘。
  3. 「房務待認領有以下任務：」→ steps/pool/PoolGivenSteps.java:20 → BackendChannel 用 JDBC 直接把任務寫進資料庫。
  4. 「"阿美" 在 App 打開待認領」→ steps/pool/PoolWhenSteps.java:21 → 用後端登入 API 取得這位員工的登入結果，交給後門 /session 直接進首頁（AppiumWorld.java:263-281），再透過 Appium 切到待認領頁，元素都用 accessibilityId 定位。
  5. 「待認領列表依序為 317、313、314、215、418」→ steps/pool/PoolThenSteps.java:56：先打 GET /pool 比順序，再讀畫面上每張卡片的 Semantics identifier 比順序；不符時印出元素樹。

④ 新增一個場景要做哪三步？

  1. 寫規格：在 specs/truth/features/ios-app/<模組>/ 加場景，句子先查 ios-app/dsl.md。
  2. 補 step 定義，App 新畫面加 Semantics identifier：step 在 app/bdd/src/test/java/com/athena/app/bdd/steps/<模組>/；資料準備放 app/bdd-support（改完要重新 install）。
  3. 先 dry-run 再實跑：-Dcucumber.execution.dry-run=true。

⑤ 這條線專屬的坑

  • Appium 4723 與 simulator 全機唯一：兩個 App 驗收同時跑會搶同一個 session，整輪作廢。開跑前 lsof -i:4723 與 ps aux | grep RunModuleFeatureTest。
  • 預設 simulator 不存在：app/bdd/lib/env.sh 與 AppiumWorld.java:92 寫死的 79F32D5C-7A71-47D6-AA8D-8142E68CFF48 在原機器已找不到，一律用 UDID= 指定。
  • App 一定要用 TEST_BACKDOOR=true 編譯，否則每個場景都「等測試後門就緒逾時」。偶發的同一錯誤多半是環境訊號，重跑一次再判斷。
  • simulator 剛開機時 simctl install 會靜默失敗（env.sh 已加重裝驗證）；另外要接硬體鍵盤，否則螢幕鍵盤會蓋住密碼欄：defaults write com.apple.iphonesimulator ConnectHardwareKeyboard -bool true。
  • 全量要 60–90 分鐘，電腦睡眠會殺掉它：開跑前掛 caffeinate -dimsu -t 28800。
  • 只支援 iOS：AppiumWorld.start() 遇到 Android 直接丟 UnsupportedOperationException。

線 3：櫃檯與住客網頁驗收

① 它在測什麼？

用 Playwright（以程式操作真實瀏覽器的框架，這裡用 Java 版）開櫃檯與住客網頁。同一份 feature 可用三種瀏覽器設定跑，由 -Dweb.profile 選（WebProfile.java），不認得的值直接丟例外：

  • desktop：Chromium 1280×720，滑鼠操作。
  • ipad：WebKit 1180×820，觸控。
  • phone：WebKit 393×852，觸控（住客頁專用，語言預設繁中）。

櫃檯網頁以 desktop 跑整套。ipad 跑整個目錄時，腳本只跑標了 @ipad 的 feature，也就是畫面會因尺寸或觸控而不同的那幾份；其餘行為在兩種尺寸下相同，不必整套重跑。新寫的規格只要有 iPad 專屬的畫面或手勢，就在「功能:」上一行加 @ipad。指定單一份 feature 時照樣全跑；真的要整套都跑 iPad，設 IPAD_ALL_SCENARIOS=1。

② 怎麼跑？

先 docker compose up -d；腳本會自己起 8080 後端與 5199 vite，但不會幫你起容器，開跑前會確認 Postgres、Kafka 與照片模擬服務 4443 都連得上。

bash app/web-bdd/run-feature.sh frontdesk-web/待派單/待派單清單.feature desktop
完整參數、路徑規則與腳本流程 — --keep／--stop、住客頁、dry-run、結束碼、日誌位置 
bash app/web-bdd/run-feature.sh [--keep] [--stop] [--rebuild] [feature 路徑] [desktop|ipad|phone]

bash app/web-bdd/run-feature.sh --keep frontdesk-web/ desktop       # 櫃檯全部，跑完保留後端與 vite
bash app/web-bdd/run-feature.sh --keep guest-web/ phone             # 住客全部
bash app/web-bdd/run-feature.sh guest-web/設備報修/組成文字送出.feature phone
bash app/web-bdd/run-feature.sh --stop                              # 收掉 --keep 留下的行程

# 只檢查句型（仍會先起後端與 vite）
MAVEN_ARGS="-Dcucumber.execution.dry-run=true" bash app/web-bdd/run-feature.sh <路徑>

路徑規則：以 guest-web/ 或 frontdesk-web/ 開頭就相對於 specs/truth/features/，否則相對於 frontdesk-web/。可以指整份 feature、一個模組目錄，或單一場景（xxx.feature:18，冒號後是場景那一行的行號）。不給 profile 時 guest-web/ 用 phone，其餘用 desktop。

腳本依序：檢查 JDK 25、必要指令與 Playwright 瀏覽器 → 取目錄鎖（app/web-bdd/target/run-feature/lock）→ 確認 5433、9092 與 4443 連得上 → install bdd-support → 起 8080 後端（沒有 jar 或原始碼比 jar 新就重建，約 30 秒）→ 起 vite 5199 → mvn test → 收掉自己起的行程。

結束碼：0 通過、2 環境問題、130／143 被中斷，其他是 mvn 的結束碼。日誌在 app/web-bdd/target/run-feature/{backend,web,test}.log，報表在 app/web-bdd/target/cucumber-reports/frontdesk-web.html，失敗時會把開著的分頁截圖附進報表。

③ 一行句子怎麼走完？

  1. run-feature.sh 起好 8080 與 5199，以 -Dweb.profile=desktop -Dweb.baseUrl=http://localhost:5199 執行 RunFrontdeskWebFeaturesTest。

④ 新增一個場景要做哪三步？

  1. 寫規格：在 specs/truth/features/frontdesk-web/ 或 guest-web/ 的模組目錄加場景，句子先查該目錄的 dsl.md。
  2. 補 step 定義與頁面物件：step 在 app/web-bdd/src/test/java/com/athena/web/bdd/steps/<模組>/；頁面操作封裝進 pages/；資料準備放 app/bdd-support。
  3. 先 dry-run 再實跑：MAVEN_ARGS="-Dcucumber.execution.dry-run=true"。

⑤ 這條線專屬的坑

  • 後端只能是 8080：app/web/vite.config.ts 把後端寫死成 http://localhost:8080，代理 /api、/staff/stream、/guest/stream、/guest。手動環境（8083）是用 node -e 呼叫 vite 的 createServer 在啟動時蓋掉代理，沒有改設定檔。
  • 沿用既有的 8080 後端時，它沒帶 test-support 設定檔會報錯：先 run-feature.sh --stop。
  • 命令列另指定 cucumber.plugin 時要帶上 StepPhaseListener：它不是報表，而是讓「後端沒有任何資料被改動」這類結果句拿得到 When 之前的快照。
  • 表格欄位有白名單：TaskTableRows 不認得的欄位直接丟錯（TaskTableRows.java:110）。
  • 住客頁沒有自己的入口：只有 RunFrontdeskWebFeaturesTest，寫死讀 frontdesk-web/；腳本用 -Dcucumber.features= 指路徑時 Cucumber 會忽略寫死的目錄，所以同一個入口也能跑 guest-web/。

App 與網頁的測試資料怎麼準備？為什麼不走後端 API？

重點

app/bdd-support 讓「假設」步驟直接用 JDBC 寫資料庫（只有照片例外，要經正式 API 上傳），「當」與讀回一律走正式 REST。後端刻意沒有測試用的造資料端點。代價是種資料的 SQL 要跟著資料表結構手動維護。

黑箱驗收最大的麻煩是「假設」：要讓畫面出現一張「工務已認領、做到一半」的單，得先讓後端資料處於那個狀態。

壞做法在後端開一組「測試專用」的造資料 API

寫起來最快，但正式程式碼裡多了一批只給測試用的端點；部署時忘了關，就是任何人都能任意改資料的後門。

可行但很慢每個假設都用正式 API 一步一步操作到那個狀態

最真實，但一張「做到一半」的單要經過建單、派單、認領、開始好幾個請求，整套驗收會慢好幾倍；有些狀態（例如三天前建立的單）根本操作不出來。

現在的做法假設直接寫資料庫；當與讀回走正式 REST

BackendChannel（約 3000 行）以 -Dbackend.db.url／user／password（預設 jdbc:postgresql://127.0.0.1:5433/tms、tms／tms，即 Flyway 管理帳號）直接寫入飯店、員工（bcrypt 雜湊格式與後端一致）、各狀態的單、訂房、住客請求。這個決定寫在 app/bdd-support/pom.xml 的註解。

resetBusinessData()（BackendChannel.java:436）在同一個交易裡先 LOCK TABLE 再 TRUNCATE … RESTART IDENTITY CASCADE，避免與後端查詢互相卡死。

權衡後端行為規格測試另有自己的 tms/src/test/.../bdd/support/*Fixtures，兩邊的 SQL 是手動對照維護的：改了一邊，要記得檢查另一邊。

照片是唯一的例外。工務單照片的內容必須真的存在照片模擬服務裡，畫面才讀得到，光寫一列資料庫不夠；所以 insertReportPhotos、replaceRepairPhotos 以上傳者的身分經正式 API 建立並上傳照片，再用 SQL 把照片綁到工務單（BackendChannel.java:1389-1416）。上傳者必須是同一個 BackendChannel 建過、知道帳密的員工。每張照片都是內容不同、真的解得開的 1 × 1 JPEG：只有開頭結尾記號的假 JPEG 過得了後端檢查，但 App 與瀏覽器會顯示「照片無法顯示」。另有 markLegacyPhoto（把照片改成舊版留下的樣子）、repairPhotoIds（照工務單詳情的排序列出照片編號）、photoContent（以某位員工身分讀照片）。所以跑 App 線與網頁線時，後端連的照片模擬服務 4443 一定要在。

內建兩組預設資料：App 線的「測試飯店」（代碼 test-hotel，密碼 demo1234）；櫃檯網頁的「雅典娜酒店」（代碼 athena，密碼 Tms12345，12 個帳號 F0101…O0001，客房 2–5 樓每層 01–16）。

員工編號刻意不跟其他飯店重複，因為後端登入沒帶飯店代碼時會跨飯店找帳號（登入怎麼決定飯店）。

多個工作目錄同時 install bdd-support 會互相覆蓋 ~/.m2 裡同一份 SNAPSHOT。多個 git worktree 平行開發時，改用獨立的本機倉庫（後端測試不依賴 bdd-support，不需要）：

export MAVEN_ARGS="-Dmaven.repo.local=$HOME/.m2-004/repository \
  -Dmaven.repo.local.tail=$HOME/.m2/repository \
  -Dmaven.repo.local.tail.ignoreAvailability=true"

三條線能不能同時跑？

重點

後端線可以跟誰都同時跑。App 線與網頁線預設共用 8080 與 5433 的 tms 資料庫，而每個場景開頭都清空它，所以不能同時跑；要同時跑，App 線改連 8081／5434 的隔離堆疊。

改連隔離堆疊用環境變數切換：BACKEND_URL=http://127.0.0.1:8081 BACKEND_DB_PORT=5434。這套堆疊目前 repo 裡沒有啟動腳本，見接手待查。

新增場景時，三條線共通的規矩是什麼？

重點

句型先查 dsl.md，沒有就先補進去再寫；規格本身有缺口時不要自己補腦，回到規格流程處理。

  • 新句型先寫進 dsl.md：寫清楚「怎麼做、權威狀態落在哪、要查什麼」。
  • 句型裡有斜線：Cucumber Expression 的裸 / 代表「或」，中文句裡的斜線要寫成 \\/。
  • 規格有缺口（會影響驗收意圖或句型邊界）時回到規格流程；specs/plans/006-engineering-pool-repair-ticket/implement-notes.md 有多筆「待回交」的範例。
  • specs/plans/NNN-*/features/acceptance/*.feature 不被任何測試線執行：它是需求階段的業務流程驗收稿，要先拆成介面層級的 truth feature 才會變成可執行測試。

完整的需求流程是 /specify → … → /dsl-refine（寫 truth feature 與 dsl）→ /tasks → /implement → /bdd，每一步做什麼、何時停下來，見 流程 Skill。
