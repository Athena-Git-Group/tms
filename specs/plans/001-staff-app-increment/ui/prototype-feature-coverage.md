## 1. 原型畫面清單

### 1.1 視角

原型右側是「情境模擬」操作面板（不屬於 App 畫面），可切換**兩個登入視角**：

| 視角 | 登入者 | 說明 |
| --- | --- | --- |
| 房務 | 阿美（房務 · 3 樓，H-0532） | 打掃、備品、報修 |
| 工務 | 阿德（工務 · 全館，E-0217） | 工務單分流、維修、保養 |

**沒有主管視角**。主管／住客／櫃檯的行為全部由模擬面板按鈕觸發（查房全過／退回、核准／退回工務單、急件降級、作廢、改派、住客掃碼、住客撤回、班末掃描、請假退回、驗收…），畫面只呈現員工端看到的結果。

### 1.2 Tab 與主要畫面（房務視角）

Tab bar 四分頁：**首頁／待認領／通知／我的**（註：待接池在原型叫「待認領」）。交班單收在「我的 › 工作磚」。

### 1.3 工務視角畫面（同一 App，部門切換）

工務首頁（進度環「x / y 張已完修」＋手上張數＋急件數＋今日保養 x / y＋「下一張（急件優先）」＋我的任務含「等主管審核」「已完修」chip）；工務待認領（來源分流磚：全部／急件／住客／櫃檯／房務報修）；工務單詳情（步驟條「待開始 → 維修中 → 完修 → 驗收」＋處理歷程頁「怎麼來到工務＋處理紀錄」）；暫停面板（等零件、需要外包廠商、住客在房約時間、先處理別的急件、公共區域／保養可「放回待認領」）；完修回報（照片必填＋處理結果三選一：已修好／暫時處理（自動建追蹤單）／無法修復 OOO）；開工單 FAB（客房／公共區域、類別、照片必填、「誰來處理」）；保養（自動派單進我的任務）。

### 1.4 狀態標籤與顏色語意（房務 chip）

模擬面板自己附了一張「狀態標籤對照（系統設計 9 個狀態中員工看得到的 6 個）」。`chip()` 實際輸出：

| 原型標籤 | 內部 state | 用色 | backend dsl 對照 |
| --- | --- | --- | --- |
| 待認領 | pool | 橘底 | 「待接」`pool`（**用語不同**） |
| 待開始 | accepted | 灰底 | 待開始 ✔ |
| 退回重做 | accepted＋redo>0 | 紅底 | （dsl 無此標籤；重做用 redo_count 表達） |
| 已延後 | snoozed | 橘底 | 已延後 `deferred` ✔ |
| 已中斷 | paused | 黃底 | 已中斷 `interrupted` ✔（**內部命名 paused**） |
| 進行中 | doing | 青綠底白字 | 進行中 ✔ |
| 待查房／已送達 | done（打掃／非打掃） | 淺青底 | ✔ |
| 查房通過 | inspected | 綠底 | ✔ |
| 完成 · 免查房 | inspected＋waived | 灰底綠字 | ✔ |
| 已取消 | cancelled | 灰底 | ✔ |

工務 chip：等主管審核／待認領／待開始／維修中／已暫停／已完修（工務單 dsl 用語是「已認領／處理中／已完修」——**又是另一套**）。

### 1.5 情境模擬怎麼走（互動流程）

面板按鈕 → 改 state → 畫面反應：住客掃碼進池（推播「新需求 · 316 衣架 ×4」＋同樓層 chip＋池內標亮）；查房全過／退回（退回會重設計時與 SOP、推播、首頁紅標）；續住免查房開關；工務單流程（報修 → 主管核准／退回／急件直送 → 工務認領／維修／完修 → 房務端狀態列同步）；離線切換與恢復同步；未接超時兩段升級；請假退回／班末退池／住客撤回／作廢／改派；撞單（認領失敗）；上傳失敗一張；相機權限拒絕；推播權限關閉；共用手機／臨時密碼；即時動態位置切換。

## 3. 覆蓋矩陣：feature → 原型

判定：**有**＝原型有對應畫面/元素且語意一致；**部分**＝有對應但呈現、文案或機制有落差；**無**＝原型找不到對應。

### F1 首頁今日進度 — 部分

| Rule | 判定 | 原型證據與落差 |
| --- | --- | --- |
| R1 今日進度四項 | 部分 | 進度環卡有「x / y 間房已清完」（＝打掃完成／總數）、「預估剩餘工時」、「臨時需求完成 N 單」；但第四格是「**查房通過 N**」，**沒有「今天完成單數」**。且全部在前端用本機任務算（`finishedClean`、`remainMin`），不是「後端算出」的值 |
| R2 待開始依後端推薦順序 | 部分 | 首頁有「下一間」卡與「我的任務」列表，但排序是前端寫死（state 排序 → redo 優先 → 房號升冪，列表標題寫「依樓層排序」）；feature 期望 302、316、308（redo 優先、備品插隊）這種**後端推薦順序**，原型 `nextTask()` 邏輯近似但非後端回應 |
| R3 連續零退回天數 | 無（邏輯有、畫面沒掛） | `renderVals` 有 `streak`／`streakText: '連續 6 天零退回'`，但目前 template **沒有任何節點渲染它**（只在通知假資料 n4 的內文「連續 6 天零退回，繼續保持。」出現）。工務側同樣有 `連續 12 天零返修` 未上畫面 |
| R4 逾時升級橫幅 | 無 | 原型完全沒有「逾時升級橫幅」元件；逾時走「未接超時」兩段模型：推播＋通知中心紀錄＋池內單卡標籤「未接 · 已提醒同仁／已通知主管」，無 L1/L2/L3、無首頁橫幅、無「處理完自動消失」的橫幅行為 |

### F2 任務卡狀態與提示 — 部分

| Rule | 判定 | 原型證據與落差 |
| --- | --- | --- |
| R1 一次一間提示 | 有 | `busyAlert`：Alert「一次處理一間」＋「305 還在進行中。先完成或中斷它，再開始這間。」＋「前往 305」；308 不變。feature 只要求提示含「305 還在進行中」，吻合 |
| R2 中斷單顯示停住的已做時間 | 有 | paused 任務頁計時顯示 `pausedSec`（不走），副標「已暫停 · 預估 N 分」；列表副標「已做 mm:ss · {原因}」 |
| R3 實心紅徽章「已升級 L{n}」 | 無 | 任務卡（我的任務）沒有任何升級徽章；esc 標籤只出現在待認領單卡，且文案是「未接 · …」不是「已升級 L1」 |
| R4 到期「到期 11:00」／「已過到期（09:30）」 | 無 | 原型任務完全沒有 `due_at`／到期時間概念；它的時間提示是「**超時 N 分**」（超過**預估分鐘**），是另一個概念。也因此「不顯示 SLA 時限標記」無從對照 |
| R5 完成 · 免查房 | 有 | chip「完成 · 免查房」、步驟條末步「免查房」、狀態列「完成 · 免查房／房況已回寫 PMS：住客房・已整理（OC）」、慶祝頁「免查房，直接完成」 |

### F3 點開推播的去處 — 部分

## 4. 規格待補清單：原型 → feature（設計先行、規格待補）

原型有、9 支 feature 完全沒規格化的畫面／功能，依建議優先序：

1. **任務頁核心互動**：步驟條（已接→進行中→完成→查房/免查房/送達）、一狀態一主按鈕（開始/完成/延後/中斷/恢復處理）、SOP 勾選與「跳過不擋流程」、計時 hero 與「超時 N 分」（超過預估）提醒、完成慶祝頁。這是 App 最主要的操作流程，truth 目前只有零星斷言（已做分鐘、狀態文字）。
2. **延後／中斷原因面板**：預設原因清單（延後：請勿打擾…；中斷：缺備品，去拿、需要工務協助…）＋其他原因 60 字——backend 有 hold_reason／deferred_by_self，App 端選原因的畫面沒 feature。
3. **工務視角全部**：工務首頁（急件優先排序、今日保養）、工務待認領（來源分流：急件/住客/櫃檯/房務報修）、認領撞單、暫停（含「放回待認領」限公共區域/保養）、完修回報（已修好/暫時處理→追蹤單/無法修復 OOO→PMS 停用）、開工單 FAB、主管驗收步驟、處理歷程頁。
4. **通知中心頁**：今天/更早分組、未讀、全部標為已讀、點開導頁、「沒跳出的通知仍留紀錄」——推播 feature 只驗「點開去處」，收件匣沒有規格。
5. **離線模式整體規則**：「進行中的單可以做完；開始/認領/延後/開新單一律擋」（`offlineBlock` Alert）、離線列、待同步筆數、「即時連線異常 → 每 5 秒輪詢」降級列——F8 只覆蓋工務單離線暫存這一角。
6. **工務單生命週期（房務端）**：等主管審核/核准/未核准（補資料再送出）/撤回、狀態摘要卡、進度直列、主管降級急件附原因——F8/F9 只管送出前。
7. **帳號與登入**：登入頁（記住帳號/共用手機）、錯誤與鎖定、臨時密碼強制改密、登出守衛（離線/有進行中的單不能登出）。
8. **我的**：推播通知設定（必要通知不能關、只在上班時間通知）、文字大小、多語言（含「使用者輸入維持原文」）、個人資料。
9. **遺失物**：拾獲登記（照片必填＋浮水印、地點 chips）、我登記的、物品詳情與狀態（待交到櫃檯/櫃檯保管中/已認領/逾期）。
10. **交班單分頁**：凍結快照、簽收（「我已閱讀，簽收交班單」「已簽收 08:02」）——F6 只驗任務頁交辦區，交班單本體沒 feature。
11. **即時動態（Live Activity）**＋急件不重複推播規則（有即時動態時急件只更新動態）。
12. **未接超時升級（池內單）**：兩段（一般 10/20 分、急件 3/8 分）提醒同仁→通知主管、單卡標籤——與 truth 的 L1/L2/L3 模型需先對齊（見 §5），對齊後補規格。
13. **雜項**：撞單提示（「這單已被小陳認領」）、住客撤回、班末退池、請假退回附進度、主管作廢/改派的員工端呈現（部分散落於推播 feature 的例子，但畫面行為沒規格）、慶祝頁「全部做完→去待認領」、首頁各空狀態文案、相機權限拒絕/隱私提醒、照片檢視器。

> 註：第 3、7、8、9、10 項是否入本次 increment 由 plan 決定；但第 1、2、5、6 項直接支撐現有 9 支 feature 的流程，建議優先補。
