# 前端 / UI 與靜態雛形規劃

## 介面範圍

- 目標系統介面：`房務／工務員工 App（iOS，Swift；Android 另案）`——單一 App 依登入者部門切換房務／工務視角，無獨立主管視角（主管／住客／櫃檯的動作一律由「情境模擬」操作面板代打，App 畫面只呈現員工端看到的結果）。
- 需求來源：`spec.md` 的 FR-001–048、`specs/truth/features/ios-app/` 9 支 feature（任務執行、工務單、今日進度、待接池、房間交辦、查一下、推播）。
- 上游依據：`spec.md`、`plan.md`（Wave 2 `iOS 員工 App 介面`）、`truth-delta.md`、`ui/prototype-feature-coverage.md`（本次最重要的輸入）、`specs/truth/features/ios-app/**`、`specs/truth/features/backend/dsl.md` 狀態用語對照表。
- 產出順序：`先定稿 ui/ui-plan.md，再依這份 plan 對 ui/prototype/Main.dc.html 做「你→您」文案掃除，輸出 ui/index.html。`
- 視角定位：
  - **房務視角**（阿美）：打掃、備品、報修。Tab bar 四分頁——首頁／待認領／通知／我的；交班單收在「我的 › 工作磚」。
  - **工務視角**（阿德）：工務單分流、維修、保養。同一 App 用部門切換呈現，不是獨立產品。
  - **情境模擬操作面板**：原型右側的按鈕群（住客掃碼、主管查房全過／退回、核准／退回工務單、急件降級、作廢、改派、班末掃描、請假退回、驗收…）**不是產品畫面**，是 reviewer 用來模擬「別人做的事」好觀察 App 反應的 review 工具。這一整塊（含「情境模擬」標題、視角切換按鈕、實機載體／iOS 版本選項、觸覺回饋說明文字）**不進 truth、不建 accessibility id、/dsl-refine 不得引用它當驗收依據**。App 實作時這塊整個不存在。

## 視覺方向

- 風格來源：`既有可互動原型`（Claude Design 匯出，`ui/prototype/Main.dc.html`），品牌色票、M3／iOS 雙設計語言 token、間距與圓角在原型的 `<style data-dc-design-system-vars>` 已完整定義，本輪沿用，不重新設計。
- 本次風格結論：延續原型既有視覺——品牌青綠 `#0C7680`、iOS 26 Liquid Glass 風格 Tab bar 為預設、M3／iOS 元件並存（依載體切換）。
- 視覺重點：任務卡狀態 chip 的色語意（橘＝待認領、灰＝待開始、紅＝退回重做、青綠＝進行中…，見下方「畫面↔feature 歸屬矩陣」後的狀態對照）、進度環與計時 hero、工務單照片流程的上傳狀態回饋。
- 審美原則：`ui/index.html` 必須像產品本身，不得把分析備註、元件樹、TODO 或 reviewer 說明寫進畫面；「情境模擬」面板例外——它本就是原型自帶、供人判讀的操作區，不算产品文案，但同樣不得新增任何 ui-plan 自己的說明文字進去。

## 四筆產品裁決的記錄與影響面

以下四筆為使用者已拍板的裁決，是本輪 `/dsl-refine` 與後端修訂的依據；ui-plan 只記錄方向，不在本次改動 truth。

### 裁決 1 — 用語統一「待認領」

- **結論**：`specs/truth/**`、Terms、後端推播文案全面把「待接池／待接」改為「待認領」；原型用語已經正確，不改原型。
- **影響面**：`specs/truth/features/backend/dsl.md` 狀態用語對照表第一列（`待接` → `pool`）要改標籤文字；`specs/truth/features/ios-app/待接池/` 的 feature 標題與句型、`specs/truth/features/backend/待接池/` 的 feature 與 dsl、`PushPayload` 相關文案、以及任何引用「待接池」做畫面導頁說明的句子，都要在 `/dsl-refine` 一次掃完（風格鐵則：改一個詞要全文一次掃完，不做半套）。

### 裁決 2 — 逾時升級採原型「未接超時」兩段模型

- **結論**：放棄 truth 的 L1/L2/L3 三層＋首頁/待接池橫幅＋任務卡「已升級 L{n}」實心紅徽章。改採原型模型：一般單未接 10 分鐘提醒同仁、20 分鐘通知主管；急件未接 3 分鐘提醒同仁、8 分鐘通知主管；呈現方式是系統推播＋通知中心紀錄＋待認領池內單卡標籤「未接 · 已提醒同仁」／「未接 · 已通知主管」，沒有橫幅、沒有徽章、沒有 L 層。
- **影響面**：後端已經照 L1/L2/L3＋`esc_level`＋`automation_rules`＋`due_at`＋SLA 設定鍵實作（見 `truth-delta.md` `/data-plan` 的 `Table automation_rules、tasks.due_at、tasks.rule_hit` 一列），這是**待改項**——backend dsl（`backend/dsl.md` 的逾時升級橫幅 Then 句型、`esc_level` 欄位語意）、App dsl（`ios-app/dsl.md` 的「畫面顯示逾時升級橫幅」「畫面沒有逾時升級橫幅」兩個 Then 句型）、以及已落地的 `V6 migration`／後端程式碼，都要在 /dsl-refine 之後排入改動；原型不改。
- 一併影響 F2-R4（到期 `due_at` 顯示與「不顯示 SLA 時限標記」）：due_at／SLA 門檻欄位是為了撐住 L1/L2/L3 才新增的，邏輯上隨本裁決一併退場，但「到期時刻」是否仍以其他形式保留（例如單純顯示 `due_at` 但不掛升級層級）**本次四筆裁決沒有明講**，列為下方「剩餘風險」待 /dsl-refine 另行確認，不要自行假定。

### 裁決 3 — 急件判定權採原型「系統判定」

- **結論**：急件由系統依飯店設定規則判定，房務不能改，主管事後修正；放棄「建議設為急件、由人決定」的提示式設計。
- **影響面**：`specs/truth/features/ios-app/工務單/` 的 `開單提示.feature` R2（目前期望「建議設為急件」提示句）要向原型修訂為「系統判定：急件 · {規則}」＋「房務不能更改，判錯由主管修正」的卡片語意；對應 backend 工務單 dsl 若有「建議急件」相關 Then 句型也要一併修；原型不改。

### 裁決 4 — 稱謂統一「您」

- **結論**：這筆是**原型要改**。`ui/index.html` 的使用者可見文案全面「你→您」；truth／dsl 已經用「您」，不必動。
- **影響面與執行結果**：已在本次 `ui/index.html` 完成，見下方「靜態雛形輸出規劃」與回報中的替換統計。

## 畫面與流程

> 原型是**單檔 SPA**（React 元件樹＋內部 state 切換畫面，不是多個 `.html` 檔），因此「畫面」在這裡指 App 內的邏輯畫面／Tab／Sheet，不是獨立檔案。下列畫面清單承接 coverage 報告 §1 的盤點，补齐每頁的目的、進入條件、主要操作與流轉——細節與互動流程見 coverage 報告 §1.2–§1.5，此處不重複列到元素層級。

### 1. 首頁（今日）

- 對應雛形區塊：`ui/index.html` 內 `home` 畫面 state（房務視角）／`engHome`（工務視角）
- 主要目的：讓員工一進 App 就看到今日進度、下一間該做什麼、進行中的單要不要繼續。
- 進入條件：登入成功，或從其他分頁切回首頁 Tab。
- 主要操作：查看進度環、點「繼續處理」回到進行中的單、點「開始打掃」開工下一間、點任務列表項目進任務頁。
- 成功流轉：點任務卡或「開始」→ 任務頁；全部做完 → 空狀態卡＋「去待認領」。
- 失敗回饋：已有進行中單時再開另一間 → Alert「一次處理一間」，不離開首頁。

### 2. 待認領（pool）

- 對應雛形區塊：`pool` 畫面 state（Tab「待認領」）
- 主要目的：讓員工在沒有被指派任務時，自己挑一單來做。
- 進入條件：點 Tab bar「待認領」。
- 主要操作：點分類磚篩選（全部／備品／打掃／其他）、點「認領這單」。
- 成功流轉：認領成功 → 導向任務頁。
- 失敗回饋：撞單（單已被別人認領）→ Alert「這單已被{人}認領」，留在待認領列表並移除該單；分類下沒有單 → 空狀態卡。

### 3. 任務頁（詳情）

- 對應雛形區塊：`task` 畫面 state
- 主要目的：員工在這裡完成一間房（或一張工務單）從開始到結束的所有操作。
- 進入條件：從首頁任務卡、待認領認領成功、通知點開、或工務單詳情返回。
- 主要操作：看交辦 callout、勾 SOP 項或「跳過」、點「查一下」、點主按鈕（開始／完成／延後／中斷／恢復處理）、點報修圖示開報修面板。
- 成功流轉：完成 → 完成慶祝頁（打掃類待查房或免查房）／回首頁（備品類送達）。
- 失敗回饋：查房退回時狀態列顯示合併退回資訊並重置計時與 SOP 勾記；缺照片等工務單相關失敗見第 6 項。

### 4. 完成慶祝

- 對應雛形區塊：`celebrate` 畫面 state
- 主要目的：給員工明確的「這間做完了」回饋與下一步指引。
- 進入條件：任務在任務頁被標記完成。
- 主要操作：點「回到首頁」。
- 成功流轉：回首頁；若還有下一間，首頁直接顯示下一間卡。
- 失敗回饋：離線完成時顯示「已離線暫存，連線後自動同步」提示，不當作失敗，但要讓員工知道還沒真正送出。

### 5. 延後／中斷面板

- 對應雛形區塊：任務頁彈出的 `holdSheet`
- 主要目的：讓員工說明暫停原因，系統才能把原因呈現給交接的人或主管。
- 進入條件：任務頁點「延後」或「中斷」。
- 主要操作：選預設原因（延後：請勿打擾、住客還在房內、先處理別的單、其他；中斷：缺備品去拿、需要工務協助、住客回房、臨時被叫去支援、其他）；選「其他」要填 60 字說明。
- 成功流轉：確認後回任務頁，狀態變為已延後／已中斷。
- 失敗回饋：其他原因未填文字或超過 60 字 → 送出鈕禁用／即時字數提示。

### 6. 報修面板（工務單表單）

- 對應雛形區塊：任務頁彈出的 `repairSheet`
- 主要目的：讓員工開一張工務單並附上照片證據。
- 進入條件：任務頁點報修圖示，或非任務情境下的開工單 FAB（工務視角）。
- 主要操作：選問題類別、填狀況說明（選填）、看急件判定卡、拍照或選相簿（1–3 張）、點送出。
- 成功流轉：送出成功 → 回任務頁或導向工務單詳情，狀態列顯示「已送出」相關文案。
- 失敗回饋：同房同類別未結案 → 重複提示＋「補充照片到這張單」；沒照片 → 送出鈕禁用＋欄位提示；第 4 張 → 加入按鈕消失；某張上傳失敗 → 該張顯示「重試」，其餘不受影響；離線 → 存成待送出，不視為失敗。

### 7. 工務單詳情

- 對應雛形區塊：`ticket` 畫面 state
- 主要目的：讓開單人（房務）追蹤工務單目前進度，必要時補照片或撤回。
- 進入條件：從任務頁、通知、或「我的」進入。
- 主要操作：看狀態摘要卡與進度直列、補照片、撤回（限認領前）。
- 成功流轉：工務完修 → 狀態摘要卡更新為「已修好」，回原任務的狀態列提示可恢復處理。
- 失敗回饋：已被認領後嘗試撤回 → 操作入口直接不可用（`already_claimed` 語意在畫面上以隱藏撤回按鈕呈現，不是先點了才報錯）。

### 8. 查一下面板

- 對應雛形區塊：任務頁彈出的 `askSheet`
- 主要目的：員工在房內遇到不確定的事，先查房間記錄或工務記錄，查不到才麻煩主管。
- 進入條件：任務頁點「查一下」浮動按鈕。
- 主要操作：點推薦問題、看出處卡、點「有幫助／沒幫助」、查不到時點「問主管」。
- 成功流轉：有答案 → 顯示回答＋出處卡；問主管送出 → Toast「已傳給主管，回覆會用推播通知您」。
- 失敗回饋：查不到 → 明說「查不到 {房號} 的相關記錄」＋「系統不會用猜的回答」，不顯示空答案當有答案。

### 9. 通知（通知中心）

- 對應雛形區塊：`notifications` 畫面 state（Tab「通知」）
- 主要目的：員工漏看系統推播時，還能回頭找到完整紀錄並直接跳轉處理。
- 進入條件：點 Tab bar「通知」，或系統推播橫幅點開。
- 主要操作：點通知項目跳轉對應任務頁／工務單／待認領／分頁；點「全部標為已讀」。
- 成功流轉：點開後導向對應畫面，且該通知藍點消失。
- 失敗回饋：（無特別失敗情境，列表為空時顯示空狀態）。

### 10. 我的（含交班單、其他子頁）

- 對應雛形區塊：`me` 畫面 state 及其子頁（`handoverSheet`、通知設定、文字大小、語言、個人資料、變更密碼、遺失物）
- 主要目的：帳號相關操作與非當班即時任務的事務（交班單簽收、遺失物登記、顯示與通知偏好）。
- 進入條件：點 Tab bar「我的」。
- 主要操作：點工作磚進交班單／遺失物；點設定項進各子頁；登出。
- 成功流轉：交班單簽收後顯示「已簽收 HH:mm」；遺失物登記成功進入「我登記的」列表。
- 失敗回饋：變更密碼規則不符即時提示；連錯 5 次鎖定 15 分；離線或有進行中的單時登出會被攔（Alert 說明原因）。

### 11. 登入

- 對應雛形區塊：`login` 畫面 state
- 主要目的：員工取得身分進入 App，共用手機與個人手機兩種情境都要能登入。
- 進入條件：App 啟動且尚未登入，或登出後。
- 主要操作：記住帳號情境只需輸密碼；共用手機情境輸員工編號＋密碼；切換語言。
- 成功流轉：登入成功 → 首頁。
- 失敗回饋：「員工編號或密碼不正確」＋剩餘嘗試次數；連錯 5 次鎖定；臨時密碼強制先設新密碼。

### 12. 系統層（跨畫面元件）

- 對應雛形區塊：離線列、即時連線異常列、系統推播橫幅、iOS Alert、即時動態（Live Activity）、照片檢視器、模擬相機
- 主要目的：讓「連線不穩」「有新推播」「拍照證據」這些跨畫面的狀態有一致的呈現方式，不需要每個畫面各自處理。
- 進入條件：依各自觸發條件（離線時、推播送達時、連線異常時、開相機時）。
- 主要操作：離線列顯示「N 筆待同步」；系統推播橫幅點開導頁；相機取景、拍照、浮水印蓋章。
- 成功流轉：恢復連線後離線佇列自動送出；拍照完成後回到報修面板看到新照片。
- 失敗回饋：相機權限拒絕 → 顯示權限提示並導向設定；上傳失敗見第 6 項。

### 13. 工務視角（同一 App，部門切換）

- 對應雛形區塊：`engHome`、`engPool`、`ticket`（工務視角）、`pauseSheet`（工務）、`completeSheet`（工務）、開工單 FAB
- 主要目的：工務人員從待認領的來源分流（急件／住客／櫃檯／房務報修）接單、維修、完修回報；首頁看急件與今日保養。
- 進入條件：以工務身分登入，或房務／工務部門切換（原型情境）。
- 主要操作：認領工務單、暫停（含「放回待認領」）、完修回報（已修好／暫時處理／無法修復 OOO）、主動開工單。
- 成功流轉：完修 → 回報成功，原任務（若由房務報修轉來）狀態列同步更新。
- 失敗回饋：認領撞單 → 同待認領撞單語意；完修缺照片 → 送出鈕禁用。

## 互動與假資料原則

- 假資料策略：沿用原型既有的 seed 資料（房號、人名、工務單號、交班單內容等）與前端模擬邏輯（`demo()`、`nextTask()`、`chip()` 等），不重新設計假資料集合。
- 互動原則：`ui/index.html` 中所有按鈕、Tab 切換、Sheet 開合、表單輸入與狀態切換都維持原型原本的可操作性；本次只做文案「你→您」替換，不新增或刪減互動邏輯。
- 內容原則：畫面只放產品真的會顯示給使用者的內容；「情境模擬」操作面板本就是原型自帶的 review 工具區塊，保留，但不得因為這次編輯而新增任何額外的分析說明文字進去。

## 狀態與資訊揭露

- 使用者可見資訊：進度環與剩餘工時、任務狀態 chip、交辦內容與已讀視覺、查房退回資訊、工務單狀態與照片、查一下回答與出處、通知列表、我的各項設定。
- 必須隱藏資訊：查一下不得帶出住客身分（對齊 `kb` 模組 PII 邊界）；急件判定的規則引擎內部邏輯只顯示「依飯店設定規則」與命中規則名，不顯示規則引擎實作細節。
- 主要 UI 狀態：待開始／進行中／已延後／已中斷／待查房或已送達／查房通過／完成·免查房／已取消（房務任務）；等主管審核／待認領／待開始／維修中／已暫停／已完修（工務單，用語待 /dsl-refine 依裁決調整）；離線／連線異常（跨畫面）。
- 角色或權限差異：房務與工務視角共用同一套畫面框架但待認領分類、任務內容、工務單欄位不同；沒有主管視角，主管動作一律經「情境模擬」間接呈現其結果。

## 驗證與錯誤回饋

- 輸入驗證：延後／中斷「其他原因」60 字上限即時提示；變更密碼規則即時檢查；報修「狀況說明」60 字選填上限。
- 狀態衝突處理：一次一間（已有進行中單時開新單 → Alert 並保留原狀）；撞單（認領失敗 → Alert 並從列表移除）；工務單已認領後不可撤回（撤回入口直接隱藏，不是先允許點擊再報錯）。
- 使用者可理解錯誤訊息：沒照片不能送出、第 4 張加不進去、同房同類別未結案、查不到記錄、員工編號或密碼不正確——均沿用原型既有文案，不在本次改動（唯一改動是「你→您」）。

## accessibility id 約定

### 命名規則

- 採 **dot 分段＋kebab-case**：`{畫面}.{區塊}.{元素}[--{修飾}]`，例如 `task.handover.unread-dot`、`pool.card.status-tag--unaccepted-manager`。
- 畫面層級用簡稱（`home`、`pool`、`task`、`celebrate`、`hold`、`repair`、`ticket`、`ask`、`notification`、`me`、`login`、`engHome`、`engPool`），與原型內部 state 名稱對齊，方便實作時互查。
- 重複元素（列表項）在 id 後加房號／單號等識別值作為執行期變數，例如 `pool.card.{roomNo}.status-tag`；Appium 定位時以此做動態匹配，兩平台共用同一組 id（`accessibilityIdentifier` / `contentDescription`）。
- 狀態類元素（chip、badge、dot）用 `--state` 修飾而不是另開新 id，讓同一元素在不同狀態下仍可用同一 id 定位、只讀取其文字或狀態屬性斷言。

## 「純視覺不進 truth」清單

以下屬於視覺呈現細節，`/dsl-refine` 補規格、App 實作與測試驗收都不應依賴它們：

- 品牌色票、陰影高度（M3 elevation 1–5）、圓角半徑等 design token 的具體數值。
- 進行中脈動點、按鈕按壓態、頁面轉場等動畫效果。
- 完成慶祝頁的彩帶／慶祝動效。
- 即時動態（Live Activity）動態島精簡／展開／最小三種呈現的版面排法與縮放。
- iOS 18 vs iOS 26（Liquid Glass）的 Tab bar／導覽列／按鈕視覺差異（原型供人對照用，App 只會照拍板版本實作一種）。
- 文字大小滑桿的七段具體 px／行高數值。
- 觸覺回饋（原型本身就說明網頁無法真的震動，只是示意）。
- 「情境模擬」操作面板整體（視角切換、實機載體、iOS 版本選項說明文字）——見上方「介面範圍」已明確排除。
- 空狀態插圖所用的系統圖示名稱（如 `tray`、`checkmark.circle`）。

## 靜態雛形輸出規劃

- 多頁入口：本 increment 的原型是**單檔 SPA**，不拆分成多個 `.html`。依 Rule 1（多頁雛形固定以 `ui/index.html` 作為入口）精神，`ui/index.html` 本身就是唯一入口，也是完整產品——所有畫面透過內部 React state 切換，不是另外建立 `pool.html`、`task.html` 等檔案。
- 預計輸出檔案：`ui/index.html`（以 `ui/prototype/Main.dc.html` 為基底）；執行期依賴 `ui/prototype/support.js`、`ui/prototype/vendor/react.js`、`ui/prototype/vendor/react-dom.js`——這三個 runtime 檔案**不重複拷貝**，`index.html` 的 `<script>` 直接引用 `prototype/` 下既有檔案。
- 換頁原則：畫面切換一律走原型既有的 state 切換機制，不新增跨檔案導頁。
- Review 目標：讓 reviewer 不看 Markdown 也能直接在瀏覽器點擊、切換視角、跑完整個情境模擬流程，並確認使用者可見文案已全面「您」。
- 本機開啟方式：`ui/index.html` 用到外部 `<script src>`，部分瀏覽器在 `file://` 下會擋這些請求；需在 `specs/plans/001-staff-app-increment/ui/` 目錄下起一個本機 HTTP server（例如 `python3 -m http.server`）再開啟，不能直接雙擊檔案。
- `ui/prototype/Main.dc.html` 定位：原始匯出檔，**之後不再維護**。任何文案或行為調整都改 `ui/index.html`，不回頭動 `Main.dc.html`。

## 前端實作切分建議

- 頁面／容器切分：依「畫面與流程」13 個邏輯畫面切分 App 端的 View／Screen，對齊原型既有的 state 名稱，減少實作與原型比對的轉譯成本。
- 共用元件或區塊：任務狀態 chip、池內單卡、工務單狀態摘要卡、照片上傳格、交辦 callout、系統推播橫幅、離線列。
- 對後端契約的依賴：`GET /me/today`、`GET /pool`、`GET /tasks/{id}`（`TaskDetail`）、工務單 7 個 path、`roomMemoryAsk` 與查一下推薦／回饋/問主管端點、推播 `PushPayload`——詳細欄位對照見 `specs/truth/contracts/**`（Wave 1 已定案），App 端實作不得自創欄位。
- 驗收重點：首頁→待認領→任務頁→完成的主流程必須連續；工務單從報修到完修的房務端全程可追蹤；查一下、交辦、推播去處三者的 Appium 驗收要能用上方 accessibility id 表直接定位，不依賴文字或座標比對。

## 剩餘風險與下一步

- **優先補規格（建議納入本 increment）**：coverage 報告 §4 的第 1、2、5、6 項——任務頁核心互動（步驟條、SOP、計時、完成慶祝）、延後／中斷原因面板、離線模式整體規則、工務單生命週期（房務端）。這四項直接支撐現有 9 支 feature 的使用者流程，且本次「畫面↔feature 歸屬矩陣」已標出對應畫面，可直接作為 `/dsl-refine` 的切片依據。
- **四筆裁決已落地的改動方向**：裁決 1–3 需要 `/dsl-refine` 動手修 truth（待接池用語、逾時升級模型、急件判定權），裁決 4 已在本次 `ui/index.html` 完成。
- **未經使用者明確拍板、本次用「原則外推」給方向的 10 筆用語落差**（§5 表中 #4–6、#8–14）：方向是基於裁決 1–3 的精神推論，**不是使用者直接拍板**，`/dsl-refine` 執行前建議再次確認，尤其是：
  - #4 到期（`due_at`）概念本身去留——裁決 2 只明確放棄升級橫幅／徽章，沒有明講 `due_at` 顯示要不要保留。
