## 視覺方向

- 風格來源：沿用 002 雛形 `specs/plans/002-celebrate-and-resume/ui/celebrate.css` 的設計 token（品牌色 `#0C7680`、品牌淺底 `#C8E8ED`、琥珀警示 `#944B00`、分組背景 `#F2F2F7`、390 乘 844 手機外框），以及 App 既有的房務首頁任務卡、待認領單卡、工務單詳情四步步驟條。設計原型 `Claude Design/Main.dc.html` 沒有主管的 App 畫面，主管首頁、三類清單與查房畫面由本檔定版面
- 本次風格結論：主管首頁是「三格數字在最上面、名下的單在下面」的一頁，不是儀表板。三格是三個可點的大磚，數字是畫面上最大的字；清單每一列以房號（或單號）當主角，右側一欄固定放「開始等的時間」，跨日的列在時間前面多一個日期。查房畫面是一張逐項判定的清單，每一項一組「通過 / 不通過」兩段切換，送出鈕在底部固定列，判完才亮。工務單詳情沿用工務端既有版面（滿版標題、四步步驟條、一條狀態列、資訊卡），只把底部動作列換成主管的動作
- 視覺重點：三格數字的大小與顏色（待查房品牌色、待審核琥珀色、待驗收品牌深色）讓主管進 App 不點任何東西就讀完三個數字（NFR-001）；清單列的右欄時間用等寬數字對齊，跨日那一列的日期用琥珀色，讓「昨天就在等」一眼看出（SC-004）；查房畫面每一項判定後整列變色（通過淡綠、不通過淡紅），沒判的保持白底，主管掃一眼就知道還剩哪幾項
- 審美原則：每個畫面只有一顆實心主按鈕。查房送出、驗收、核准是實心；退回是描邊；「回到清單」是文字按鈕。畫面上只放主管真的會看到的字，分析備註、欄位名、實作註記全部留在本檔

## 介面分析

### 介面 1：進 App 的首頁分流與推播開首頁

**問題**。App 目前三個入口各自寫「看 `dept` 是不是 `engineering`」：`login_screen.dart` 第 122 到 125 行、`force_password_change_screen.dart` 第 138 到 140 行、`push_gateway.dart` 的 `case 'home'` 第 194 到 196 行（這一處連部門都不看，一律開房務外殼，所以工務員工點開去處為首頁的推播會被導進房務首頁）。主管帳號 `dept` 為空，三處都把他當房務。

**結論**。三個入口共用同一條判定，放在 `core/` 一個純函式（建議 `core/landing.dart` 的 `landingShellFor(session)`），輸入是登入 session 的 `role` 與 `dept`，輸出是要開哪個外殼：

| 判定順序 | 條件 | 去處 |
| --- | --- | --- |
| 1 | `role` 等於 `manager` | 主管外殼（不看 `dept`，含被設了部門的主管） |
| 2 | `dept` 等於 `engineering` | 工務外殼 |
| 3 | 其餘 | 房務外殼 |

先看角色再看部門，是因為角色是「這個人是誰」、部門是「這個人幫哪一邊做事」，主管即使掛了部門也還是主管（spec 邊界情況「主管帳號帶有部門時仍依角色進主管首頁」）。`push_gateway.dart` 的 `case 'home'` 改呼叫同一個函式，工務員工的既有錯誤順帶修掉。

**主管外殼**。沿用 `main_shell.dart` 的 `_MainShell(homeTab, poolTab)` 模式，新增第三個 `ManagerShell`，`homeTab` 是主管首頁、`poolTab` 是主管待認領（介面 5），通知與我的兩個分頁不動（FR-002）。分頁列的「待認領」徽章讀的是 `MyToday.poolBadgeCount`，契約寫的口徑是「呼叫者現在搶得到的待認領單數」，主管搶不到任何單，這個值對主管應該是 0 或不顯示，要請 Wave 2 在契約寫明主管呼叫時的值。

**推播開工務單詳情也要跟著改**。`push_gateway.dart` 的 `case 'ticket'` 目前也是看 `dept` 決定開房務版還是工務版的詳情，主管（`dept` 為空）會被開成房務版，看不到主管動作。介面 4 定義主管版詳情後，這一處同樣改成先看角色。

### 介面 2：主管首頁與三類清單

**首頁版面（由上而下）**。導覽列標題「主管首頁」；三格磚一排（待查房、待審核、待驗收），每格顯示類別名與數字，點磚進該類清單；區段標題「我名下的單」；任務卡列表沿用房務首頁的 `_TaskRow`（建議抽到 `core/widgets/` 共用）；名下沒單時這一區顯示一句說明「今天沒有名下的單」加一行副文「有需要時可以到待認領看看兩個部門的單」。不帶房務首頁的問候列、進度環與「下一間」卡（spec 假設第 1 條）。

**三格與清單的資料來源**。三格數字與三份清單依同一套判定公式（spec「三類待辦的判定公式」）。NFR-001 要求進 App 就看到三個數字，所以首頁載入只能有一次往返拿到三個數字；清單內容在點磚時再取或一起取都可以，但三格數字必須和各清單列數同源（FR-004）。這是 Wave 2 `/api-plan` 決定端點形狀的第一個輸入：三個數字要在同一個回應裡。

**清單每一列要顯示什麼**。每一列的目標是讓主管不點開就認得這是哪一張單、在等多久。欄位釘如下，作為 Wave 2 查詢回應的形狀需求（欄位名由 `/api-plan` 定，這裡只釘語意）：

| 欄位語意 | 待查房 | 待審核 | 待驗收 | 畫面上的位置 |
| --- | --- | --- | --- | --- |
| 任務識別（開詳情用） | 任務 id | 任務 id 與工務單 id | 任務 id 與工務單 id | 不顯示 |
| 房號；公共區域時是地點說明 | 必要 | 必要 | 必要（定期保養可能是公共區域，例如「5 樓製冰機」） | 左側主角，大字 |
| 工務單號 | 不適用 | 必要 | 必要 | 房號前面的小字（FR-028） |
| 內容 | 任務標題（退房打掃、續住整理） | 報修說明 | 報修說明；定期保養時是保養說明 | 第二行 |
| 原清房者顯示名 | 必要（主管要知道退回會回到誰名下；也用來理解為什麼自己清的房不在這裡） | 不適用 | 不適用 | 第三行次要字 |
| 報修人顯示名與類別 | 不適用 | 必要（類別全寫：冷氣、水電、家具設備、門鎖、其他） | 選用 | 第三行次要字 |
| 完修結果三選一（已修好、暫時處理、無法修復） | 不適用 | 不適用 | 必要（FR-020 明說三種都要列，主管得看出哪些是無法修復） | 第三行次要字，無法修復用琥珀色 |
| 來源是不是定期保養 | 不適用 | 不適用 | 必要（spec 已知風險二，保養單要看得出來） | 第三行一個「定期保養」標籤 |
| 完修人顯示名 | 不適用 | 不適用 | 選用 | 第三行次要字 |
| 開始等主管的時間 | 最近一次完成時間 | 最近一次進入等主管審核的時間 | 完修時間 | 右欄，今天只顯示 `HH:mm`，不是今天顯示 `MM/DD HH:mm` |
| 重做次數大於 0 | 選用（可標「重做後再查」） | 不適用 | 不適用 | 第三行一個標籤 |

「今天」以系統時區認定日界線（目前全租戶同一時區），由後端在回應裡直接給「是不是今天」或給帶時區的時間、App 以該時區比對，二選一交 Wave 2；App 不拿手機時區判斷。

**排序**。清單依「開始等主管的時間」由舊到新，由後端排好直接呈現，App 不重排（與 `todayTasks` 的契約同一套做法）。

**空狀態**。某一類為 0 時磚照常顯示 0，點進去的清單是一句說明，三類各一句：「目前沒有等你查的房」「目前沒有等你審核的報修」「目前沒有等你驗收的工務單」，下面一行「有新的單進來時會出現在這裡」。不是空白畫面（FR-005）。

**刷新時機**。主管在查房結果頁、工務單詳情完成一次動作回到清單時，清單重取、該單消失，首頁三格同步減一（FR-029）；收到 409 時同樣重取（FR-030）。下拉重新整理沿用員工首頁。本輪不加任何「有單在等主管」的即時推送（spec 假設第 3 條）。

**「我名下的單」沿用房務任務列的既有限制**。資料走既有的 `getMyToday` 的 `todayTasks`，契約（`員工工作台.yaml` 第 36 到 54 行）已寫明「屬於今天」依 `work_date` 有無分兩把尺，後端 `TaskExecutionService.belongsToToday` 已落地，缺口 #39 在 001 回交時已結案。但要揭露給 Wave 2 兩件事：① `getMyToday` 同時算打掃進度、查房通過數、`poolBadgeCount` 等房務口徑，主管呼叫時這些值的語意要在契約寫明（或寫明主管首頁只讀 `todayTasks`）；② 主管做完自己名下的單後，那張單會進別的主管的待查房，不會進自己的（FR-011），所以主管首頁三格不會因為自己完成一張單而變動，這是正確行為，要寫進 ios-app feature 免得被當 bug。

### 介面 3：查房畫面

**版面**。導覽列標題「查房 · 301」，返回鍵回待查房清單。頂部一張摘要卡：房號大字、任務標題、原清房者與完成時間。下面是查房項目清單，每一項一列：項目名在左、右側一組兩段切換「通過 / 不通過」。還沒判的列白底、切換兩段都未選；判通過整列淡綠底、判不通過整列淡紅底。底部固定動作列只有一顆實心「送出查房結果」，上方一行小字顯示進度「已判 4 / 5 項」；全部判完前鈕是禁用態（不是按了才報錯，與 `送出鈕為 "{按鈕狀態}"` 句型同一套語意）。沒有備註欄、沒有照片（FR-010）。

**沒有任何啟用項目**。項目清單位置顯示一句「這家飯店目前沒有設定查房項目，送出即視為全部通過」，送出鈕直接可按（spec 邊界情況第 4 條）。

**查房項目的來源**。飯店目前啟用、`applies_to` 為 `inspection` 的 `sop_items`，既有端點 `listSopItems`（`contracts/groups/知識與通知/SOP與查房項目.yaml`）。進畫面時取一次，被拒時重取。

**送出與結果**。送出成功後換到結果頁（介面 3 的第二個畫面），三種說法：
- 全部通過：「301 查房通過，已結案」，副文「小美會收到通知」
- 任一項不通過、原清房者還在班：「301 退回重做」，副文「回到小美名下，不合格：浴室無水痕」
- 任一項不通過、原清房者已下班或請假：「301 退回重做」，副文「小美已下班，這張單回到了房務待認領」

結果頁只有一顆主按鈕「回到待查房」。退回時列出的不合格項目就是退回原因（FR-009、FR-010）。「回到原清房者名下」還是「回到待認領」由後端回應告訴 App，App 不自己判斷班表。

**送出被拒要分辨兩種拒絕（給 Wave 2 的需求，不預設錯誤碼）**。查房送出會踩到兩種互斥的拒絕，畫面的反應完全不同，所以 App 必須能用回應裡的機器可讀訊號（不是靠 HTTP 狀態碼或訊息文字）分辨：

| 拒絕 | 畫面反應 | 需要後端給什麼 |
| --- | --- | --- |
| 單已不是待查房（另一位主管先送出、或單被改派、作廢） | 彈出「這張單已被處理」，按「知道了」回到待查房清單，清單重取 | 一個明確的「狀態衝突」訊號，與工務單四個動作的 409 同一類語意 |
| 主管判定的項目集合與飯店現行集合不符（少項或多項，含送出前剛新增或停用了項目） | 留在查房畫面，頂部出現一行「查房項目剛更新，請重新判定」，項目清單換成現行集合，所有判定清空，送出鈕回到禁用（spec 邊界情況第 3 條；acceptance「王主管判完五項，飯店在他送出前加了第六項」） | 一個明確的「項目集合不符」訊號；若回應能直接帶回現行項目集合，App 可少一次往返，列為偏好不是必要 |

目前契約 `createInspections` 只寫缺項 422、沒有定義多項與狀態衝突，也沒有 `Idempotency-Key`，body 還要 App 自帶 `tenantId`、`inspectorId` 與 `result`（spec「交給 /api-plan 的備忘」）。畫面這邊的需求是：App 只送任務 id 與 `[{項目鍵, 通過與否}]` 的陣列，通過或退回由後端依項目算，重送帶同一把 `Idempotency-Key`。

**離線**。進查房畫面可以（項目可能是快取），但送出鈕按下時先檢查連線，離線就彈出與員工端同一句「目前離線，只能完成進行中的單」，不送請求、不入離線佇列（FR-031）。

### 介面 4：工務單詳情的主管動作

**第三種版面還是疊加**。App 現在有兩種工務單詳情：房務版（`ticket_detail_housekeeping.dart`，狀態摘要卡、補照片、撤回、補資料再送出）與工務版（`ticket_detail_engineering.dart`，四步步驟條、一條狀態列、資訊卡、認領 / 開始 / 完修動作）。主管要看的東西是兩版的並集：報修內容（照片、類別、說明、報修人）在兩版都有，完修回報（完修照片、處理結果、處理說明）只有工務版有，步驟條只有工務版有。主管要做的事兩版都沒有。

結論是**不做第三種版面，在工務版上疊加**：新增 `TicketView.manager`，內容區沿用工務版的滿版標題、四步步驟條、狀態列與資訊卡，差別只有底部動作列：

| 工務單狀態 | 狀態列文字 | 主管動作列 |
| --- | --- | --- |
| `pending_review`（等主管審核） | 「等主管審核 · 阿芳 11/10 09:12 送出」 | 描邊「退回」＋實心「核准」 |
| `done` 且尚未驗收 | 「已完修 · 等主管驗收」，接完修結果 | 實心「驗收」 |
| `rejected`（主管未核准） | 「主管未核准 · 退回原因：…」 | 無 |
| `pool`、`accepted`、`doing`、`cancelled` | 各自既有文字 | 無 |
| `done` 且已驗收 | 「已驗收 · 王主管」 | 無 |

選工務版當底不選房務版，是因為步驟條回答「這張單到哪一步了」，正是主管審核與驗收時要看的；房務版的補照片、撤回、補資料再送出都是報修人的動作，主管不該看到。主管從待審核、待驗收、推播、通知中心任何入口開同一張單，看到的都是這一版（FR-032）。

**工務單 dsl 的裁決要翻案**。`specs/truth/features/ios-app/工務單/dsl.md` 第 9 行寫「主管審核與驗收本身都是主管端（後台／情境模擬面板）的動作，不是這個模組要承接的 App 互動」。本輪改成：主管在 App 的工務單詳情核准、退回、驗收；房務端看到的「等主管審核」「主管未核准」與工務端看到的「已驗收 · {主管}」呈現不變。這是 `/dsl-refine` 的 MODIFY 項。

**核准**。按實心「核准」直接送出，不另開確認（核准是把單放進工務待認領，可逆性高，工務接單前主管還能從別處處理）。成功後回到待審核清單，該單消失，首頁待審核減一。

**退回**。按描邊「退回」升起底部面板：標題「退回給 阿芳」，一個多行文字框，佔位字「寫下退回原因，報修人會看到這段話」，底部實心「送出退回」。文字框去掉前後空白後為空時送出鈕禁用（FR-018）。成功後同核准。成功後系統推播報修人，帶退回原因，點開進該工務單詳情（FR-019）。

**驗收**。按實心「驗收」直接送出，不開面板、不填任何東西（FR-021）。畫面上沒有「驗收不通過」「退回」或備註欄（FR-023）。成功後回到待驗收清單，該單消失，首頁待驗收減一。

**已被處理（409）**。四個動作任一收到狀態衝突時，彈出「這張單已被處理」，副文「可能是另一位主管剛處理過，或報修人撤回了這張單」，按「知道了」回到來源清單並重取（FR-030）。查房的狀態衝突也走同一個對話框。

**離線**。四個動作按下時先檢查連線，離線就彈出與員工端同一句「目前離線，只能完成進行中的單」，不送請求、不入離線佇列（FR-031）。`features/ios-app/系統層/離線模式與連線異常.feature` 的 Rule「離線時開始、認領、延後、開新工務單一律被擋」要擴成主管也在場景大綱裡，例子多四列：送出查房結果、核准工務單、退回工務單、驗收工務單。

### 介面 5：待認領切換部門只看不搶

**版面**。沿用房務待認領的版面（標題「待認領」、連線狀態列、分類磚、單卡列表），在標題下方多一個兩段切換「房務 / 工務」。切到房務時，分類磚與單卡與 `PoolScreen` 一致（全部、備品、打掃、其他）；切到工務時與 `EngPoolScreen` 一致（全部、急件、房務報修、櫃檯）。差別只有一個：單卡底部沒有「認領這單」鈕（FR-025）。既有空狀態「這個部門目前沒有在職員工可以搶單」不動。

**記住部門**。選擇只存在這台手機（`SharedPreferences` 一把鍵，值 `housekeeping` 或 `engineering`，沒有紀錄視為 `housekeeping`）；切換時寫入，進畫面時讀出（FR-024）。這不是後端資料，不進契約與資料模型。

**查詢**。兩個池都走既有 `listDeptPool` 並明帶 `dept`（主管帳號沒有部門，省略會 422 `dept_required`；`pool_screen.dart` 第 75 到 83 行已處理房務這一半），`PushTarget.dept` 在 `kind` 為 `pool` 時已必填，契約不動。

**實作切分**。不複製兩份畫面。建議把 `PoolScreen` 與 `EngPoolScreen` 的列表與單卡抽成「給定部門與是否可認領」的元件，主管待認領是一個外層容器：持有目前部門、畫切換、把 `canClaim: false` 往下傳。單卡 id 沿用員工端（`pool.card.{roomNo}`、`engPool.item.{單號}`），只是沒有 `.claim-button` 節點。

**推播**。`push_gateway.dart` 的 `case 'pool'` 目前帶 `highlight` 切到待認領分頁；主管要多做一步：先把 `PushTarget.dept` 寫入本機的部門選擇，再切分頁並標亮（FR-026）。工務池的標亮以單號或房號比對，沿用 `EngPoolScreen` 既有做法。推播文案沿用 truth 句型「{房號} {任務名} 已等 {N} 分，還沒人接」；雛形的推播入口只用去處與標亮。

## 畫面與流程

### 1. `主管首頁`

- 對應雛形檔案：`ui/index.html`
- 主要目的：雛形入口，也是產品的主管首頁。三格數字一眼讀完，往下是名下的單
- 進入條件：角色為 `manager` 的帳號從登入、強制改密完成、點開去處為首頁的推播任一入口進 App
- 主要操作：點三格任一格進該類清單；點名下任務卡進任務頁（雛形中以 403 示意，不另做任務頁）；底部分頁切到待認領
- 成功流轉：待查房格 → `ui/queue.html?kind=inspection`；待審核格 → `ui/queue.html?kind=review`；待驗收格 → `ui/queue.html?kind=verify`；待認領分頁 → `ui/pool.html`
- 失敗回饋：三格載入失敗時磚上顯示「--」與一行「載入失敗，下拉重試」；名下沒單時顯示「今天沒有名下的單」（雛形以 `?mine=0` 呈現）

### 2. `三類清單`

- 對應雛形檔案：`ui/queue.html?kind=inspection`、`?kind=review`、`?kind=verify`（同一個畫面三種類別，與實作的單一清單元件對應）
- 主要目的：讓主管不點開就認得每一張單、在等多久，最舊的在最前面
- 進入條件：從首頁三格點入
- 主要操作：點一列進該單的動作畫面
- 成功流轉：待查房列 → `ui/inspect.html?room=301`；待審核列、待驗收列 → `ui/ticket.html?no=W-0201`
- 失敗回饋：該類為 0 時顯示一句說明與副文，不是空白；處理過的單從清單消失並讓首頁格數減一（雛形以 `sessionStorage` 記住已處理的單，關掉瀏覽器分頁即還原）

### 3. `查房畫面`

- 對應雛形檔案：`ui/inspect.html?room=301`
- 主要目的：逐項判定、全部判完才能送出
- 進入條件：從待查房清單點一列
- 主要操作：每一項切「通過 / 不通過」；判完按「送出查房結果」
- 成功流轉：全部通過 → `ui/inspect-result.html?room=301&outcome=passed`；任一項不通過 → `?outcome=returned`（原清房者在班）或 `?outcome=pool`（原清房者已下班）
- 失敗回饋：項目集合不符時留在本頁、頂部出現「查房項目剛更新，請重新判定」、項目換成現行集合、判定清空、送出鈕回到禁用（雛形中 303 這張單第一次送出會進這個狀態，重判後才送得出去）；單已不是待查房時彈出「這張單已被處理」回清單；離線時彈出「目前離線，只能完成進行中的單」（雛形以 `&offline=1` 呈現）

### 4. `查房結果`

- 對應雛形檔案：`ui/inspect-result.html?room=301&outcome=passed|returned|pool`
- 主要目的：說清楚這次是結案還是退回、退回時單去了哪裡
- 進入條件：查房送出成功
- 主要操作：實心「回到待查房」
- 成功流轉：→ `ui/queue.html?kind=inspection`，該單已不在清單上
- 失敗回饋：無

### 5. `工務單詳情（主管視角）`

- 對應雛形檔案：`ui/ticket.html?no=W-0201`（等主管審核）、`?no=W-0108`（已完修待驗收）、`?no=W-0202`、`?no=W-0112`、`?no=W-0204`、`?no=W-0109`（其他四種狀態，沒有主管動作）
- 主要目的：主管看得到報修內容與完修回報，只在兩種狀態出現主管動作
- 進入條件：從待審核、待驗收清單點一列；或從推播、通知中心開任一張工務單
- 主要操作：等主管審核時「退回」（升起原因面板）與「核准」；已完修待驗收時「驗收」
- 成功流轉：核准、退回送出、驗收成功 → 回對應清單（`ui/queue.html?kind=review` 或 `?kind=verify`），該單消失
- 失敗回饋：退回原因空白時送出鈕禁用；狀態衝突時彈出「這張單已被處理」、按「知道了」回清單（雛形中 W-0110 這張單按驗收會進這個狀態）；離線時彈出「目前離線，只能完成進行中的單」（雛形以 `&offline=1` 呈現）

### 6. `退回原因面板`

- 對應雛形檔案：`ui/ticket.html?no=W-0201` 內的底部面板，不另成一頁
- 主要目的：退回必須附原因，報修人看得到這段話
- 進入條件：在等主管審核的工務單詳情按「退回」
- 主要操作：輸入原因；「送出退回」；「取消」收回面板
- 成功流轉：→ `ui/queue.html?kind=review`
- 失敗回饋：原因去掉空白後為空時送出鈕禁用

### 7. `主管待認領`

- 對應雛形檔案：`ui/pool.html`（第一次為房務）、`ui/pool.html?dept=engineering&highlight=306`（推播帶部門與標亮）
- 主要目的：看兩個部門的池，不搶單
- 進入條件：底部分頁「待認領」；或點開去處為待認領且帶部門的推播
- 主要操作：切「房務 / 工務」；點分類磚篩選
- 成功流轉：切換後列表換成該部門的單，選擇記在這台手機（雛形以 `localStorage` 模擬），重開停在上次的部門
- 失敗回饋：部門沒有在職員工時顯示既有空狀態「這個部門目前沒有在職員工可以搶單」

## 狀態與資訊揭露

- 使用者可見資訊：三格數字、每一列的房號或單號、內容、原清房者或報修人、完修結果、開始等的時間與跨日日期、查房項目與判定、報修照片與完修照片、處理說明、退回原因、驗收人
- 必須隱藏資訊：任務與工務單的 id、狀態機內部值、錯誤碼、租戶 id、查房人 id、判定公式本身
- 主要 UI 狀態：首頁（有單、名下沒單、載入失敗）；清單（有單、空、含跨日列）；查房（未判、部分判、全判可送、項目更新重判、送出中、離線擋下、已被處理）；查房結果（結案、退回原清房者、退回待認領）；工務單詳情（等審核有動作、待驗收有動作、其他四種無動作、退回面板開啟、已被處理、離線擋下）；待認領（房務、工務、標亮、空狀態）
- 角色或權限差異：三格與三類清單只對 `manager` 出現（FR-033），房務與工務員工的首頁沒有這三格、App 裡沒有入口；待認領對主管沒有認領鈕，對員工有；工務單詳情對主管是 `TicketView.manager`，對房務與工務各是既有兩版

## 驗證與錯誤回饋

- 輸入驗證：查房每一項都判過才能送出（進度字「已判 n / 總數 項」）；退回原因去空白後非空才能送出。兩者都用禁用態表達，不是按了才報錯
- 狀態衝突處理：查房、核准、退回、驗收四個動作收到狀態衝突時統一彈「這張單已被處理」，按「知道了」回來源清單並重取；查房另有「項目集合不符」這一種拒絕，留在原畫面重新載入項目讓主管重判。兩種拒絕 App 要靠回應裡的機器可讀訊號分辨，不是靠訊息文字
- 使用者可理解錯誤訊息：離線沿用員工端「目前離線，只能完成進行中的單」；已被處理用「這張單已被處理」加一句原因提示；項目更新用「查房項目剛更新，請重新判定」。都說「現在怎麼了」與「接下來能做什麼」，不出現錯誤碼

## 靜態雛形輸出規劃

- 多頁入口：`ui/index.html` 就是主管首頁，承擔流程入口，不是連結目錄
- 預計輸出檔案：`ui/manager.css`（共用樣式與設計 token）、`ui/manager.js`（示範資料與已處理的單的記憶）、`ui/index.html`、`ui/queue.html`、`ui/inspect.html`、`ui/inspect-result.html`、`ui/ticket.html`、`ui/pool.html`
- 未另外做成頁面的狀態：①任務頁與完成畫面沿用房務員工的既有畫面，首頁名下任務卡點下去不另做；②通知與我的兩個分頁內容與員工一致，雛形分頁列上的這兩格不可點；③查房畫面「沒有任何啟用項目」是同一頁的項目清單換成一句說明，雛形以 `ui/inspect.html?room=301&items=0` 呈現；④離線與已被處理是對話框，不另成頁
- 換頁原則：只有產品本來就會換畫面時才換頁（首頁到清單、清單到查房或詳情、送出到結果頁）；判定、面板、對話框、部門切換都留在同頁
- Review 目標：讓 reviewer 不讀規格就能回答四個問題：主管進 App 第一眼看到什麼、一張待查房的單怎麼從清單走到結案或退回、一張工務單在六種狀態下主管各能按什麼、主管在待認領為什麼沒有認領鈕

- 共用元件或區塊：三格磚（可抽成 `TmsCountTile`）；清單列（房號或單號主角、兩行說明、右欄時間與跨日日期）；查房項目列（兩段切換）；狀態衝突對話框（「這張單已被處理」）；離線擋下提示沿用 `core/system_status.dart` 的 `offlineOnlyCompleteMessage`；房務首頁 `_TaskRow` 抽到 `core/widgets/` 供主管首頁共用；待認領列表與單卡抽成「給定部門、是否可認領」的元件
- 對後端契約的依賴（全部交 Wave 2 `/api-plan` 定形狀，本檔只定語意）：①主管待辦查詢，三個數字同一次往返，清單每列欄位見介面 2 的表，排序由後端定，含「是不是今天」或可依系統時區比對的時間；②`createInspections` 要能分辨「狀態衝突」與「項目集合不符」兩種拒絕、接受 `Idempotency-Key`、body 不需 App 自帶 `tenantId`、`inspectorId`、`result`；③`RepairTicket` 補完修結果三選一、完修時間、最近一次進入等主管審核的時間、來源是不是定期保養、公共區域的地點表達；④`readRepairTicket` 可查看者加主管；⑤`MyToday.poolBadgeCount` 與房務進度欄位在主管呼叫時的語意；⑥`listSopItems` 作為查房項目來源，確認回應含 `applies_to` 與啟用狀態可篩
- 驗收重點：三個入口三種角色各到正確首頁一條（含被設了部門的主管）；三格數字等於清單列數一條；跨日列標日期且排最前一條；查房未判完不能送、全通過結案、一項不過退回原清房者、原清房者下班退回待認領、項目更新重判、沒有項目直接送出各一條；六種狀態的工務單詳情主管動作對照一條；退回原因空白不能送一條；兩位主管同時處理只接受先到一條；離線四種動作擋下且不補送一條；待認領第一次房務、切換後重開停在上次、推播帶部門切到該部門並標亮、沒有認領鈕各一條
