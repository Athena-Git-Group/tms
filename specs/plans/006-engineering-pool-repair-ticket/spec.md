# 功能規格：派給工務的單一律是工務單

**功能分支**: `bugfix/main_engineering_pool_repair_ticket`

**建立日期**: 2026-11-23

**狀態**: 草稿

**輸入**: 使用者描述：「核心流程是住客掃碼開需求 → 櫃檯看到 → 櫃檯派給房務或工務 → 同仁在手機 App 認領 → 做完 → 完成。實機走過一輪：房務通，工務斷。修法選定：任務派給工務時，後端開一張工務單，讓工務的世界維持以工務單為中心，2026-11-11 的驗收裁決（任一主管驗收一次、先到先決、不通過退回重修、驗收完才結案）也適用在這些單上。不做『App 顯示沒有單號的單』那條路。另外修掉實機看到的小問題：工務待認領單卡顯示代碼 `repair`，要改成工務單的類別。」

本文的寫法：「」內是畫面或推播的原文；`code` 是資料值。

## 範圍

**這是一個違反既有 truth 的錯誤，不是新功能。** truth 早就預期櫃檯轉來的單是工務單：`specs/truth/features/ios-app/工務單/工務視角.feature` 的「工務待認領可以只看急件、房務報修或櫃檯轉入的單」與「單卡顯示來源標示」都拿來源為「櫃檯」的工務單當例子；`specs/truth/features/ios-app/推播/點開推播的去處.feature` 的「阿德點開櫃檯轉單的推播」點開的是 W-0620 這張工務單。後端卻沒有照做。

**實機量到的現象**（2026-11-23，證據在 `/Users/Caresys/.claude/jobs/bf2b4d32/tmp/e2e-chain/`）：
- 櫃檯把住客在設備報修送出的 T-0024 派給工務後，這張單在工務部門的待認領裡，但沒有工務單號（截圖 03、04、12）。
- 工務阿強（`mt1`）的工務待認領分流磚寫 7 張，列表只畫出 5 張；櫃檯轉來的那張永遠不出現，也就永遠沒有人能認領（截圖 09、10、11、12）。
- 有畫出來的工務單，房號方塊上的類別寫的是代碼 `repair`，不是「冷氣」「其他」這類中文（截圖 09）。
- 同一輪派給房務的兩張單都走完了，住客端也看到完成（截圖 13 到 30）；櫃檯看板最後只剩派給工務的那張卡住（截圖 31）。

**根因**：後端把單派給工務時只改了狀態與部門，沒有開工務單；工務 App 的待認領只畫有工務單號的單。把單的類別換成工務單類別的那一步，App 拿到的是任務類型而不是工務單類別。

**本版做**：
- 讓「屬於工務的單一定是工務單」成為系統保證：櫃檯從待派單派給工務時，同一張單就成為一張工務單。
- 櫃檯派出後五秒內復原時，工務單跟著撤掉，單的類別與急件標記回到派單前。
- 住客自己送出的需求不會繞過櫃檯直接進工務（沿用 2026-11-05 的「住客不直通工務」裁決；2026-11-23 使用者確認這條裁決蓋過 005 住客 Web 與原型裡「命中工務規則直接進工務待認領」的寫法）。
- 櫃檯 Web 待派單頁的頁尾說明跟著改，不再說「命中規則的文字會直接進部門待認領」。
- 已經卡在工務、沒有工務單的單，上線時補成工務單或退回待派單。
- 工務待認領單卡顯示工務單類別的中文。

**本版不做**：
- App 端顯示沒有工務單號的單（使用者已排除這條路）。
- 依住客原話自動判斷工務單類別：櫃檯轉來的單一律是「其他」，工務在詳情看標題就知道是什麼問題。
- 改住客端的進度階段對照表（見「新行為」）。
- 櫃檯派單時通知該部門「有新單」：今天櫃檯派給房務或工務都不發 `pool_new_request` 推播，工務只能自己看待認領（急件例外，照常發急件推播）。住客打「冷氣」原本經分類規則直接進工務時會發這則推播，故事 4 之後這條路改走櫃檯，推播跟著沒了。`specs/truth/features/ios-app/推播/點開推播的去處.feature:50` 的「櫃檯轉單 · 202 窗簾掛勾鬆脫」只是 Given 裡的假資料，後端沒有任何路徑會發。這是已知缺口，另開一題處理。
- 改工務單的驗收規則：沿用 2026-11-11 的裁決，本版只讓櫃檯轉來的單也進入這套規則。

**舉例說明用的人物與資料**：
- 櫃檯林佩君；工務阿強（`mt1`）、阿德；房務主管張主管；工務主管陳主管。
- 305 房的住客在住客頁的設備報修打了「窗簾掛勾鬆脫」，沒有命中任何分類規則，進了待派單。
- 本飯店上一張工務單是 W-0620，所以下一張是 W-0621。

## 使用者情境與測試 *(必填)*

### 使用者故事 1 - 櫃檯派給工務的單，工務接得到、做得完、主管驗收後結案 (Priority: P1)

作為櫃檯，我把住客的報修派給工務之後，希望工務馬上在 App 的待認領看到它、能認領並處理；作為主管，我希望這張單跟其他工務單一樣經過我驗收才結案；作為住客，我希望看到我的報修走到完成。

**為何為此優先級**: 這就是實機斷掉的那一段。派給工務是核心流程的一半，現在的結果是單永遠卡在工務待認領、沒人看得到。

**獨立驗證方式**: 在手動測試環境走一次：住客打字報修 → 櫃檯派給工務 → 阿強在 App 認領、開始、完成 → 陳主管驗收通過 → 住客頁顯示已完成。

**舉例說明**:

林佩君在待派單看到 305 房的「窗簾掛勾鬆脫」，按「派給工務」。這一刻 305 這張單成為工務單 W-0621：

| 項目 | 值 |
| --- | --- |
| 單號 | W-0621（與房務報修、工務自開、櫃檯代開共用同一個流水號） |
| 房號 | 305 |
| 類別 | 其他 |
| 標題 | 窗簾掛勾鬆脫（住客原話，櫃檯看到什麼工務就看到什麼） |
| 報修人 | 林佩君（按派單的人） |
| 來源標示 | 櫃檯 |
| 照片 | 0 張，不要求 |
| 急件 | 依飯店的急件規則判定，與櫃檯代開工務單相同 |

櫃檯看板與詳情上，305 這張單的單號從原本的 `T-` 單號改顯示 W-0621，與工務看到的是同一個號碼；類別改顯示修繕。

阿強打開工務待認領，分流磚寫幾張，列表就畫幾張，W-0621 在裡面，單卡房號方塊寫「其他」、來源標示「櫃檯」。阿強認領、開始、附 1 張完修照片完成 W-0621，單轉為已完修等驗收。陳主管驗收通過，W-0621 轉為已結案。

**驗收情境**:

1. **Given** 305 的「窗簾掛勾鬆脫」在待派單、下一張工務單號是 W-0621，**When** 林佩君把 305 派給工務，**Then** 305 成為工務單 W-0621，類別「其他」、報修人林佩君、來源「櫃檯」，在工務待認領裡且沒有負責人。
2. **Given** 林佩君已把 305 派給工務，**When** 林佩君用同一把防重複鍵重送一次，**Then** 305 仍只有一張工務單 W-0621，流水號沒有多跳。
3. **Given** 林佩君已把 305 派給工務，**When** 阿強打開工務待認領，**Then** 分流磚的張數等於列表畫出的張數，W-0621 在列表裡。
4. **Given** 阿強已完修 W-0621，**When** 陳主管驗收通過，**Then** W-0621 已結案，住客頁的 305「窗簾掛勾鬆脫」顯示已完成。
5. **Given** 林佩君把 306 的「想多一顆枕頭」派給房務，**When** 派單完成，**Then** 306 不是工務單，沒有用掉任何工務單號。

**功能需求（FR）**:

- **FR-001**: 系統 MUST 在櫃檯把待派單的單派給工務的同一個動作裡，讓同一張單成為一張工務單；不另外建一張新的單，住客、櫃檯、工務看的是同一張。
- **FR-002**: 系統 MUST 為這張工務單取下一個工務單號，與其他開單路徑共用同一個流水號。
- **FR-003**: 系統 MUST 把這張工務單的類別設為「其他」、報修人設為按派單的人、標題沿用這張單原本的標題，且不要求照片。
- **FR-004**: 系統 MUST 依飯店的急件規則判定這張工務單是否為急件，判定結果與櫃檯代開工務單的規則相同；判定為急件時照常發急件推播。急件推播以工務單為單位防重複：同一張單復原後再派給工務、開出新的工務單時，新單判定為急件照樣推播。
- **FR-005**: 系統 MUST 在工務待認領與工務首頁把這張工務單的來源標示為「櫃檯」，與櫃檯代開的工務單同一種來源，「櫃檯」分流磚篩得到它。
- **FR-006**: 系統 MUST 讓這張工務單照工務單的規則走完：工務完修後等主管驗收，任一位房務主管或工務主管驗收一次、先到先決，不通過退回重修，驗收通過才結案（2026-11-11 裁決）。
- **FR-007**: 系統 MUST 在同一次派單因網路逾時重送時，維持只有一張工務單、只用掉一個單號。
- **FR-008**: 系統 MUST 在單派給房務時維持現狀，不開工務單、不用掉工務單號。

### 使用者故事 2 - 派給工務後五秒內復原，工務單一起撤掉 (Priority: P2)

作為櫃檯，我按錯「派給工務」時按「復原」，希望這張單完全回到待派單的樣子，工務待認領不會留下一張沒人要的工務單。

**為何為此優先級**: 復原是既有功能；派給工務會開工務單之後，復原必須跟著收回，否則工務會看到一張已經回到櫃檯手上的單。依賴故事 1。

**獨立驗證方式**: 派給工務、五秒內復原，確認單回到待派單、工務待認領沒有它、事件紀錄保留派單與復原兩筆。

**驗收情境**:

1. **Given** 林佩君剛把 305 派給工務，305 成為 W-0621，**When** 林佩君復原 305 的派單，**Then** 305 回到待派單、還沒分部門，不再是工務單，工務待認領沒有 W-0621。
2. **Given** 林佩君派給工務後復原了 305，**When** 林佩君再把 305 派給工務，**Then** 305 成為下一個號碼的工務單 W-0622；W-0621 不再使用。
3. **Given** 305 今天有 VIP 入住，林佩君派給工務時 W-0621 判定為急件，**When** 林佩君復原，**Then** 305 不再是急件；**When** 林佩君再派給工務，**Then** W-0622 判定為急件，阿強與主管都收到 W-0622 的急件推播。

**功能需求（FR）**:

- **FR-009**: 系統 MUST 在復原一張派給工務的單時，於同一個動作裡撤掉這次派單開出的工務單，並讓這張單的類別與急件標記都回到派單前；之後改派房務時，這張單不會因為派過工務而在房務待認領被當成急件。
- **FR-010**: 系統 MUST NOT 重用被撤掉的工務單號；單號流水號允許因此跳號。

### 使用者故事 3 - 工務待認領單卡顯示工務單類別 (Priority: P2)

作為工務，我在待認領一眼就想知道這張單是冷氣、水電還是其他，不想看到 `repair` 這種代碼。

**為何為此優先級**: 實機看到的顯示錯誤，所有工務單卡都受影響，但不擋流程。

**獨立驗證方式**: 準備一張冷氣、一張其他的工務單，打開工務待認領，看兩張單卡房號方塊上的字。

**驗收情境**:

1. **Given** 工務待認領有冷氣類的 W-0601 與其他類的 W-0621，**When** 阿德打開工務待認領，**Then** W-0601 的單卡寫「冷氣」、W-0621 寫「其他」，沒有任何單卡寫代碼。

**功能需求（FR）**:

- **FR-011**: 系統 MUST 在工務待認領的每一張單上帶出它的工務單類別。
- **FR-012**: App MUST 在工務待認領單卡的房號方塊顯示工務單類別的中文（家具／設備顯示「設備」，沿用既有的短字）。

### 使用者故事 4 - 住客自己送出的需求不會繞過櫃檯直接進工務 (Priority: P3)

作為飯店，我們的規則是住客不直通工務：住客的報修先到櫃檯，由櫃檯判斷再轉。即使飯店把含「冷氣」的文字設成分給工務，住客打的字也先到待派單。

**為何為此優先級**: 目前分類規則命中工務時，單會直接進工務待認領、而且沒有工務單，與故事 1 同一個病，只是入口不同。實機設定裡有這條規則（含「冷氣」「空調」「air con」分給工務）。

**獨立驗證方式**: 設一條把含「冷氣」分給工務的分類規則，住客打「冷氣不冷」，確認單在待派單。

**驗收情境**:

1. **Given** 飯店的分類規則把含「冷氣」的文字分給工務，**When** 305 的住客打字送出「冷氣不冷」，**Then** 305 停在待派單，工務待認領沒有它。
2. **Given** 同一條規則，**When** 412 的住客打字送出「想多一條毛巾」且命中房務的規則，**Then** 412 照舊直接進房務待認領。

**功能需求（FR）**:

- **FR-013**: 系統 MUST 在住客的自由文字命中的部門是工務、或命中的類型是修繕時，把單放進待派單（類別其他、照常取 T- 單號），等櫃檯派單；命中房務而且類型不是修繕時維持直接進房務待認領。命中的規則照樣記在單上供追查。
- **FR-014**: 系統 MUST 在住客勾選的服務項目被飯店設定成交給工務、或類型是修繕時，同樣把單放進待派單。

### 使用者故事 5 - 已經卡在工務的單上線後補好 (Priority: P2)

作為工務，上線之後我希望先前派過來、一直看不到的單出現在待認領，不必請櫃檯重派。

**為何為此優先級**: 手動測試環境與開發資料庫已經有這樣的單（實機 7 張只畫 5 張）；只修新流程不補舊資料，舊單會永遠卡住。

**獨立驗證方式**: 在有卡住單的資料庫上線，確認每一張都已處理：櫃檯派過來的成為工務單並出現在工務待認領；住客經分類規則直接進來的回到待派單。

**驗收情境**:

1. **Given** 資料庫裡有一張櫃檯派給工務、還在工務待認領、沒有工務單的 T-0024，**When** 新版上線，**Then** T-0024 成為一張工務單，類別「其他」、報修人是當初派單的人、來源「櫃檯」，出現在工務待認領。
2. **Given** 資料庫裡有一張住客經分類規則直接進工務待認領、沒有工務單、也沒有 T- 單號的單，本飯店上一張 T- 單號是 T-0030，**When** 新版上線，**Then** 這張單回到待派單，領到 T-0031，歷程多一筆系統退回待派單的紀錄（櫃檯歷程畫面不顯示這一筆）。
3. **Given** 資料庫裡有一張部門是工務、沒結束、沒有工務單，但不是上面兩種的單（例如手寫 SQL 塞進去的同仁來源單），**When** 新版上線，**Then** 上線停下並列出筆數，任何一張單都沒有被搬動。

**功能需求（FR）**:

- **FR-015**: 系統 MUST 在上線時，把櫃檯派給工務、尚未結束、沒有工務單的單補成工務單，欄位規則與 FR-002、FR-003 相同，單號接續目前的流水號。
- **FR-016**: 系統 MUST 在上線時，把住客需求未經櫃檯直接進工務、還在待認領、沒有工務單的單退回待派單；沒有 T- 單號的補一個接續流水號的 T- 號，並為每張補一筆系統事件，讓事件紀錄與下游都看得到這次退回。
- **FR-017**: 系統 MUST NOT 改動已結束（已完成、已結案、已取消）的歷史單。
- **FR-019**: 系統 MUST 在上線時遇到部門是工務、沒結束、沒有工務單，卻不屬於 FR-015、FR-016 兩種的單（包括派單紀錄沒有操作者的單、住客來源卻不在待認領的單、非住客來源又沒有派單紀錄的單）時，讓上線停下並列出筆數，不猜怎麼處理、不默默搬動。

### 邊界情況

- 當兩位櫃檯同時把同一張單派出時，系統 MUST 只讓先到的成立，且只開一張工務單；後到的照既有規則被拒。
- 當工務單判定為急件、急件推播已發出後櫃檯才復原時，系統 MUST 照常撤掉工務單，急件標記回到派單前；已送出的急件推播不收回，工務點開會看到這張單已不在待認領。之後再派給工務開出的新單若判定為急件，照常推播新單號。
- 當住客在工務認領前收回這張需求時，系統 MUST 照既有規則讓單取消；工務單跟著成為已撤回，工務待認領不再顯示。
- 當派給工務的單被工務放回待認領、因請假或班末退回、驗收不通過退回時，系統 MUST 沿用原本的工務單，不另開。
- 當櫃檯派單時這張單已經有工務單（不應發生，但重送與重試都可能走到）時，系統 MUST 沿用既有的工務單，不開第二張。

## 需求 *(必填)*

### 全域需求

#### 功能需求

- **FR-018**: 系統 MUST 保證「單只要屬於工務部門，就是一張工務單」：每一張部門為工務的單都恰好有一張工務單；唯一的例外是本版上線前就已結束的歷史單（FR-017）。讓單成為工務部門的只有兩個動作：開單時就開給工務、從待派單派給工務；兩者都必須經過同一個「開工務單」的步驟，這個步驟對已經有工務單的單不做任何事。

#### 非功能需求

- **NFR-001**: 派單與開工務單在同一筆交易內完成：任何一步失敗，整個派單都不成立，不會留下「已派給工務但沒有工務單」或「有工務單但還在待派單」的中間狀態。

### 關鍵實體 *(若功能涉及資料，必填)*

- **單（任務）**: 住客、櫃檯、同仁看的那一張單。派給工務時它的類別變成修繕；復原時回到派單前的類別。
- **工務單**: 掛在修繕單上的延伸資料，與單一對一，記單號、類別、報修人、急件判定、驗收紀錄。本版沒有新增欄位。
- **工務單流水號**: 每間飯店一組，所有開單路徑共用，只增不減。

**狀態公式**：工務待認領分流磚的總張數 ＝ 工務待認領列表畫出的單卡張數 ＝ 部門為工務、狀態為待認領的單數 ＝ 其中有工務單的單數。

## 新行為（交付時請使用者確認）

- 住客的單被櫃檯派給工務後成為修繕單，住客頁的進度從此照修繕單的對照表走：工務完修（已完修、等驗收）時住客看到「已完成」並可評分；驗收通過結案後仍是「已完成」、不再請評分；驗收不通過退回重修時，住客頁會從「已完成」退回「已受理」或「處理中」。以前住客的單派給工務後類別仍是其他，做完就結束、不會退回，所以這對住客是新的行為。住客頁的對照表本版不改。
- 上線那一刻，住客經分類規則直接進工務、還在待認領的舊單會退回待派單，正在看進度頁的住客會從「已受理 · 工務收到」退回「已送出 · 櫃檯」。
- 上線順序：先停掉舊版本後端，再起新版。資料修補在新版啟動時執行；舊版還在服務時起新版，修補檢查之後有人認領，新版的自我檢查會讓它起不來。
