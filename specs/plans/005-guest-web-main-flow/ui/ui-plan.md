# 前端 / UI 與靜態雛形規劃

這份文件把 `plan.md` 交給 `/ui-plan` 的八個畫面介面寫成一份畫面規劃：住客掃碼頁每一頁長什麼樣、有哪些狀態、每一句文字出自哪裡、用到後端的哪些資料。讀的順序建議是「介面範圍 → 狀態對照表怎麼落到三個畫面 → 畫面與流程 → 待釐清的處理結果」。本檔的寫法與 `spec.md` 相同：「」內是畫面文字，`code` 是資料值，`{…}` 是會被實際內容換掉的位置。標「預設，待使用者確認」的文字與呈現，是本檔在 `spec.md` 與原型都沒有出處時給的預設。

## 視覺方向

- 風格來源：原型的實際樣式值，與它引用的「TMS 設計系統（Web）」`tms-web` 的 token，配色 B。品牌色 `#0C7680`、品牌淺底 `#C8E8ED`、頁面底色 `#F2F2F7`、卡片白底、暖色點綴 `#FFDCC5`／`#703700`、成功 `#DDF3E4`／`#1A6B34`、中性 `#E5E5EA`／`#3C3C43`
- 本次風格結論：「灰底上的白色圓角卡片」加兩張彩色大卡。首頁是一整頁往下捲的一頁式，沒有底部分頁列；首頁以外的頁一律左上返回。立體感只留在主視覺卡與服務列的插圖物件、浮起的提問列。原型外框裡的 iPhone 狀態列、Safari 浮動工具列、模擬鍵盤、時間滾輪是裝置的一部分，網頁不畫
- 視覺重點：首頁最大的字是問候（34px 粗體兩行，第二行品牌色）；接著是「我的需求」進度卡（20px 粗體標題、四格進度條）與兩張主視覺卡（蜜桃色「備品補充」、青色「設備報修」）。進度頁最上面是 22px 粗體的需求標題與狀態標籤，下面一張帶底色的狀態訊息框，住客不用往下捲就讀得到「現在怎樣」
- 審美原則：一頁只有一顆實心主按鈕（備品補充與設備報修的頁底送出鈕、送出成功頁的「查看進度」、重試狀態的「重試」、評分卡的「送出評分」）；危險動作用灰底紅字。可點的東西一律至少 44px（原型有 36 至 40px 的元件，這裡依 NFR-005 補到 44px）。即將開放的入口照原型的位置與插圖擺出來，但沒有箭頭、按下去沒有任何回饋，以一顆中性色的「即將開放」標籤取代原本的說明字。畫面上只放住客真的會看到的字；示範資料、切換狀態的方法都寫在本檔，不寫進畫面

### 深色模式

v1 只做淺色（預設，待使用者確認）。`guest.css` 的每一個顏色都是 CSS 變數，深色那一組照設計系統的值另外寫好、掛在 `[data-theme="dark"]` 底下，但 v1 不跟著手機的深色設定切換，頁面宣告 `color-scheme: light`，表單元件與捲軸也維持淺色。理由：住客頁的驗收只在一組手機設定下跑，多一種外觀就要多一倍的畫面檢查；設計系統的深色值已經存在，之後要開，只要在外框依 `prefers-color-scheme` 設定 `data-theme`，元件一行都不用改。雛形網址加 `?theme=dark` 可以看到深色的樣子，那只是讓 reviewer 確認變數夠用，不是產品功能。

### 1. `進入層：載入中、無法使用頁、重試狀態`

- 對應雛形檔案：`ui/unavailable.html`（預設是無法使用頁；`?state=retry` 重試狀態；`?state=loading` 載入中）
- 主要目的：打開 QR Code 的網址就靜靜換 session 進首頁；這間房不能用時明講請找櫃檯；連不上時讓住客自己再試
- 進入條件：打開 `/g/{代碼}` 或它底下任何一頁、這個分頁沒有這枚代碼的 session（第一次掃、新分頁、從歷史記錄打開）；或已經在用時某次呼叫被回 401，重換 session（FR-004）
- 主要操作：無法使用頁沒有任何可以點的東西；重試狀態只有「重試」
- 成功流轉：換到 session 就顯示原本要去的那一頁（打開 `/g/{代碼}` 是首頁；從歷史記錄打開子頁是那一頁；已經在用時重換成功，就重發剛才那一次呼叫、畫面不變）
- 失敗回饋：後端回 `409 room_vacant` 顯示無法使用頁；回 `429`、連不上、`5xx` 顯示重試狀態。已經在用時重換 session 也一樣分這兩種

| 狀態 | 畫面 | 文字出處 |
| --- | --- | --- |
| 載入中（換 session 加第一次讀需求清單） | 只有頁面底色與正中央一個 24px 的品牌色轉圈，沒有字；兩件事都回來才畫首頁，避免「我的需求」晚一步跳出來把下面的卡片往下推 | 本檔預設 |
| 無法使用（空房、代碼已作廢、代碼不存在、已過退房時刻，後端都回同一個結果） | 置中提示：橘色資訊圖示、標題「請洽櫃檯」、內文「目前無法在這裡提出需求，需要什麼請直接找櫃檯。」，下面一張白卡：左邊品牌淺底圓形電話圖示，右邊上一行「櫃檯（24 小時）」、下一行粗體「房內電話撥 9」。沒有房號、沒有首頁的任何東西、沒有按鈕與連結（白卡不是電話連結） | 標題與白卡出自原型與 FR-003；內文是 C-01，預設，待使用者確認 |
| 重試（被限流、連不上、後端出錯） | 置中提示：灰色 Wi‑Fi 圖示、標題「連線失敗，請再試一次」、下面一顆滿寬實心「重試」（高 54px）。沒有「請洽櫃檯」、沒有「櫃檯（24 小時）」那張白卡 | 文字出自 `spec.md` 邊界情況；版面比照送出成功頁，本檔預設 |
| 按了「重試」、還在等後端 | 「重試」不能按、按鈕上一個轉圈，字不變 | 本檔預設 |
| 重試後換到 session | 直接換成原本那一頁 | `spec.md` 邊界情況 |
| 重試後後端回無法使用 | 換成無法使用頁 | `spec.md` 邊界情況 |
| 重試後又失敗 | 留在重試狀態，畫面不變 | `spec.md` 邊界情況 |

三種無法使用的情形畫面一字不差（FR-002、SC-002）。這一層沒有語言膠囊；語言照這支手機記住的或瀏覽器的語言（畫面 10）。換 session 的過程中網址不變，所以住客永遠不用再掃一次。

### 2. `首頁`

- 對應雛形檔案：`ui/index.html`
- 主要目的：一眼看到房號、我的需求走到哪、最常用的兩件事；其他服務與住宿指南從這裡進
- 進入條件：換到 session 之後的第一頁；從任何子頁返回；送出成功頁按「回首頁」

- 假資料策略：311 房，示範時鐘固定在 14:30、不會自己走（`?at=08:30` 之類可以改，影響問候與 10 分鐘額度）。飯店沒有另外設定服務項目，備品補充是後端預設的五項「衣架」「毛巾」「牙刷組」「礦泉水」「吹風機」；資訊頁三頁「早餐」（兩行內文）「Wi‑Fi」「退房時間」。預設的需求是驗收劇本裡那三張：09:30「毛巾」房務已完成還沒評分、14:05「礦泉水 ×2」房務待認領、14:12「冷氣不冷：風量很小」待派單。資料只存在這個瀏覽器分頁，關掉分頁或在網址加 `?reset=1` 就還原
- 互動原則：首頁到備品補充到送出成功到清單到進度頁到取消或評分、首頁到設備報修到送出成功，全部可以實際操作；語言選單、數量加減、類別膠囊、字數、限流估算、確認框、提示浮層、返回到進來的地方都會動。後端才會發生的事（限流在送到一半拒絕、連不上、同仁剛好接手、另一支手機先評了分、同仁推進狀態）用網址參數切換，畫面上沒有任何切換狀態用的控制項
- 內容原則：畫面文字只放產品真的會顯示的字，一律用 `spec.md`、驗收劇本與原型的原文；本檔預設的文字在各畫面的狀態表裡標了出處，並彙整在「找不到出處的文字」。雛形的四種語言只收原型字典裡已有譯文的句子，以及把原型句子裡的姓名、時間拿掉後的句子（例如原型「{同仁} 正在處理 · {時間} 開始」拿掉時間與姓名，留「{部門}正在處理」各語言的前半句）；沒有出處的句子在別的語言下維持繁體中文，完整的四語文字是實作的工作

- 使用者可見資訊：房號；這次住宿每一張需求的類型圖示、標題、狀態（五個顯示階段）、部門（房務、工務、櫃檯）、送出時間（時:分）、櫃檯回覆原文、自己有沒有評過分；飯店設定的服務項目名稱；資訊頁標題與內文

- 角色或權限差異：住客只有一種身分；同一間房的每一支手機看到同一份需求清單（同一筆訂房）。住客頁不讀也不寫櫃檯的登入狀態，櫃檯 Web 也看不到住客的 session（FR-055）

## 驗證與錯誤回饋

- 輸入驗證：數量 0 到 5，靠加減鈕的不能按擋住，不跳提示；設備報修沒選類別、選「其他」但補充說明只有空白時「送出報修」不能按；補充說明最多 200 字，打不進去。這些都在當下擋，不跳提示
- 狀態衝突處理：

| 後端回的 | 住客頁怎麼做 |
| --- | --- |
| 任何一次呼叫回 `401` | 丟掉手上的 session，用網址裡的代碼靜靜重換一次；換到就重發剛才那一次、畫面不變；換不到依進入層（`409 room_vacant` 無法使用頁、其他重試狀態）。一輪最多重換一次 |
| 建立需求回 `429` | 備品補充依 C-04；設備報修顯示限流提示框 |
| 撤回回 `409 state_conflict` | 提示浮層「同仁已經接手，無法取消。請撥 9 找櫃檯。」並重讀這一張 |
| 評分回 `409 state_conflict` | 不提示，重讀這一張，評分卡依新狀態消失 |
| 寫入時連不上或 `5xx` | 備品補充、設備報修在清單下方紅色提示框；取消與評分用提示浮層「沒有送出，請檢查網路連線後再試一次。」；都不改畫面上的資料 |
| 讀取時連不上或 `5xx`，畫面上已經有資料 | 留著舊資料，不提示，照即時更新的異常規則每 4 秒重讀 |
| 讀取時連不上或 `5xx`，畫面上還沒有資料 | 進入層的重試狀態 |

- 使用者可理解錯誤訊息：每一句都說「沒成功、為什麼、接下來怎麼辦」，而且一律給撥 9 這條退路。限流與「同仁已經接手」是住客自己改不了的，所以給櫃檯電話；連不上是住客自己能處理的，所以說檢查網路再試一次。會影響「到底送出去了沒」的訊息（限流、連不上）放在畫面上不會自己消失的提示框；只是動作結果的回饋（已取消、謝謝、無法取消）用會消失的提示浮層

**鍵盤與螢幕報讀**。Tab 走得到每一個可以點的東西，焦點外框是 2px 品牌色、外推 2px；確認框打開時焦點移進去、Tab 只在兩顆按鈕之間、關閉後回到「取消這個需求」；Esc 關閉最上面那一層（確認框、語言選單）。類別膠囊是單選群組，星星是單選群組（每顆的名稱「{n} 顆星」）；加減鈕的名稱是「減少{名稱}」「增加{名稱}」，數字變化會被報讀；即將開放的入口是純文字（「晚點 退房，即將開放」），不是按鈕；插圖一律不給報讀軟體。

## 與 `spec.md` 對不上的地方

1. **`pool` 的四步樣子**。`spec.md` 使用者故事 3 驗收情境 5 寫「第 1 步打勾並寫「{部門}收到」、第 2 步實心寫「同仁接手後開始」」，但同一個故事的對照表（`pool` 走到第 1 步）、FR-025（目前的步實心）、驗收劇本「礦泉水 ×2 從房務待認領到阿美完成」（「已受理」實心「房務收到」、「處理中」空心「同仁接手後開始」）與原型都是「已受理」實心、「處理中」空心。本檔照後者畫。建議 `spec.md` 改這一句。
2. **FR 編號引用錯位**。`spec.md`「範圍」與「設計圖與後端現況的出入」有幾處引用的 FR 編號對不上內容：即將開放入口寫 FR-055（應為 FR-051）、出入第 7 項報修組成文字寫 FR-037（應為 FR-034）、第 8 項各步副文寫 FR-026、FR-027（應為 FR-025、FR-026）、第 9 項取消原因寫 FR-025（應為 FR-024）、第 10 項評分寫 FR-043、FR-047（應為 FR-041、FR-042）、第 13 項寫 FR-055（應為 FR-051）。本檔一律引用內容對得上的編號。
3. **送到一半被擋時先送哪一張**。驗收劇本「櫃檯剛替這間房代開了一張單，住客的估算偏高，送到第二張被擋」與「送到一半手機斷線」都假設「礦泉水 ×2」先建立、「衣架」後送；但 FR-015 規定照清單順序送，後端預設的清單是「衣架」在「礦泉水」前面，照 FR-015 會先建立「衣架」。本檔與雛形照 FR-015。建議 `/dsl-refine` 寫這兩個 Example 時，讓先送的那一項排在清單前面（例如改用「毛巾」與「礦泉水」），或不要寫死哪一項被擋。
4. **待派單的部門**。`spec.md` 說待派單時「後端還沒定部門」顯示「櫃檯」；後端實際上在規則沒命中時就把 `dept` 填成 `frontdesk`（見「用到的後端資料」）。畫面結果一樣是「櫃檯」，不影響本檔。

## 待決事項

下面幾件事不在六題待釐清之內，是這一趟整理畫面時發現的缺口。

1. **送出、取消、評分時連不上**。`spec.md` 只寫了後端拒絕，沒寫送不出去。本檔預設備品補充與設備報修用紅色提示框、取消與評分用提示浮層，文字見「找不到出處的文字」。
2. **讀取失敗**。`spec.md` 只寫了換 session 失敗的重試狀態。本檔預設：已經有資料時留著舊資料、不提示、每 4 秒重讀；還沒有資料時用同一個重試狀態。
3. **從設備報修送出的單在待派單時圖示是對話泡泡**（見「用到的後端資料」）。照後端的 `type` 顯示是對的，但住客可能覺得「我報修的怎麼不是鎚子」。要改只能讓後端在報修時帶類型，本版不改後端，先照資料顯示。
4. **報修文字的類別一律用中文**。這是從驗收劇本「住客用日文補充說明」推出來的（類別「電視無訊號」加日文補充說明）。若想讓類別也跟著介面語言，改的是 FR-034 與那一個 Example。
5. **送出成功頁重新整理**。本檔把剛建立的識別碼放在網址上，重新整理仍是同一頁；如果這幾張在這之間被取消，成功頁照樣說「已送出」，因為它說的是「送出」這件事本身。
6. **網頁標題**（瀏覽器分頁上的字）`spec.md` 沒寫，本檔的預設見畫面 10。
