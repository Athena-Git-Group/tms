# 前端 / UI 與靜態雛形規劃

這份文件把 `plan.md` 交給 `/ui-plan` 的七個畫面介面寫成一份畫面規劃：每個畫面長什麼樣、有哪些狀態、每一句文字出自哪裡、要跟後端拿哪些資料。讀的順序建議是「介面範圍 → 畫面與流程 → 給 `/api-plan` 的資料需求 → 待釐清 C-01 至 C-18 的處理結果」。本檔的寫法與 `spec.md` 相同：「」內是畫面文字，`code` 是資料值，`{…}` 是會被實際內容換掉的位置。

- 目標系統介面：櫃檯 Web（`app/web/`），`plan.md` 盤點編號 1 至 7 的七個畫面介面，合併成一份畫面規劃
  1. 登入、改密碼與帳號面板
  2. 共用外框與尚未開放的入口
  3. 總覽看板（含拖曳派單）
  4. 待派單頁、派單浮條與復原
  5. 當場回答面板
  6. 單筆詳情面板
  7. 即時更新與連線異常提醒列
- 需求來源：`spec.md` 使用者故事 1 至 7；FR-001 至 FR-103；NFR-001 至 NFR-008；SC-001 至 SC-019；邊界情況全部；待釐清 C-01 至 C-18
- 需求的優先序：原型「櫃檯 APP」頁的 `Desk.dc.html` 最優先；`spec.md` 已寫定的使用者決定高於原型裡與它衝突的地方（兩邊不同之處列在「與原型不同的地方」一節）；資料值跟後端現況，全寫不縮寫。`docs/11` 不當依據
- 上游依據：`spec.md`、`plan.md`（介面盤點、Wave 1 分析重點、後端現況的落差）、`research.md`（決策 3、4、8、9）、`truth-delta.md`、`features/acceptance/` 12 份驗收劇本；既有 truth：`specs/truth/data/data-model.dbml` 的 `tasks`、`task_events`，`specs/truth/techstack.md` 櫃檯 Web 各列；原型檔 `Desk.dc.html` 與設計系統 `ds/tms-web/tokens.css`（本次以 Artifact 工具重新取得，不在 repo 內）

## 視覺方向

- 風格來源：原型 `Desk.dc.html` 的實際樣式值，與它引用的「TMS 設計系統（Web）」token。品牌色 `#0C7680`、品牌淺底 `#C8E8ED`、頁面底色 `#F2F2F7`、卡片白底、暖色點綴 `#FFDCC5`／`#703700`、錯誤 `#FFE4E1`／`#B42318`、成功 `#DDF3E4`／`#1A6B34`
- 本次風格結論：整個畫面是「灰底上的白色圓角卡片」。原型有 iPadOS 18 與 iPadOS 26 兩種外觀，差別只在按鈕是文字還是圖示、側欄是貼邊還是浮動玻璃。櫃檯 Web 採貼邊側欄加文字按鈕（原型的 iPadOS 18 外觀）：面板的離開鈕寫「關閉」「取消」「完成」，四種語言都讀得懂，也不需要玻璃模糊效果。原型畫面上方的 iPad 狀態列與底部的 Home 指示條是裝置的一部分，網頁不畫，工具列因此比原型矮
- 視覺重點：看板卡片最大的字是房號（22px 粗體），其次是右上的等待膠囊；膠囊用顏色說等了多久（灰、橘、紅），不用急件標記。數量卡的數字 26px 粗體。待派單頁每列左邊是一塊黃底的房號磚，右邊三顆等高的膠囊按鈕。詳情面板最上面是 34px 的房號與狀態標籤，接著一張帶底色的狀態訊息卡，讓櫃檯人員不用往下捲就讀到「現在的狀況」
- 審美原則：一個區塊只有一顆實心主按鈕。待派單頁每列三顆都是描邊（沒有哪一顆是系統建議）；詳情面板派單區沿用原型：「派給房務」「派給工務」描邊、「當場回答…」實心。可點的東西高度一律至少 44px（原型有 32 至 40px 的膠囊，這裡依 NFR-006 補到 44px）。畫面上只放櫃檯人員真的會看到的字；示範用的帳號、切換狀態的方法都寫在本檔，不寫進畫面

### 版面尺寸與伸縮規則

- 當場回答面板、帳號面板：標題列固定，內容自己捲；當場回答面板的「回覆並結案」固定在面板底部

## 畫面與流程

### 1. `登入頁`

- 對應雛形檔案：`ui/index.html`
- 主要目的：櫃檯共用的裝置上，每個人用自己的員工編號與密碼登入；登入前可以換介面語言
- 進入條件：還沒登入、登出之後、關掉分頁或瀏覽器再打開、已登入時另開的新分頁
- 主要操作：輸入「員工編號」（照打的樣子送出，不轉大小寫、不去前後空白，與員工 App 一致；最多 12 字）與「密碼」（最多 32 字）、按「顯示密碼」／「隱藏密碼」、按「登入」、按「忘記密碼？」、打開右上的語言選單選一種語言
- 成功流轉：一般帳號進總覽看板，側欄收起；拿臨時密碼的帳號進改密碼畫面
- 失敗回饋：見下表；所有失敗都留在登入頁

版面（由上到下，內容置中、寬 420px）：右上語言選單（地球圖示加目前語言的名稱）→ 品牌圖示 → 「登入 TMS 櫃檯」→ 飯店名稱 → 「這台裝置是櫃檯共用的，請用自己的帳號登入」→ 一張白卡，兩列「員工編號」「密碼」（標籤在列內左側，密碼列右側是顯示／隱藏鈕）→ 提示的位置 → 「登入」→ 「忘記密碼？」。

| 狀態 | 畫面 | 文字出處 |
| --- | --- | --- |
| 兩欄有一欄是空的（員工編號只打空白不算空，可以按） | 「登入」是灰色、不能按 | FR-002 |
| 送出中 | 「登入」不能按，按鈕上的字不變 | 本檔預設 |
| 員工編號不存在、密碼錯、角色不能用櫃檯畫面（密碼不是臨時密碼） | 白卡下方紅字「員工編號或密碼不正確。」，密碼欄清空 | 原型、FR-005 |
| 帳號被鎖定 | 白卡下方一張淡紅底提示卡：標題「暫時無法登入」、內文「連續輸錯 5 次，請 15 分鐘後再試，或請主管在後台重設密碼。」，密碼欄清空 | FR-005（文字來自手機 App） |
| 帳號已停用 | 同一個位置的提示卡：標題「這個帳號已停用」、內文「請主管在後台重新啟用後再登入。」，密碼欄清空 | C-01，本檔預設 |
| 查不到飯店名稱，或還沒回來 | 飯店名稱那一行不畫，其餘照常，可以登入 | FR-001、使用者決定 |
| 連不上後端 | 白卡下方紅字「現在連不上系統，請檢查網路連線後再試一次。」，兩欄內容保留 | 本檔預設，`spec.md` 沒有這個情形 |
| 被擋的角色剛改完臨時密碼 | 提示卡：標題「這個帳號不能使用櫃檯畫面」、內文「新密碼已經生效。櫃檯畫面只開放櫃檯、主管與值班主管的帳號。」，兩欄是空的 | C-02，本檔預設 |
| 按「忘記密碼？」 | 對話框：標題「忘記密碼」、內文「請主管在後台重設密碼。重設後你會拿到臨時密碼，第一次登入時要改成自己的密碼。」、按鈕「好」 | 原型、FR-009 |
| 語言選單打開 | 四個選項「繁體中文」「English」「日本語」「Tiếng Việt」，目前的語言前面打勾；點選單以外的地方收起 | 原型、FR-001 |

使用者一開始改任何一欄，紅字或提示卡就消失。鎖定與停用用「卡」、帳密錯誤用「一行紅字」，兩者一眼分得出來（FR-005 要求三種提示彼此不共用）。

顯示的資料：飯店名稱（登入前依網址上的飯店識別代碼向後端查，查不到或還沒回來時不顯示；見「給 `/api-plan` 的資料需求」）；這台裝置上記的介面語言。

### 2. `改密碼畫面`

- 對應雛形檔案：`ui/change-password.html`
- 主要目的：拿臨時密碼登入的人，先把密碼改成自己的，才能進任何櫃檯畫面
- 進入條件：用臨時密碼登入成功（含被擋的角色）。直接輸入其他頁的網址、或在這一頁重新整理，都回到這一頁
- 主要操作：輸入「新密碼」「確認密碼」（各有顯示／隱藏鈕）、看四條規則即時打勾、按「更新密碼」、按「登出」離開
- 成功流轉：`frontdesk`、`manager`、`duty_manager` 直接進總覽看板、側欄收起，不必再登入；`housekeeping`、`engineering`、`owner` 回到登入頁並看到「這個帳號不能使用櫃檯畫面」的提示卡
- 失敗回饋：見下表；所有失敗都留在這一頁，兩欄內容保留

原型沒有畫這個畫面（C-16）。版面沿用登入頁的置中版型，欄位與規則清單沿用原型帳號面板裡「變更密碼」那一頁的畫法，拿掉「目前密碼」欄（FR-016：不需要再輸入一次臨時密碼）。由上到下：右上語言選單 → 品牌圖示 → 「設定新密碼」→ 「你是用臨時密碼登入的，先改成自己的密碼才能繼續。」→ 一張白卡，兩列「新密碼」「確認密碼」→ 四條規則「至少 8 碼」「包含英文字母」「包含數字」「兩次輸入相同」（符合的那一條前面的圓點變綠、字變黑）→ 「更新密碼」→ 「登出」。

| 狀態 | 畫面 | 文字出處 |
| --- | --- | --- |
| 四條規則還沒全部符合 | 「更新密碼」是灰色、不能按；沒符合的規則維持灰色 | 規則文字出自原型；按鈕文字「更新密碼」出自原型 |
| 新密碼與臨時密碼相同 | 送出後白卡下方紅字「新密碼不能和臨時密碼相同。」 | 規則出自 FR-016，字句是本檔預設 |
| 連不上後端 | 白卡下方紅字「沒有更新成功，請檢查網路連線後再試一次。」 | 本檔預設 |
| 按「登出」 | 不問確認，直接回登入頁，兩欄是空的 | 本檔預設 |

標題「設定新密碼」、說明句、「登出」這三處文字原型沒有，是本檔預設。留一個「登出」是因為裝置是共用的：拿臨時密碼的人如果臨時走開，下一位同事要有辦法回到登入頁。

顯示的資料：無（只用登入回應裡「必須先改密碼」的標記與角色）。

### 3. `共用外框`（側欄、工具列、提醒列的位置）

- 對應雛形檔案：`ui/board.html`、`ui/triage.html`
- 主要目的：登入後每一頁共用的框架：知道自己在哪一頁、還有幾張單等著派、現在登入的是誰
- 進入條件：登入後的每一頁
- 主要操作：在「總覽看板」「待派單」之間切換、按「收合側欄」／「打開側欄」、點帳號卡打開帳號面板
- 成功流轉：切換頁面時外框不變；開著的詳情面板關閉、數量卡篩選清除、房號搜尋保留
- 失敗回饋：「通知板」「遺失物」「設定」「代開單」點了沒有任何反應（不換頁、不跳提示、不變色）

**側欄**由上到下：品牌圖示、「TMS 櫃檯」、副標「{飯店名稱}」、右側「收合側欄」鈕 → 功能列「總覽看板」「待派單」「通知板」「遺失物」（目前的頁是品牌色底白字；「待派單」右側是紅色圓形徽章，數字是待派單數，0 的時候不顯示）→ 「設定」（灰字、右側一個向右的箭頭；只有 `manager` 與 `duty_manager` 看得到，點了不展開）→ 最下面是帳號卡：頭像（姓名最後一字）、姓名、「{角色中文} · {員工編號}」、向右的箭頭。

「遺失物」在原型有未讀徽章，那是 006 的功能，這一包不顯示。

**工具列**由左到右：「打開側欄」鈕（側欄收起時才有）→ 頁標題（28px 粗體）與頁副標（13px）→ 「搜尋房號」輸入框（只在總覽看板，寬 220px）→ 「代開單」（實心品牌色膠囊，前面一個加號；兩頁都有，點了沒有反應）。

| 頁 | 頁標題 | 頁副標 |
| --- | --- | --- |
| 總覽看板 | 「總覽看板」 | 「{M/D} {週幾} · {N} 張未結案 · 即時更新」，例「10/26 週一 · 23 張未結案 · 即時更新」 |
| 待派單（有單） | 「待派單」 | 「{N} 張等你派單 · 最久已等 {M} 分」 |
| 待派單（沒有單） | 「待派單」 | 「目前沒有要派的單」 |

資料還在載入時，頁副標裡的張數先不顯示：總覽看板只寫「{M/D} {週幾}」，待派單頁副標留空。

**側欄的預設與記憶**（FR-039）。登入後還沒自己按過收合或打開時：總覽看板收起、待派單頁打開。自己按過一次之後，兩頁都維持他選的樣子，直到登出。詳情面板打開時側欄自動收起（這次自動收起不算「自己按過」）；面板開著時按「打開側欄」，面板關閉、側欄打開。

顯示的資料：飯店名稱；登入者的姓名、角色、員工編號；待派單數；全館未結案張數；今天的日期與星期（飯店當地）。

### 4. `帳號面板`（身分卡、語言頁、登出確認）

- 對應雛形檔案：`ui/board.html`、`ui/triage.html`（點側欄帳號卡）
- 主要目的：確認現在登入的是不是自己、換介面語言、把裝置交給下一位時登出
- 進入條件：點側欄底部的帳號卡
- 主要操作：點「語言」進語言頁選一種語言、從語言頁按「‹ 帳號」回來、按「登出」、按「完成」關閉
- 成功流轉：選了語言立刻套用並記在這台裝置上（每人一筆）；「登出」確認後回登入頁，兩欄是空的，登入頁停在剛登出那一位的語言

### 5. `總覽看板`（含拖曳派單）

### 6. `待派單頁、派單浮條與復原`

- 對應雛形檔案：`ui/triage.html`（浮條與復原在 `ui/board.html` 也有）
- 主要目的：把等著派的需求一筆一筆派給房務或工務；派錯 5 秒內收回
- 進入條件：從側欄點「待派單」
- 主要操作：按某一列的「派給房務」「派給工務」「當場回答…」、點列的其他地方開詳情面板、在浮條上按「復原」
- 成功流轉：派出 → 這一列立刻消失、底部浮條「已派給{部門}（{房號}）」加「復原」、側欄徽章少 1；復原成功 → 這一列回到清單（依進來的時間排回原本的位置）、浮條消失
- 失敗回饋：送出失敗、撞單、復原失敗兩種，見狀態表

由上到下：頁首 → 需求清單 → 頁尾說明。

**頁首**：兩顆白底膠囊「房務 {n} 單待接」「工務 {n} 單待接」，同一行靠右是灰色小字「點部門就送出，5 秒內可復原；當場回答會先開回覆面板」。

**每一列**（白卡、圓角 18px）：左邊一塊 64px 見方的黃底房號磚（房號 21px 粗體、下面「{N} 樓」），點它也是開詳情面板；中間由上到下是「{住客原話}」（17px 半粗體，全文顯示不截斷）、原文列「{語言}原文：{原文}」（有翻譯內容時才有）、一行灰字「{住客名或「空房」}」「VIP」「· 住客掃碼 ·」「已等 {N} 分」；右邊三顆描邊膠囊按鈕「派給房務」「派給工務」「當場回答…」，高 48px。內容區窄到放不下時，三顆按鈕整組換到下一行。

「已等 {N} 分」的顏色跟看板的等待膠囊同一組門檻：不到 10 分灰、10 分以上橘、20 分以上紅；不到 1 分寫「已等 不到 1 分」。

原文列的語言名稱目前有「日文原文」「英文原文」兩種（`spec.md`）；其他語言的寫法是「{語言中文名}原文：{原文}」，語言中文名由畫面依原文語言代碼對出來，對不出來時寫「原文：{原文}」（本檔預設）。

**頁尾說明**：13px 灰字，原文見 FR-048。

**派單浮條**：畫面底部置中、離底 28px 的深色浮條（`rgba(30,30,30,.92)` 白字）：打勾圖示、「已派給{部門}（{房號}）」、右邊「復原」（淺青字）。出現 5 秒後自己消失。5 秒內又派了另一張，浮條換成新的那一張，前一張就不能在這裡復原了（原型的做法）。浮條跟著人走不跟著頁：5 秒內從待派單頁換到總覽看板，浮條還在；登出或重新整理就沒有了。

### 7. `當場回答面板`

- 對應雛形檔案：`ui/triage.html`、`ui/board.html`（從待派單頁的列或詳情面板的派單區打開）

### 9. `即時更新與連線異常提醒列`

- 對應雛形檔案：`ui/board.html`、`ui/triage.html`
- 主要目的：畫面不用重新整理就跟上現場；連線有問題時明講資料可能延遲
- 進入條件：即時連線斷了之後重連失敗、太久沒有收到後端的訊號、後端宣告事件處理落後，或已有資料之後重抓失敗。斷線後第一次重連就成功時不出現（見下方「什麼時候出現、什麼時候消失」）
- 主要操作：無。提醒列上沒有任何按鈕
- 成功流轉：連線恢復後提醒列自己消失，回到即時更新
- 失敗回饋：提醒列本身就是回饋；這段期間照常可以看單、派單、當場回答

提醒列在工具列下方、內容區上緣：白底圓角 14px、橘色警告三角圖示、粗體「即時連線異常」、灰字「看板資料可能延遲，每 5 秒自動更新」。它出現時，看板與清單的可用高度少 52px。頁副標的「即時更新」四個字不變（FR-038 只定了這一種格式）。

**什麼時候出現、什麼時候消失**（使用者 2026-11-18 裁決）。即時連線斷了，畫面先自己重連一次；這一次就連上的話提醒列完全不出現，畫面上看不出斷過。下面三種情況才出現：

| 出現的情況 | 怎麼判斷 |
| --- | --- |
| 重連失敗 | 斷線後的重連至少失敗一次 |
| 太久沒有資料 | 連線還在，但約兩個心跳週期沒有收到後端的任何訊號（後端心跳每 15 秒一次，目前門檻 35 秒） |
| 後端宣告降級 | 後端送來「事件處理落後」的訊號，或心跳帶 `degraded=true` |

跟即時連線無關的「已經有資料之後重抓失敗」照畫面 5、畫面 6 的狀態表，同樣出現提醒列。

消失的規則照舊：收到後端「已恢復」的訊號，或心跳帶 `degraded=false`，提醒列才消失；單純重連成功不算。

這樣改的理由：後端每 30 分鐘會例行收掉連線、讓畫面重連一次。原本「斷線就出現、等恢復訊號才消失」的規則，會讓提醒列在每次例行重連時閃出來，最多停留一個心跳週期（約 15 秒），櫃檯人員會以為系統出了問題。

**更新間隔**：提醒列寫「每 5 秒自動更新」，實際間隔略短（目前 4 秒），確保同仁在手機上的動作在 5 秒內反映到畫面（讀取本身與畫面更新也要時間，真的每 5 秒讀一次一定超過 5 秒）。提醒列出現期間的重讀、讀取失敗時的自動再試（畫面 5、畫面 6 的「讀不到資料」）用同一個間隔，都是 4 秒。畫面上的字維持「每 5 秒」，不改成 4 秒。

**跟著變的範圍**（FR-092）：看板的卡片位置、等待膠囊、負責人頭像、欄頭數量與警示、四張數量卡、頁副標張數、泳道副標；待派單頁的清單、頁首負荷、頁副標；側欄徽章；開著的詳情面板。卡片換欄時不做飛行動畫：舊位置直接消失，新位置的卡片閃一圈品牌色外框約 2 秒，讓眼睛跟得上。

**不被即時更新打斷的東西**：正在拖的卡片（那張單被別人處理掉時，放開後才跳撞單對話框）、打開的當場回答面板與裡面打的字、對話框、看板的捲動位置。

**等待時間用哪一個時鐘**（`plan.md` 交給本檔的題目）。畫面上所有「等 {N} 分」「{N} 分鐘前」「做 {N} 分」都是「現在 − 某個時間」取整數分鐘（無條件捨去）。「做 {N} 分」的「某個時間」是第一次開始的時刻：中途中斷、停下的時間也算在內，不是累計工時，所以有中斷過的單，看板和員工 App 的計時本來就不一樣（使用者 2026-11-18 裁決）。「現在」用後端的時鐘：每次後端回應時，畫面記下「後端時間 − 這台裝置的時間」這個差，之後的「現在」＝裝置時間＋這個差。這樣櫃檯電腦的時間不準也不會算錯。算出來是負數時一律當 0，也就是顯示「剛剛」，不會出現負的分鐘數，也不會因為裝置時鐘快了而提早變橘、變紅或提早逾時。分鐘數每 10 秒重算一次，不需要等後端推送。頁副標的日期與「今天」的界線也用校正後的時間，照飯店當地日期。

## 驗證與錯誤回饋

- 輸入驗證：員工編號最多 12 字、照打的樣子送出，不轉大小寫、不去前後空白（與員工 App 一致），欄位不是空的就可以按登入（只打空白也可以按，送出後由後端回「員工編號或密碼不正確。」）；密碼最多 32 字、不能是空的；搜尋房號只收數字、最多 4 碼（打其他字元不會出現在框裡）；回覆最多 120 字、去掉前後空白後不能是空的，送出的是去掉前後空白的字；新密碼四條規則即時檢查，全部符合才能按「更新密碼」。這些都在輸入的當下擋，不跳提示
- 狀態衝突處理：後端說「這張單已經不是待派單」時，畫面先把這張單更新成最新狀態，再跳一個只有「好」的對話框。對話框的標題與第一句依「這張單被怎麼處理掉了」，最後一句依「我剛才想做什麼」：

| --- | --- | --- |
| 另一位櫃檯派走了 | 「這單已經被派走了」 | 「{人} 剛剛把 {房號} 派給{部門}。看板已更新成最新狀態，」 |
| 另一位櫃檯當場回答了（C-13） | 「這單已經回答過了」 | 「{人} 剛剛已經當場回答 {房號}。看板已更新成最新狀態，」 |

| 其他（例如後端沒說是哪一種） | 「這張單已經被處理了」 | 「{房號} 已經不在待派單。看板已更新成最新狀態，」 |

- 使用者可理解錯誤訊息：每一句都說「發生什麼事、這張單現在在哪、下一步做什麼」。送出失敗與復原失敗用對話框而不是自己會消失的浮條，因為櫃檯人員可能正在講電話，沒看到的話會以為單已經派出去了。讀取失敗用畫面中央的訊息加「重試」，同時自動再試（畫面上寫每 5 秒，實際每 4 秒，與提醒列期間的重讀同一個間隔，見畫面 9），成功後自己換回正常畫面。所有對話框只有一顆「好」（登出確認除外），按 Enter 或 Esc 也可以關

**鍵盤與螢幕報讀**。`spec.md` 不做鍵盤快速鍵，但基本的鍵盤操作要通：Tab 走得到每一顆可點的東西，焦點有 3px 品牌色外框（原型的樣式）；面板與對話框打開時焦點移進去、關閉時回到原本的位置；Esc 關閉最上面那一層。拖曳派單沒有鍵盤版，用鍵盤的人走詳情面板或待派單頁的按鈕。卡片給螢幕報讀軟體的標籤是「{房號} {標題}，{狀態}，{等待文字}」。浮條與提醒列是 `role="status"`，錯誤對話框是 `role="alertdialog"`。

### 看板清單（總覽看板、側欄徽章、頁副標）

範圍：還沒結束的單不限日期，加上今天結束的單（FR-041）；照資料模型的說法就是 `tasks.ended_at` 是空的單，加上 `ended_at` 落在今天的單。備品、其他類的完成與當場回答在完成當下就寫 `ended_at`，打掃單與工務單的 `done` 還在等查房或驗收、不寫，所以這一個條件同時涵蓋「已完成」欄與「已結案」欄的日期規則。清單裡每一張單要有：

| 資料 | 用在哪 |
| --- | --- |

請 `/api-plan` 回答的四件事：

1. 清單精簡、詳情另抓，還是清單一次帶齊？畫面兩種都接得住：詳情面板有載入中的樣子。建議清單帶到上表為止，歷程與「內容」裡清單沒有的（住客入住與退房日期、開單人、取消細節、各種「誰在幾點」）由單筆詳情帶。
2. 排序由誰排？畫面需要的三種順序見 FR-023。清單一次回完的話由畫面排即可。
3. 「今日排房」的判斷：原型看的是來源 `system`；`spec.md` 寫的是「系統指派的」。請確認「來源是 `system` 且還沒被轉派」是不是就等於系統班前排房指派，或另給一個欄位。
4. 「已完成」欄裡備品、其他類只留今天完成的，這個篩選請在後端做（畫面不該拿到昨天完成的備品單）；用上面 `ended_at` 的條件就會成立。

數量卡、欄頭數量與警示、未結案張數、側欄徽章都由畫面從這份清單算，不需要另外的統計介面；條件是清單回的是全館完整範圍，不分頁。

每一則的標題與全文，照飯店設定的順序。原型的五則是「早餐時間」「Wi-Fi」「退房時間」「健身房」「叫車」。飯店沒有設定時回空清單，畫面就不顯示那一排。

| --- | --- |

## 待決事項

下面幾件事不在 C-01 至 C-18 之內，是這一趟整理畫面時發現的缺口。

1. **歷程裡其他事件的句子**。`task_events` 有 24 種事件，原型與 `spec.md` 只寫了 16 種句子。同仁報修、工務單驗收通過與不通過、同仁自己暫停、恢復處理、同仁自己延後、退回待認領、被指派、被轉派、主管作廢、查房退回、抽查退回、住客評分等事件，在櫃檯的歷程上各寫哪一句，沒有出處。這些單現在就會出現在看板上。建議 `/dsl-refine` 時列一張完整對照表，句子比照手機 App 既有的用字。在那之前，實作遇到沒有句子的事件先不顯示那一筆。雛形為了讓示範資料的歷程看起來完整，替其中幾種放了暫定的句子（「報修「{標題}」，進工務待認領」「轉派給 {人}（原：{原負責人}）」「驗收通過，結案」「暫停處理（{原因}）」「取消這張單」「排房調整，這張單取消」「撤回報修」），這些都不是定案。
2. **復原沒有送成功**（網路中斷）。`spec.md` 只寫了復原的兩種「後端拒絕」，沒有寫送不出去的情形。本檔預設跳「沒有復原成功」對話框、浮條不再回來。
3. **「今日排房」怎麼判斷**。見「給 `/api-plan` 的資料需求」看板清單的第 3 點。
4. **篩選成只看「待派單」時拖曳沒有落點**。這時畫面上沒有「待認領」欄。本檔預設不特別處理（提示文字照常），派單走按鈕。若要處理，可以在只看「待派單」時暫時把「待認領」欄也顯示出來。
5. **「等最久」數量卡上，待派單的單標題要不要加「」**。原型不加，`spec.md` 的例子是待認領的單所以看不出來。本檔照原型不加。
6. **非住客來源的單出現在待派單**。`spec.md` 說只有住客打字的需求會停在待派單，待派單頁每列因此固定寫「· 住客掃碼 ·」。資料上若出現其他來源的 `triage` 單，這一段照實際來源顯示（「櫃檯開單」「系統排房」「同仁報修」）。
7. **很久以前的時間怎麼寫**。`spec.md` 與原型的寫法都只有分鐘（「等 {N} 分」「{N} 分鐘前建立」「接 {N} 分」）。還沒結束的單不限日期，班前排房的單到下午就是「370 分鐘前建立」，放三天的單會是四位數的分鐘。本檔照 `spec.md` 只寫分鐘；要不要在 60 分以上改成「{H} 小時 {M} 分」，待使用者決定。
